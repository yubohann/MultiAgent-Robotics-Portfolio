## 你在答辩中的定位

你不要把自己讲成“写了几张用例图、整理了几份文档”的人。系统分析负责人和需求负责人的核心价值，是把一个模糊的课程题目，变成边界清楚、角色清楚、流程清楚、功能清楚、验收清楚的系统方案。

你在答辩中的定位可以这样说：

> 我负责本项目的系统分析与需求建模工作，主要任务是明确超市管理系统的业务边界、用户角色、核心流程、功能模块、非功能要求和验收标准，并把这些需求落实到业务流程图、UML 用例图、数据流图、界面设计、数据库模型、后端接口和测试用例中。

老师听你讲时，最关心的不是你有没有背会“需求分析”这个词，而是你能不能证明：

1. 这个系统为什么要做这些模块。
2. 每个模块对应什么业务问题。
3. 管理员、收银员、店长、采购员、库管员等角色分别做什么。
4. 需求建模结果和后续设计、代码、测试是否一致。
5. 如果老师追问某个流程，你能不能从流程图讲到页面、数据表和测试用例。

你要记住一句主线：

> 我的工作是把“超市日常经营”拆成可管理的业务场景，再把业务场景转化成用例、流程、数据和验收项，保证后续开发不是凭感觉写代码，而是围绕需求闭环实现。

## 一、整个项目从需求角度怎么理解

这个项目是一个面向课程实验和课程设计的超市门店管理系统。它不是单一的收银程序，也不是只做商品列表，而是围绕小型超市门店的日常运营进行系统分析。

从需求角度看，超市门店每天会发生这些事情：

1. 管理员要维护商品资料，包括商品编码、条码、名称、分类、单位、进价、售价、最低库存和上下架状态。
2. 库管员或管理员要查看库存，发现低库存商品，处理库存调整、入库、盘点和库存流水。
3. 收银员要快速检索商品，加入购物车，选择支付方式，完成结算。
4. 销售完成后，系统要生成销售订单和销售明细，方便后续查询。
5. 店长或管理员要查看销售情况、订单数量、客单价、毛利、热销商品和分类占比。
6. 财务人员要处理收支流水、日结对账、供应商应付、付款记录和月结快照。
7. 管理员还要维护会员、员工、供应商和系统参数，支撑二期课程设计要求。
8. 管理员需要发布公告，收银员或其他用户要能阅读并留下已读记录。
9. 系统要有权限边界，不同角色不能看到或操作不属于自己的功能。
10. 项目需要测试用例、自动化测试、代码审查、截图和报告材料作为交付证据。

所以这个系统的需求主线可以概括为：

> 基础资料维护 -> 收银销售发生 -> 库存同步变化 -> 销售与财务留痕 -> 经营数据分析 -> 主数据和权限支撑。

你答辩时要把项目讲成“业务闭环”，不要讲成“页面集合”。

## 三、阶段一：项目启动与初步调查怎么讲

阶段一对应 `stage1-startup-management.md`。

这个阶段的重点是回答三个问题：

1. 谁参与项目，分别负责什么。
2. 项目为什么可做，有哪些风险。
3. 系统边界和初步功能范围是什么。

### 1. 团队角色

阶段一材料中，团队角色分为项目经理、系统分析师、系统构架师、咨询师、后端、前端、测试和设计等职责。

作为系统分析负责人，你重点负责：

1. 需求建模。
2. 用户角色梳理。
3. 测试用例和验收记录。
4. 将流程图、用例图和系统实现保持一致。

答辩时可以这样讲：

> 我的职责是连接业务和开发。一方面要理解超市门店的业务流程，另一方面要把这些流程整理成开发人员可以实现、测试人员可以验证的需求模型。

### 2. 初步会议记录

阶段一记录了几次关键会议：

| 时间 | 主题 | 对需求的影响 |
| --- | --- | --- |
| 2026-03-10 | 系统边界确认 | 确定先做商品、库存、财务三个一期模块，再补销售、会员等二期模块 |
| 2026-03-12 | 用户角色梳理 | 明确管理员、收银员、店长等角色 |
| 2026-03-15 | 技术栈确认 | 确定 Flask、Jinja2、SQLAlchemy、SQLite、静态 JS |
| 2026-03-18 | 交付物确认 | 明确代码、SQL、图表、报告、测试用例、截图都要进入 Gitee |

这几次会议能说明项目需求不是凭空想的，而是经过边界确认、角色梳理和交付物确认。

### 3. SWOT 与可行性

系统分析负责人需要说明项目为什么可行。

本项目的可行性可以从四个角度讲：

| 角度 | 结论 |
| --- | --- |
| 技术可行性 | Flask、SQLAlchemy、SQLite 足够支撑课程演示，开发成本低 |
| 经济可行性 | 使用开源技术和本地环境，不需要额外采购 |
| 操作可行性 | 浏览器访问，管理员和收银员分工明确，操作符合门店习惯 |
| 进度可行性 | 按 7 个阶段推进，先完成核心模块，再补二期模块 |

风险也要讲清楚：

1. 需求图和代码实现可能不一致。
2. 测试滞后会导致业务闭环无法证明。
3. 截图缺失会影响课程验收证据。
4. SQLite 更适合课程演示，不适合多门店高并发生产环境。

你可以说：

> 我在阶段一就把风险写进材料，是为了提醒后续开发不能只补页面，还要补测试、截图和代码审查记录，保证最终报告和系统实现一致。

## 四、阶段二：WBS、甘特图和关键路径怎么讲

阶段二对应 `stage2-wbs-gantt-critical-path.md`。

这一阶段的作用是把“要做一个超市管理系统”拆成可管理的任务。

### 1. WBS 任务分解

WBS 中把任务拆成：

1. 团队角色与计划确认。
2. 初步调查与会议记录。
3. SWOT 与可行性报告。
4. 功能模块拆分。
5. 技术方案与架构图。
6. 商品录入原型。
7. 泳道图与业务流程。
8. UML 用例图。
9. ER 与 ORM 建模。
10. 界面设计文档。
11. 测试用例设计。
12. 自动化测试编写。
13. 系统代码补齐。
14. 代码审查与截图留存。
15. 最终报告归档。

这里要强调：需求工作不是阶段三才开始，阶段一和阶段二已经在做边界、角色、功能、进度和风险分析。

### 2. 甘特图与时间安排

阶段二将项目排成 6 周：

| 周期 | 工作重点 |
| --- | --- |
| 第 1 周 | 团队分工、初步调查、SWOT、可行性 |
| 第 2 周 | 功能拆分、技术方案、原型 |
| 第 3 周 | 业务流程图、UML 用例图 |
| 第 4 周 | ER/ORM 建模、界面设计 |

| 第 6 周 | 系统补齐、代码审查、截图、报告归档 |

这样安排的逻辑是：先分析需求，再做设计，再实现，再测试和归档。

### 3. 关键路径

关键路径是：

`团队角色与计划确认 -> 初步调查 -> 功能模块拆分 -> UML 用例图 -> ER 与 ORM 建模 -> 系统代码补齐 -> 自动化测试编写 -> 代码审查与截图留存 -> 最终报告归档`

你可以这样解释：

> 关键路径上的任务决定了项目能否按时完成。尤其是功能模块拆分和 UML 用例图，如果前期需求没有拆清楚，后面的数据模型、页面设计和测试用例都会跟着偏。

## 五、系统边界怎么讲

系统边界是需求负责人最应该讲清楚的部分。

本项目的系统边界可以这样定义：

> 本系统面向单店超市场景，主要管理门店内部的商品、库存、收银、销售、财务、公告、经营分析和基础主数据。系统默认在本机或门店局域网环境运行，使用浏览器访问，数据库采用 SQLite，适合作为课程设计和小规模演示系统。

### 1. 系统内部包含

| 范围 | 说明 |
| --- | --- |
| 用户与权限 | 管理员、收银员登录，管理员申请审核 |
| 商品管理 | 商品新增、编辑、上下架、删除、导入 |
| 库存管理 | 库存列表、库存流水、低库存预警、库存调整 |
| 收银结算 | 商品检索、购物车、支付方式、优惠、结算 |
| 销售管理 | 销售订单查询、订单明细 |
| 财务管理 | 收支流水、日结对账、供应商应付、付款、月结 |
| 经营分析 | 销售概览、趋势、热销商品、分类占比 |
| 公告管理 | 公告发布、上下线、未读、已读 |
| 智能助手 | 库存、销售、商品和帮助类问答 |
| 二期主数据 | 会员、员工、供应商、系统参数 |

### 2. 系统外部不包含或只做设想

| 范围 | 说明 |
| --- | --- |
| 多门店总部系统 | 当前按单店课程演示设计 |
| 真实支付通道 | 当前记录支付方式，不直接接入微信、支付宝真实支付 API |
| 真实扫码枪设备 | 当前支持条码字段和查询逻辑，硬件接入作为外部集成设想 |
| 完整采购订单流 | 当前重点覆盖供应商和应付，采购订单可作为扩展 |
| 大规模并发 | SQLite 更适合本地演示，生产可迁移到 MySQL 或 PostgreSQL |

答辩时如果老师问“为什么没做真实支付”，你可以回答：

> 本课程项目重点是系统分析、业务流程、数据模型、界面和测试闭环。真实支付属于外部平台集成，需要商户资质和支付 SDK，不适合作为课程核心范围，所以本系统只记录支付方式和交易结果。

## 六、用户角色与职责

本系统至少包含以下角色：

| 角色 | 主要职责 | 对应功能 |
| --- | --- | --- |
| 管理员 | 管理后台、维护资料、审核申请、发布公告 | 商品、库存、销售、财务、公告、会员、员工、供应商、系统参数 |
| 收银员 | 完成商品检索、购物车和收银结算 | 收银台、公告阅读 |
| 店长 | 查看经营情况、销售统计和财务概览 | 首页概览、销售管理、财务管理、经营分析 |
| 库管员 | 查看库存、处理库存调整和预警 | 库存管理、库存流水 |
| 财务人员 | 处理收支、对账、应付和月结 | 财务管理 |
| 采购员 | 维护供应商和补货相关信息 | 供应商管理、库存预警与补货流程 |
| 系统分析/测试人员 | 维护需求、测试用例和验收记录 | 文档、测试、截图、审查记录 |

实际代码中，登录角色主要是 `admin` 和 `cashier`。店长、库管员、财务人员、采购员在课程分析中作为业务角色出现，在实现中多数由管理员角色承接。这一点要讲清楚，避免老师追问角色为什么和代码不完全一一对应。

你可以这样说：

> 需求建模中我保留了业务角色，是为了把职责分析清楚；实现阶段为了课程复杂度可控，将店长、库管、财务和采购等后台职责统一归入管理员权限，收银员单独保留为前台操作角色。

## 七、功能需求总体拆分

系统功能可以按业务域拆成 12 个模块。

| 模块 | 功能需求 |
| --- | --- |
| 账号认证 | 登录、退出、注册、管理员申请审核、角色权限 |
| 商品管理 | 商品 CRUD、分类、编码条码、价格、上下架、批量导入 |
| 库存管理 | 当前库存、库存流水、库存预警、库存调整 |
| 收银结算 | 商品检索、购物车、支付方式、优惠金额、结算、小票 |
| 销售管理 | 订单列表、条件筛选、订单明细 |
| 财务管理 | 收支流水、日结对账、应付登记、付款记录、月结 |
| 经营分析 | 销售额、订单数、客单价、毛利、趋势、排行、分类占比 |
| 公告管理 | 公告发布、目标角色、上下线、未读和已读 |
| 智能助手 | 库存问答、销售问答、商品问答、帮助问答 |
| 会员管理 | 会员档案、等级、积分、启停 |
| 员工管理 | 员工档案、岗位、排班、启停 |
| 供应商与系统管理 | 供应商档案、结算周期、系统参数 |

功能拆分的依据不是页面数量，而是业务职责。商品管理解决“卖什么”，库存管理解决“还有多少”，收银结算解决“怎么卖”，销售管理解决“卖了什么”，财务管理解决“钱和账如何核对”，经营分析解决“经营效果如何”。

## 八、非功能需求怎么讲

需求负责人不能只讲功能，还要讲非功能要求。

| 非功能要求 | 本项目中的体现 |
| --- | --- |
| 易用性 | 后台统一侧边栏和顶部栏，管理页面采用搜索、筛选、表格、分页和弹窗 |
| 可维护性 | 后端按 routes、services、models 分层，前端按模板和 JS 分文件 |
| 可追踪性 | 库存流水、财务流水、公告已读、代码审查和测试结果都可追溯 |
| 安全性 | 密码哈希、登录 Session、角色权限、管理员审核 |
| 可靠性 | 收银结算使用校验和事务回滚，避免库存和订单不一致 |
| 可测试性 | 17 个测试用例，pytest 自动化测试，coverage 结果留存 |
| 可部署性 | README 提供 uv、Python、启动命令和默认账号 |
| 可扩展性 | 二期主数据模块、系统参数、SQLAlchemy ORM 和服务层结构便于扩展 |

答辩时你可以说：

> 非功能需求决定系统能不能被稳定使用。比如库存流水属于可追踪性，角色权限属于安全性，自动化测试属于可测试性，分层结构属于可维护性。

## 九、业务流程图怎么讲

阶段三归档了 12 组业务流程图，满足任务书“不少于 10 组泳道图或业务流程图”的要求。

| 序号 | 流程 | 需求重点 |
| --- | --- | --- |
| 1 | 销售收银流程 | 商品检索、购物车、支付、生成销售单、扣减库存 |
| 2 | 采购入库流程 | 供应商、商品入库、库存增加、库存流水 |
| 3 | 库存盘点流程 | 实际数量核对、差异调整、流水记录 |
| 4 | 退货退款流程 | 订单核对、退款处理、库存回补 |
| 5 | 库存预警与补货流程 | 低库存识别、补货建议、采购协同 |
| 6 | 会员积分流程 | 会员识别、积分累计、积分调整 |
| 7 | 班次交接与日结流程 | 收银班次、应收实收核对、差异记录 |
| 8 | 商品调价流程 | 商品价格变更、历史订单价格快照 |
| 9 | 管理员注册审核流程 | 管理员申请、审核、通过或拒绝 |
| 10 | 商品批量导入流程 | Excel/CSV 导入、校验、创建商品和库存 |
| 11 | 财务日结对账流程 | 按日期和支付方式计算应收、录入实收、保存差异 |
| 12 | 公告发布与阅读流程 | 管理员发布、用户查看、未读变已读 |

讲流程图时，不要每张都展开。答辩一般重点讲 2 到 3 个代表流程：

1. 销售收银流程：最能体现业务闭环。
2. 库存预警与补货流程：体现库存管理价值。
3. 财务日结对账流程：体现经营结果留痕。

## 十、代表流程一：销售收银流程

销售收银是系统最核心的业务流程。

可以按下面顺序讲：

1. 收银员登录系统，进入收银台。
2. 收银员输入商品名称、编码或条码。
3. 系统查询上架且有库存的商品。
4. 收银员把商品加入购物车。
5. 系统实时计算商品数量、应收金额和实收金额。
6. 收银员选择支付方式，必要时输入优惠金额。
7. 系统校验购物车不为空、商品未下架、库存充足、支付方式合法、优惠金额合法。
8. 校验通过后生成销售订单和销售明细。
9. 系统扣减库存，并写入库存流水。
10. 收银员可以打印小票。
11. 管理员后续可在销售管理中查询订单，在财务模块中查看收入，在经营分析中查看统计。

这个流程说明“需求不是孤立功能”，一次收银会同时影响销售、库存、财务和分析。

答辩时可以这样总结：

> 销售收银流程是整个系统的主交易流程，它把商品、库存、订单、财务和报表连接起来，是需求分析中的核心闭环。

## 十一、代表流程二：库存预警与补货流程

库存预警流程体现系统对门店运营的支持。

流程可以这样讲：

1. 商品资料中保存最低库存。
2. 库存表保存当前库存。
3. 系统对比当前库存和最低库存。
4. 如果当前库存低于或等于最低库存，就进入预警列表。
5. 管理员或库管员查看预警商品。
6. 根据预警情况联系供应商或进行补货。
7. 入库后库存数量增加。
8. 系统写入库存流水，记录变化原因。

这个流程体现的是从“发现问题”到“处理问题”的管理能力。

你可以说：

> 库存预警不是单纯显示红色数字，而是需求上要帮助门店提前发现缺货风险，避免热销商品断货。

## 十二、代表流程三：财务日结对账流程

财务日结流程体现系统对金额一致性的管理。

流程可以这样讲：

1. 系统根据当天销售订单计算不同支付方式的应收金额。
2. 管理员或财务人员进入财务管理页面。
3. 选择日期和支付方式。
4. 系统显示应收金额。
5. 财务人员录入实际收到的金额。
6. 系统计算差异金额。
7. 保存对账记录。
8. 后续可以在财务模块中查看对账情况和月结结果。

这个流程可以回答老师关于“财务管理是不是只是显示销售额”的问题。

你可以说：

> 财务日结对账的需求是把系统账面金额和实际收款金额进行核对，并保存差异，保证经营结果可追溯。

各位老师好，我在本项目中主要负责系统分析和需求建模工作。我的任务不是直接写某一个页面或某一个接口，而是先把超市门店的业务边界、用户角色、核心流程和功能范围分析清楚，再把这些需求转化为后续设计、开发和测试可以依据的材料。

本项目是一个面向课程实验和课程设计的超市管理系统。从需求角度看，它不是单一的收银程序，而是围绕超市日常经营形成的业务闭环。管理员需要维护商品、库存、会员、员工、供应商和系统参数；收银员需要检索商品、加入购物车并完成结算；销售完成后系统要生成销售订单和销售明细，同时扣减库存并留下库存流水；财务人员或管理员需要进行收支管理、日结对账、供应商应付和月结；店长需要查看销售趋势、热销商品、分类占比和毛利指标。因此，我把系统主线概括为：基础资料维护、收银交易发生、库存同步变化、销售与财务留痕、经营数据分析、主数据和权限支撑。

在阶段一，我主要参与了项目启动和初步调查。我们先明确团队角色、成员技能、每周投入时间和风险安排，然后通过会议记录确认系统边界。2026 年 3 月 10 日，我们确定先完成商品、库存、财务等一期核心模块，再补销售、会员等二期模块；3 月 12 日，我们梳理用户角色，明确管理员负责后台管理，收银员负责收银台，店长查看分析和财务；3 月 18 日，我们确认代码、SQL、图表、报告、测试用例和截图都需要纳入 Gitee。通过这些前期工作，项目范围不是临时拼出来的，而是有分析过程和材料支撑的。

在阶段二，我把需求进一步拆成 WBS、甘特图和关键路径。项目按六周推进：第一周做团队分工和初步调查，第二周做功能拆分和技术方案，第三周做业务流程图和 UML 用例图，第四周做数据建模和界面设计，第五周做测试用例和自动化测试，第六周做系统补齐、代码审查、截图和报告归档。关键路径从团队计划、初步调查、功能模块拆分、UML 用例图，到 ER 建模、代码补齐、自动化测试和最终归档。这样安排是为了保证先分析需求，再设计实现，最后测试验收。

在系统边界上，我把本项目定义为单店超市管理系统。系统内部包含账号权限、商品管理、库存管理、收银结算、销售管理、财务管理、经营分析、公告管理、智能助手以及会员、员工、供应商、系统参数等二期主数据模块。系统外部不把多门店总部系统、真实支付平台、真实扫码枪硬件和大规模并发作为课程核心范围。这样做是为了让项目既完整，又不会超出课程设计可控范围。

在用户角色上，我区分了管理员、收银员、店长、库管员、财务人员和采购员等业务角色。管理员负责后台资料和权限管理，收银员负责收银结算，店长关注经营分析，库管员关注库存和预警，财务人员关注对账和月结，采购员关注供应商和补货。实际系统实现中，为了控制课程复杂度，店长、库管、财务和采购这些后台职责主要由管理员角色承接，收银员作为独立角色保留。这样既能在需求分析中体现真实职责，也能让代码实现保持简洁。

在需求建模方面，本项目归档了 12 组业务流程图，超过任务书不少于 10 组的要求。这些流程包括销售收银、采购入库、库存盘点、退货退款、库存预警与补货、会员积分、班次交接与日结、商品调价、管理员注册审核、商品批量导入、财务日结对账、公告发布与阅读。其中我重点讲销售收银、库存预警和财务日结三个代表流程。销售收银流程体现商品、库存、订单、财务和分析的主交易闭环；库存预警流程体现系统如何帮助门店发现缺货风险；财务日结流程体现系统如何把账面金额和实际收款进行核对。

同时，本项目也归档了 12 组模块级 UML 用例图，覆盖账号认证、商品管理、库存管理、收银结算、销售管理、财务管理、经营分析、公告管理、智能助手、会员管理、员工管理、供应商与系统管理。每组用例都明确了参与者和主要目标。例如收银员的目标不是简单点击按钮，而是完成一笔交易；管理员的目标不是打开后台页面，而是维护资料、控制权限并查看经营情况；财务人员的目标是完成对账和月结。

为了保证需求不是空的，我还做了需求到实现的映射。账号认证对应登录页、注册页、管理员审核页，以及 `routes/auth.py` 和 `services/auth.py`；商品管理对应 `product.html`、`routes/product.py` 和 `services/products.py`；库存管理对应 `inventory.html`、`routes/inventory.py` 和 `services/inventory.py`；收银结算对应 `cashier.html`、`routes/cashier.py` 和 `services/cashier.py`；会员、员工、供应商和系统参数对应统一的 `master_data.html`、`routes/second_phase.py` 和 `services/second_phase.py`。也就是说，报告中的每组需求，都能在页面和代码中找到落点。

从数据角度看，需求也进一步转化成数据库模型。例如用户登录和权限对应用户表和管理员申请表，商品维护对应分类表和商品表，库存追踪对应库存表和库存流水表，收银结算对应销售订单表和销售明细表，财务对账对应财务流水表和日结对账表，公告已读对应公告表和公告已读记录表。这样数据模型不是后端单独设计的，而是从需求对象中抽象出来的。

最后，需求还要落到验收。阶段六测试用例文档列出了 17 个测试点，包括管理员登录、登录失败、管理员审核、商品新增、商品编码重复、库存调整、库存不足不能结算、收银结算成功、销售订单明细、财务日结对账、公告发布与已读、角色权限控制、会员管理、员工供应商系统管理、Excel 商品导入、二期异常路径和二期 API 功能流。这些测试用例证明系统不仅能跑正常流程，也能处理异常情况。

总体来说，我的工作是把一个“超市管理系统”的题目，分析成清晰的业务边界、角色职责、功能模块、流程图、用例图、数据流、页面映射和测试验收项。通过这些工作，后续的数据建模、界面设计、后端实现和自动化测试都有了依据，也保证最终报告、图表、代码和测试结果能够互相对应。

## 二十四、老师可能追问的问题

### 问题 1：这个系统的核心需求是什么？

核心需求是支撑超市门店日常经营闭环，包括商品资料维护、库存管理、收银结算、销售订单、财务对账、经营分析和基础主数据管理。最核心的是“收银结算后能生成订单、扣减库存，并进入销售和财务统计”。

### 问题 2：为什么要做这么多流程图？

因为超市管理不是单一操作，而是多个业务流程组成的系统。流程图能说明不同角色之间如何协作、数据如何流转、系统在每一步承担什么职责。本项目归档了 12 组流程图，超过任务书不少于 10 组的要求。

### 问题 3：用例图和流程图有什么区别？

用例图强调参与者和系统提供的功能，回答“谁要用系统做什么”；流程图强调业务步骤和先后顺序，回答“一件事情从开始到结束怎么发生”。两者互补。

### 问题 4：为什么需求角色有店长、库管、财务、采购，但代码里主要是管理员和收银员？

需求建模保留业务角色，是为了把职责分析清楚。实现阶段为了课程复杂度可控，把店长、库管、财务、采购等后台职责统一归入管理员权限，收银员单独作为前台角色。这是需求分析和实现范围之间的合理简化。

### 问题 5：怎么证明需求真的落地了？

可以从三方面证明：第一，阶段三文档中每组用例都映射到页面和后端模块；第二，阶段五界面文档列出了 13 个页面承接需求；第三，阶段六测试文档列出了 17 个测试用例，并映射到 `tests/` 自动化测试。

### 问题 6：最重要的业务流程是哪一个？

最重要的是销售收银流程。它从商品检索开始，到购物车、支付、结算、销售订单、销售明细、库存扣减、库存流水、财务收入和经营分析，贯穿了系统最核心的数据链路。

### 问题 7：哪些需求属于二期课程设计？

二期主要包括会员管理、员工管理、销售管理、供应商管理和系统管理。本项目已补齐会员、员工、供应商和系统参数模块，销售管理也已实现。

### 问题 8：为什么没有接入真实支付？

真实支付需要第三方平台资质、支付 SDK 和安全审核，超出课程核心范围。本项目重点是系统分析、业务流程、数据模型、界面、后端和测试闭环，所以只记录支付方式和交易结果。

### 问题 9：需求怎么转化成测试？

每个关键需求都对应测试用例。例如登录需求对应登录成功和登录失败测试；商品管理对应商品新增和编码重复测试；收银需求对应库存不足和结算成功测试；财务需求对应日结对账测试；权限需求对应未登录和角色不符测试。

### 问题 10：你作为需求负责人最大的贡献是什么？

我的最大贡献是把课程题目变成可执行、可实现、可验收的需求体系。具体包括系统边界、用户角色、功能拆分、业务流程图、UML 用例图、需求到页面和代码的映射，以及测试验收标准。
