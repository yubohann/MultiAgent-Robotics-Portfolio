适用角色：数据建模负责人 / 后端负责人

## 你在答辩中的定位

你不要把自己讲成“只建了几张表、写了几个接口”的人。你的定位应该是：

> 我负责把超市经营业务抽象成数据库模型，并把商品、库存、收银、销售、财务、公告、会员、员工、供应商和系统参数等模块，落成可运行、可追踪、可测试的后端业务闭环。

答辩时，你要让老师相信三件事：

1. 数据模型不是随便设计的，而是从超市真实业务流程抽象出来的。
2. 后端不是页面的附属品，而是负责业务规则、数据一致性、权限控制和错误处理。
3. 项目不是静态演示，数据库、服务层、路由层、测试代码和演示数据可以互相印证。

你可以先记住一句总纲：

> 本项目后端以 Flask 为应用框架，以 SQLAlchemy ORM 管理数据模型，以 SQLite 保存演示数据，通过路由层接收请求、服务层处理业务规则、模型层维护实体关系，最终支撑“资料维护 -> 收银交易 -> 库存变动 -> 销售留痕 -> 财务汇总 -> 经营分析”的完整闭环。

## 一、整个项目从后端角度怎么理解

这个系统是一个课程设计版的超市门店管理系统。它看起来有很多页面，但从后端角度看，核心只有一条主线：

1. 管理员维护商品、分类、会员、员工、供应商、系统参数等基础资料。
2. 商品必须有编码、条码、分类、售价、进价、最低库存和上下架状态。
3. 商品创建后要有库存记录，库存发生变化时要写库存流水。
4. 收银员在收银台查询可售商品，把商品加入购物车并提交结算。
5. 后端校验商品是否存在、是否上架、库存是否足够、支付方式是否合法、优惠金额是否合法。
6. 校验通过后，后端生成销售订单和销售明细，同时扣减库存。
7. 库存扣减不是只改一个数字，还要写入库存变动日志，方便追踪。
8. 销售数据进入销售查询、财务对账和经营分析模块。
9. 财务模块可以登记其他收支、保存日结对账、维护供应商应付、记录付款和生成月结快照。
10. 公告模块支持管理员发布通知，系统记录用户是否已读。
11. 测试模块用 pytest 验证登录、权限、核心业务流、二期主数据和异常路径。

所以你要把项目讲成一个“可流转的数据系统”，而不是“几个页面加几个表”。

## 二、技术架构怎么讲

后端主要采用 Flask + SQLAlchemy + SQLite。

如果老师问“整个项目用了哪些技术栈”，不能只回答后端三件套。这个项目是一个完整的 Web 管理系统，技术栈可以按“前端展示、后端服务、数据持久化、数据导入、测试验证、工程交付”六个层面说明。

| 层面 | 技术栈 | 在项目中的具体作用 |
| --- | --- | --- |
| 运行环境 | Python 3.12+、uv、虚拟环境 `.venv` | Python 负责后端业务实现；uv 负责依赖同步和命令运行；虚拟环境保证依赖版本可复现 |
| Web 后端 | Flask | 提供页面路由和 REST 风格 API，例如商品、库存、收银、销售、财务、公告、二期主数据等接口 |
| 数据访问 | Flask-SQLAlchemy、SQLAlchemy ORM | 用模型类映射数据库表，负责对象创建、查询、分页、关联关系和事务提交 |

从后端负责人角度，可以把这些技术串成一句话：

> 本项目采用 Python + Flask 构建后端应用，用 SQLAlchemy ORM 管理 19 张核心业务表，用 SQLite 保存本地演示数据库；前端采用 Jinja2 模板、Tailwind CSS、原生 JavaScript、Fetch API 和 Chart.js 实现页面展示、异步交互和经营分析图表；商品批量导入使用 Python csv 标准库和 openpyxl；测试使用 pytest、coverage 和内存 SQLite，保证核心业务逻辑可运行、可验证、可复现。

还可以再补一句更贴近答辩的问题：

> 我们没有使用复杂的前后端分离框架，是因为课程设计重点是业务闭环、数据建模和后端一致性。Flask + Jinja2 + 原生 JavaScript 的组合足够支撑管理系统页面和 API 调用，同时部署简单，老师拉取仓库后用 `uv sync` 和 `uv run python run.py` 就可以复现。

### 技术栈概念白话解释

技术栈就是为了把系统做出来，用到的一整套语言、框架、工具和库。可以把它理解成盖房子时用到的材料、工具和施工方法。

1. Python  
Python 是后端编程语言。项目里的业务逻辑基本都是 Python 写的，例如商品新增、库存扣减、收银结算、财务统计和自动化测试。

2. Flask  
Flask 是 Python 的 Web 后端框架。它负责让项目变成一个可以通过浏览器访问的网站。浏览器访问 `/product`、`/cashier`、`/api/products` 这些地址时，就是 Flask 接收请求，然后决定返回页面还是返回数据。

3. SQLAlchemy / Flask-SQLAlchemy  
SQLAlchemy 是数据库操作工具，Flask-SQLAlchemy 是它和 Flask 的集成版本。它让后端可以用 Python 类操作数据库，而不是到处手写 SQL。例如 `Product` 类对应 `products` 表，创建一个 `Product` 对象就相当于准备新增一条商品记录。

4. ORM  
ORM 不是一个具体库，而是一种思想，意思是对象关系映射。它把数据库表映射成 Python 类，把表中的一行数据映射成 Python 对象。这样写业务代码更接近“操作对象”，而不是直接拼 SQL 字符串。

5. SQLite  
SQLite 是数据库。它不需要单独安装数据库服务器，而是直接把数据保存在一个 `.db` 文件里。本项目的数据文件是 `data/supermarket.db`，适合课程设计、本地演示和提交。

6. Jinja2  
Jinja2 是 Flask 常用的模板引擎。它负责生成 HTML 页面。简单说，后端把数据交给 Jinja2，Jinja2 把数据填进页面模板里，最后浏览器看到完整页面。

7. HTML  
HTML 是网页结构。页面里的标题、表格、按钮、输入框、弹窗，本质上都是 HTML 元素。

8. CSS  
CSS 是网页样式。它决定页面好不好看，例如颜色、字体、间距、边框、布局和按钮样式。

9. Tailwind CSS  
Tailwind 是 CSS 工具库。它提供很多现成样式类，例如 `text-slate-800`、`rounded-lg`、`px-4`。写页面时可以直接组合这些类，快速做出统一风格的管理系统界面。

10. JavaScript  
JavaScript 是前端交互语言。点击“新增商品”、搜索商品、上传 Excel、加入购物车、结算订单、刷新图表，这些动态交互都是 JavaScript 做的。

11. Fetch API  
Fetch 是浏览器自带的请求工具。前端用它向后端接口要数据或提交数据。例如商品页面用 `fetch('/api/products')` 获取商品列表。

12. JSON  
JSON 是前后端传数据的格式。例如后端返回 `{ "success": true, "message": "创建成功" }`，前端拿到后就知道操作成功了。

13. FormData  
FormData 是前端上传表单和文件用的工具。商品批量导入时，前端把 CSV 或 Excel 文件放进 FormData，再发送给 Flask 后端。

14. Chart.js  
Chart.js 是前端图表库。经营分析页面里的销售趋势图、分类占比图，就是用 Chart.js 把后端统计数据画成图。

15. Python csv  
`csv` 是 Python 标准库。它用来读取 CSV 表格文件。商品批量导入 CSV 时，后端用它逐行解析商品编码、名称、价格、库存等字段。

16. openpyxl  
openpyxl 是 Python 读取 Excel 文件的库。商品批量导入 `.xlsx` 文件时，后端用 openpyxl 读取表头和每一行商品数据。

17. python-dotenv  
python-dotenv 用来读取 `.env` 环境变量文件。比如智能助手接口密钥、模型配置、运行环境配置，可以放在 `.env` 里，不直接写死在代码中。

18. logging / RotatingFileHandler  
logging 是 Python 的日志系统。项目用它记录接口访问、状态码、耗时和异常。RotatingFileHandler 的作用是日志文件太大时自动轮转，避免一个日志文件无限增长。

19. Session  
Session 是登录状态保存机制。用户登录后，后端会记住当前用户是谁、是什么角色。后续访问商品管理、收银台等页面时，系统就能判断有没有登录、有没有权限。

20. Werkzeug 密码哈希  
Werkzeug 是 Flask 生态里的基础工具库。项目用它做密码哈希，也就是不直接保存明文密码，而是保存加密后的密码摘要。

21. pytest  
pytest 是自动化测试框架。它用来验证系统功能是否正确，例如登录是否成功、商品创建后库存是否生成、库存不足时收银是否失败。

22. coverage  
coverage 是测试覆盖率工具。它统计测试代码覆盖了多少后端代码。答辩时可以用它证明系统不是只写了功能，还做了自动化验证。

23. uv  
uv 是 Python 包管理和运行工具。它负责安装依赖、创建虚拟环境、运行命令。例如 `uv sync` 安装依赖，`uv run pytest` 运行测试。

24. Markdown  
Markdown 是文档格式。项目里的讲解稿、测试说明、代码审查记录、PPT 大纲等，很多都是 `.md` 文件。

25. drawio / PNG  
drawio 是画流程图、架构图、ER 图、泳道图的工具。`.drawio` 是可编辑源文件，`.png` 是导出的图片，方便放进报告和 PPT。

26. Git / Gitee  
Git 是版本控制工具，Gitee 是代码托管平台。Git 负责记录每次修改，Gitee 用来远程保存和提交课程设计成果。

这一段可以背成答辩总结：

> 本项目采用 Python 作为后端开发语言，Flask 作为 Web 框架，SQLAlchemy ORM 操作 SQLite 数据库；前端使用 Jinja2 模板、HTML、Tailwind CSS、原生 JavaScript、Fetch API 和 Chart.js；商品导入使用 csv 和 openpyxl；配置使用 python-dotenv，日志使用 logging；测试使用 pytest 和 coverage；工程管理使用 uv、Git 和 Gitee；文档与图表交付使用 Markdown、drawio 和 PNG。整体技术栈比较轻量，适合课程设计本地运行、演示和验收。

## 三、应用启动与初始化逻辑

后端应用创建在 `app/__init__.py` 的 `create_app()` 中。

启动流程可以这样讲：

1. 创建 Flask 应用对象。
2. 从 `config.py` 加载配置。
3. 调用 `_setup_logging(app)` 初始化日志。
4. 初始化 SQLAlchemy。
5. 在应用上下文中导入所有模型类。
6. 调用 `db.create_all()` 创建数据表。
7. 如果配置允许初始化默认数据，就创建默认用户、默认分类、二期模块默认资料。
8. 如果商品表为空，则执行 `data/SQL/seed_data.sql` 导入演示数据。
9. 调用 `register_routes(app)` 注册所有业务路由。

默认账号如下：

| 角色 | 用户名 | 密码 | 说明 |
| --- | --- | --- | --- |
| 管理员 | `admin` | `admin123` | 拥有后台管理权限 |
| 收银员 | `cashier01` | `123456` | 主要进入收银台 |

这里要强调一点：系统不是依赖手动建库才能运行。首次启动时可以自动建表、自动创建默认账号、自动导入演示数据。这样答辩时老师如果拉取项目，能够比较快地复现运行效果。

## 四、日志与配置设计

`config.py` 中配置了数据库、日志和大模型相关参数。

关键配置包括：

| 配置 | 作用 |
| --- | --- |
| `SQLALCHEMY_DATABASE_URI` | 指向 `data/supermarket.db` |
| `SQLALCHEMY_TRACK_MODIFICATIONS` | 关闭 SQLAlchemy 修改追踪，减少额外开销 |
| `LOG_FILE` | 日志文件路径，默认写入 `log/app.log` |
| `LOG_LEVEL` | 日志等级 |
| `LOG_MAX_BYTES`、`LOG_BACKUP_COUNT` | 控制日志轮转 |
| `LLM_PROVIDER`、`LLM_API_KEY`、`LLM_MODEL` | 智能助手模块预留的大模型配置 |

`app/__init__.py` 中的 `_setup_logging()` 使用 `RotatingFileHandler`，会记录每个请求的方法、路径、状态码、耗时和 IP。如果发生未处理异常，也会写入日志。

答辩时可以这样说：

> 后端不仅实现功能，也考虑了运行可维护性。日志记录可以帮助定位接口错误、性能异常和未处理异常，这一点在实际系统中很重要。

## 五、数据建模总体思路

数据建模不是先想“我要建多少张表”，而是先识别业务对象。

本系统的数据对象可以分为六组：

| 实体组 | 代表表 | 解决的问题 |
| --- | --- | --- |
| 账号与权限 | `users`、`admin_signup_requests` | 谁能登录、是什么角色、管理员申请如何审核 |
| 公告与消息 | `announcements`、`announcement_reads` | 公告发布给谁、谁已经读过 |
| 商品与库存 | `categories`、`products`、`inventory`、`inventory_logs` | 卖什么、库存多少、库存为什么变化 |
| 销售交易 | `sales`、`sale_items` | 哪笔订单、谁收银、卖了哪些商品、金额是多少 |
| 财务与对账 | `finance_transactions`、`cash_reconciliations`、`supplier_payables`、`payable_payments`、`finance_period_closings` | 收支、对账、应付、付款、月结 |
| 二期主数据 | `members`、`employees`、`suppliers`、`system_settings` | 会员、员工、供应商、系统参数 |

整个数据库可以概括为 19 张核心表。它们不是平铺的，而是围绕经营主线组合：

> 商品和库存是交易基础，销售订单是交易结果，库存流水和财务流水是过程留痕，会员、员工、供应商和系统参数是运营支撑，公告和账号权限是管理支撑。

## 六、核心数据表逐组讲解

### 1. 用户与管理员申请

核心表：

| 表 | 模型文件 | 作用 |
| --- | --- | --- |
| `users` | `app/models/user.py` | 保存登录用户、密码哈希、真实姓名、角色和启用状态 |
| `admin_signup_requests` | `app/models/admin_signup_request.py` | 保存管理员注册申请、审核状态、审核人和拒绝原因 |

`users` 表中的角色主要有 `admin` 和 `cashier`。管理员可以访问后台管理功能，收银员主要访问收银台。

密码不是明文保存，而是通过 `User.set_password()` 写入哈希值，通过 `check_password()` 校验。这一点可以说明系统对账号安全有基本考虑。

管理员注册没有直接创建账号，而是先进入 `admin_signup_requests` 表。管理员审核通过后，再创建正式管理员账号。这个流程可以回答老师关于“权限怎么控制”的问题。

### 2. 公告与已读记录

核心表：

| 表 | 模型文件 | 作用 |
| --- | --- | --- |
| `announcements` | `app/models/announcement.py` | 保存公告标题、内容、级别、目标角色、发布状态 |
| `announcement_reads` | `app/models/announcement_read.py` | 保存某个用户是否读过某条公告 |

公告表中有 `target_role`，可以设置公告面向全部用户、管理员或收银员。已读表通过 `announcement_id` 和 `user_id` 关联公告与用户。

这个设计的意义是：公告不是简单展示一段文字，而是可以精确判断某个用户有没有读过某条公告。

### 3. 商品与分类

核心表：

| 表 | 模型文件 | 作用 |
| --- | --- | --- |
| `categories` | `app/models/category.py` | 商品分类，支持父级字段和排序 |
| `products` | `app/models/product.py` | 商品主数据 |

`products` 表是商品管理的核心，主要字段包括：

| 字段 | 含义 |
| --- | --- |
| `product_id` | 商品主键 |
| `barcode` | 条码，唯一 |
| `product_code` | 商品编码，唯一且不能为空 |
| `product_name` | 商品名称 |
| `category_id` | 商品分类外键 |
| `unit` | 单位 |
| `purchase_price` | 进价 |
| `selling_price` | 售价 |
| `min_stock` | 最低库存 |
| `status` | 上架或下架 |

为什么同时保存进价和售价？因为销售明细和经营分析需要计算毛利。如果只有售价，后面无法计算利润。

为什么保存最低库存？因为库存预警需要对比当前库存和最低库存。

为什么商品编码和条码设为唯一？因为收银、导入和库存查询都需要稳定识别商品，不能出现两个商品使用同一个编码。

### 4. 库存与库存流水

核心表：

| 表 | 模型文件 | 作用 |
| --- | --- | --- |
| `inventory` | `app/models/inventory.py` | 保存每个商品当前库存 |
| `inventory_logs` | `app/models/inventory_log.py` | 保存每次库存变化的原因和前后数量 |

`inventory` 采用商品 ID 作为主键，和商品表形成一对一关系。也就是说，每个商品对应一条当前库存记录。

`inventory_logs` 记录库存变化过程，字段包括：

| 字段 | 含义 |
| --- | --- |
| `change_type` | 变化类型，例如入库、出库、调整、销售、退货、创建、导入 |
| `quantity_change` | 本次数量变化 |
| `quantity_before` | 变化前数量 |
| `quantity_after` | 变化后数量 |
| `reason` | 变化原因 |
| `operator_id` | 操作人 |
| `created_at` | 变化时间 |

答辩时一定要强调：

> 库存不能只看当前数量，还要能追踪为什么变化。因此我设计了库存流水表，每次收银扣库存、商品创建、商品导入或人工调整库存时，都留下前后数量和原因。

### 5. 销售订单与销售明细

核心表：

| 表 | 模型文件 | 作用 |
| --- | --- | --- |
| `sales` | `app/models/sale.py` | 销售订单主表 |
| `sale_items` | `app/models/sale_item.py` | 销售订单明细表 |

`sales` 表保存订单级信息，包括订单号、收银员、应收金额、优惠金额、实收金额、支付方式、订单状态和创建时间。

`sale_items` 表保存商品级明细，包括商品 ID、数量、成交单价、进价快照和小计。

这里有两个重要设计点：

1. 订单主表和明细表分离，这是典型的一对多结构。一笔订单可以包含多种商品。
2. 销售明细保存 `unit_price` 和 `purchase_price` 快照，而不是只引用商品表当前价格。因为商品价格以后可能改变，但历史订单必须保留当时成交价格和当时成本。

这句话很适合答辩：

> 销售明细保存价格快照，是为了保证历史订单不受商品后续改价影响，也让毛利分析有可靠依据。

### 6. 财务流水、对账、应付和月结

核心表：

| 表 | 模型文件 | 作用 |
| --- | --- | --- |
| `finance_transactions` | `app/models/finance_transaction.py` | 收入、支出等财务流水 |
| `cash_reconciliations` | `app/models/cash_reconciliation.py` | 按日期和支付方式保存日结对账结果 |
| `supplier_payables` | `app/models/supplier_payable.py` | 供应商应付款 |
| `payable_payments` | `app/models/payable_payment.py` | 应付款付款记录 |
| `finance_period_closings` | `app/models/finance_period_close.py` | 月结快照 |

财务模块的设计重点是“经营结果留痕”。

`finance_transactions` 可以登记其他收入和支出。`cash_reconciliations` 根据某天的销售金额计算系统应收，再由管理员录入实收金额，系统保存差异。`supplier_payables` 记录应付账款，`payable_payments` 记录付款过程。`finance_period_closings` 保存某个月的销售额、其他收入、费用、毛利、净利润、现金流入和现金流出。

答辩时可以说：

> 财务部分不是只显示销售额，而是把销售收入、其他收支、日结差异、供应商应付和月结快照拆成不同表，这样既能查询明细，也能形成阶段性财务结果。

### 7. 会员、员工、供应商、系统参数

核心表：

| 表 | 模型文件 | 作用 |
| --- | --- | --- |
| `members` | `app/models/member.py` | 会员编号、姓名、手机号、等级、积分、状态 |
| `employees` | `app/models/employee.py` | 员工编号、姓名、岗位、电话、排班、状态 |
| `suppliers` | `app/models/supplier.py` | 供应商编码、名称、联系人、电话、结算周期、状态 |
| `system_settings` | `app/models/system_setting.py` | 系统参数键值对 |

这些是二期课程设计补充模块。它们共同构成门店运营的基础资料。

系统参数采用键值对设计，比如门店名称、库存预警开关、小票页脚文案。这种设计的好处是：不需要为每个小配置单独建表，后续增加配置项比较方便。

## 七、实体关系怎么讲

你可以按下面这张关系表解释：

| 关系 | 说明 |
| --- | --- |
| `categories` 1 对多 `products` | 一个分类下有多个商品 |
| `products` 1 对 1 `inventory` | 一个商品对应一条当前库存 |
| `products` 1 对多 `inventory_logs` | 一个商品可能发生多次库存变化 |
| `users` 1 对多 `sales` | 一个收银员可以产生多笔销售订单 |
| `sales` 1 对多 `sale_items` | 一笔订单包含多条商品明细 |
| `products` 1 对多 `sale_items` | 一个商品可以出现在多笔订单明细中 |
| `announcements` 1 对多 `announcement_reads` | 一条公告对应多个用户已读记录 |
| `users` 1 对多 `announcement_reads` | 一个用户可以阅读多条公告 |
| `supplier_payables` 1 对多 `payable_payments` | 一笔应付款可以分多次付款 |

讲实体关系时不要只念表名，要讲业务含义：

> 商品是库存和销售的基础。销售订单记录一次交易，销售明细记录交易中的商品。库存表保存当前结果，库存流水保存变化过程。财务表再从销售和付款中汇总经营结果。

服务层在 `app/services/` 中，是后端最能体现业务规则的地方。

| 服务文件 | 负责内容 |
| --- | --- |
| `auth.py` | 注册、登录、管理员申请审核 |

| `inventory.py` | 库存数量设置、库存摘要、库存列表、流水查询、预警 |
| `cashier.py` | 收银台商品搜索、购物车规范化、结算和订单生成 |
| `sales.py` | 销售订单列表和订单详情 |
| `finance.py` | 财务概览、收支流水、对账、应付、付款、月结 |
| `analytics.py` | 首页概览、销售概览、趋势、排行、分类占比 |
| `announcements.py` | 公告发布、公告列表、未读数量、标记已读 |
| `assistant.py` | 智能助手回复，支持库存、销售、商品和帮助类问答 |
| `second_phase.py` | 会员、员工、供应商、系统参数 CRUD |

为什么需要服务层？因为路由层应该尽量薄。路由层负责拿参数、判断权限、返回 JSON；真正复杂的校验、计算、事务和数据库操作放到服务层。

答辩时可以讲：

> 如果把所有逻辑写在路由函数里，代码很快会变得很乱。服务层把业务规则集中起来，测试也可以直接调用服务函数验证核心逻辑，不必依赖浏览器。

### 智能助手模块怎么讲

智能助手模块要从“前端交互”和“后端能力”两面讲，但如果我是数据建模负责人或后端负责人，重点应该放在后端。

前端部分主要负责聊天体验。页面文件是 `app/templates/assistant.html`，交互脚本是 `app/static/js/assistant.js`。用户在输入框里输入问题后，前端 JavaScript 会把问题封装成 JSON，通过 `fetch('/api/assistant/chat')` 发送给后端。后端返回回答后，前端再把用户消息和助手回复追加到聊天窗口里，并显示加载状态、字数限制、清空聊天和推荐问题。

后端部分由 `app/routes/assistant.py` 和 `app/services/assistant.py` 共同完成。路由层提供两个入口：

| 路由 | 作用 |
| --- | --- |
| `/assistant` | 返回智能助手页面 |
| `/api/assistant/chat` | 接收前端问题，返回 JSON 格式回答 |

`/api/assistant/chat` 使用 `@admin_required` 控制权限，说明当前设计中 AI 助手是管理员辅助工具，不直接开放给收银员。接口收到请求后，通过 `request.get_json(silent=True)` 解析 JSON，请求字段主要是 `message`。路由层不直接写复杂问答逻辑，而是调用服务层的 `generate_assistant_reply(message)`。

服务层的处理顺序可以这样讲：

1. 先清理用户输入，拒绝空问题。
2. 限制问题长度，超过 500 字符直接返回提示。
3. 优先匹配 FAQ 预设问题，例如“如何添加新商品”“怎样更新库存数量”。
4. 如果配置了 `LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL` 等参数，就尝试调用兼容 OpenAI 格式的大模型接口。
5. 如果没有配置大模型，或者外部调用失败，就降级到本地规则回复。
6. 本地规则会识别库存、销售、商品、帮助四类问题。
7. 库存类问题会调用库存摘要、库存预警和商品库存查询。
8. 销售类问题会调用销售概览和热销商品排行。
9. 商品类问题会返回商品新增、导入、上下架和分类管理说明。
10. 最后统一返回 `success`、`answer`、`suggestions` 结构，前端按这个结构渲染。

这里要强调一个后端设计点：AI 助手不是简单把用户问题原样转发给大模型，而是做了“业务优先、模型可选、失败可降级”的设计。能用本地业务数据回答的问题，例如库存预警、今日销售、商品导入步骤，就优先结合系统已有服务返回；只有配置了大模型接口时，才尝试调用外部 LLM。这样即使答辩现场没有网络、没有 API Key，助手模块也不会完全失效。

答辩时可以这样说：

> 智能助手是前后端协同模块。前端负责聊天窗口、输入框、发送按钮、加载状态和回答展示；后端负责 `/api/assistant/chat` 接口、权限校验、问题解析、FAQ 匹配、业务数据查询、大模型调用和降级回复。它不是脱离业务的聊天框，而是能围绕库存、销售、商品和帮助说明回答问题。为了保证演示稳定性，后端设计了本地规则降级逻辑，即使没有外部模型接口，也能返回可用答案。

## 十、核心业务流程：收银结算

收银结算是最重要的后端流程，对应服务函数 `checkout_cashier_order()`。

它的流程是：

1. 检查支付方式是否合法，支付方式只能是 `cash`、`wechat`、`alipay`、`card`。
2. 调用 `_normalize_cart_items()` 规范购物车，把重复商品合并，过滤非法数量。
3. 查询商品和库存，构造商品映射。
4. 检查商品是否存在。
5. 检查商品是否上架。
6. 检查库存是否足够。
7. 计算每个商品的小计。
8. 汇总应收金额。
9. 校验优惠金额不能小于 0，不能大于应收金额。
10. 计算实收金额。
11. 生成订单号。
12. 写入 `sales` 销售订单。
13. 写入 `sale_items` 销售明细。
14. 调用 `set_inventory_quantity()` 扣减库存。
15. 库存服务写入 `inventory_logs` 库存流水。
16. 提交数据库事务。
17. 返回订单信息给前端。

如果任何一步发生异常，会执行 `db.session.rollback()`，避免订单写了一半、库存又没扣或者库存扣了但订单没生成。

这段答辩要重点讲事务：

> 收银结算涉及多张表，必须作为一个整体处理。订单主表、订单明细、库存数量和库存流水要么全部成功，要么失败回滚。否则会造成账实不一致。

## 十一、库存服务怎么讲

库存服务的核心函数是 `set_inventory_quantity()`。

它不只是修改库存数量，而是同时完成三件事：

1. 查询当前库存，如果没有则创建库存记录。
2. 根据变化前后数量计算变化量。
3. 写入库存流水，包括变化类型、变化前数量、变化后数量、原因和操作人。

库存摘要、库存列表、库存流水和预警也都在 `inventory.py` 中实现。

库存列表会把商品表和库存表联查，返回商品名称、分类、当前库存、最低库存和库存状态。库存预警会筛选当前库存小于等于最低库存的商品。

你可以这样讲：

> 库存模块的重点是可追踪。只改库存数量无法回答“为什么少了”。库存流水可以回答是哪一天、哪个商品、因为什么原因、由谁操作，库存从多少变成多少。

## 十二、商品服务怎么讲

商品服务在 `products.py` 中。

主要功能包括：

1. 商品分页查询。
2. 按名称、编码、分类、状态筛选。
3. 新增商品。
4. 编辑商品。
5. 上架和下架商品。
6. 删除商品。
7. CSV 导入商品。
8. Excel 导入商品。
9. 查询商品分类。

商品创建时会校验商品编码唯一、条码唯一、售价合法，并初始化库存记录。如果通过导入创建商品，也会写库存日志，变化类型为 `import`。

这个模块的答辩重点是：

> 商品是整个系统的基础主数据。为了保证收银、库存、销售和分析可靠，商品编码和条码必须唯一，价格字段必须合法，商品创建后还要同步创建库存。

## 十三、财务服务怎么讲

财务服务在 `finance.py` 中，内容比较多，可以按四块讲：

### 1. 财务概览

`get_finance_overview()` 按周期计算销售额、其他收入、费用、毛利、净利润、现金流入和现金流出。

### 2. 收支流水

`create_finance_transaction()` 用于登记收入或支出。它会校验金额和类型，并生成财务流水编号。

### 3. 日结对账

`get_reconciliation()` 根据日期和支付方式计算系统应收。

`save_reconciliation()` 保存实际金额，并计算差异金额。

这说明系统不仅知道卖了多少钱，还可以对账，检查系统金额和实际收款是否一致。

### 4. 应付与月结

`create_payable()` 创建供应商应付款。

`record_payable_payment()` 记录付款，并根据已付金额更新状态为未付、部分付款或已付。

`close_finance_period()` 生成月结快照，把当月销售、收入、费用、毛利和净利润固化下来。

你可以这样讲：

> 财务模块把经营过程中的收入、支出、日结、应付和月结拆成多个服务函数，既能查询明细，也能形成管理层需要看的汇总结果。

## 十四、销售与分析服务怎么讲

销售服务在 `sales.py` 中，主要负责销售订单列表和订单详情。

销售订单列表支持按关键词、收银员、状态、支付方式、开始日期、结束日期筛选。订单详情会返回订单主信息和商品明细。

分析服务在 `analytics.py` 中，主要负责：

1. 首页概览。
2. 销售概览。
3. 销售趋势。
4. 热销或滞销商品排行。
5. 分类分布。

分析模块会从销售订单、销售明细、商品和分类中聚合数据。答辩时可以说：

> 分析模块本质上是对交易数据的二次加工。销售订单负责保存事实，分析服务负责把事实按时间、商品和分类汇总成经营指标。

## 十五、公告服务怎么讲

公告服务在 `announcements.py` 中。

核心逻辑包括：

1. 管理员创建公告。
2. 按目标角色筛选用户可见公告。
3. 查询某个用户的未读公告数量。
4. 标记单条公告已读。
5. 标记全部公告已读。

## 十九、错误处理与事务

后端有两类错误处理：

### 1. 业务错误

业务错误不会直接让程序崩溃，而是返回 `False` 和错误信息。例如：

1. 登录密码错误。
2. 商品编码重复。
3. 条码重复。
4. 商品已下架。
5. 库存不足。
6. 支付方式不支持。
7. 优惠金额大于应收金额。
8. 会员编号重复。
9. 会员积分不足。
10. 供应商结算周期无效。

### 2. 系统异常

如果数据库写入过程中出现异常，服务层会调用 `db.session.rollback()` 回滚事务。

例如收银结算中，如果销售订单已经创建但写销售明细或扣库存失败，就必须回滚，否则会产生半成品数据。

答辩时可以用这句话：

> 后端不只是接收请求，还要守住数据一致性。涉及多表写入的操作都会在异常时回滚，避免订单、库存和流水不一致。

## 二十四、正式演讲稿

各位老师好，我在本项目中主要负责数据建模和后端实现。我的工作重点是把超市门店的实际经营流程，抽象成数据库模型，并通过后端服务保证数据能够在商品、库存、收银、销售、财务和分析模块之间正确流转。

从整体业务来看，这个系统不是单独的收银页面，而是一个门店经营闭环。管理员先维护商品、分类、会员、员工、供应商和系统参数等基础资料；收银员在收银台查询商品并完成结算；后端在结算时校验库存、商品状态、支付方式和优惠金额；结算成功后生成销售订单和销售明细，同时扣减库存并写入库存流水；后续销售数据进入销售查询、财务对账和经营分析模块。也就是说，系统的数据流是从基础资料到交易，再到库存、财务和分析的完整链条。

本项目整体采用 Python + Flask + SQLAlchemy + SQLite 的后端技术栈，前端采用 Jinja2 模板、Tailwind CSS、原生 JavaScript、Fetch API 和 Chart.js。应用入口是 `run.py`，应用工厂在 `app/__init__.py` 中。系统启动时会加载配置、初始化日志、初始化数据库、导入 ORM 模型、创建数据表、初始化默认用户和分类，并在商品表为空时导入 `seed_data.sql` 演示数据。商品批量导入部分使用 Python `csv` 标准库和 openpyxl，自动化测试使用 pytest、coverage 和内存 SQLite。默认数据库文件是 `data/supermarket.db`，默认管理员账号是 `admin/admin123`，默认收银员账号是 `cashier01/123456`。这样项目拉取后可以比较快地运行和演示。

在代码结构上，我把后端分成路由层、服务层和模型层。路由层位于 `app/routes/`，负责接收页面请求和 API 请求，并通过登录和角色装饰器控制权限。服务层位于 `app/services/`，负责处理业务规则，例如商品导入、库存调整、收银结算、财务对账、公告已读和二期主数据维护。模型层位于 `app/models/`，负责定义用户、商品、库存、销售、财务、会员、员工、供应商等实体。

在数据建模方面，系统一共围绕 19 张核心表展开，可以分为六组。第一组是账号与权限，包括 `users` 和 `admin_signup_requests`，用于登录、角色和管理员审核。第二组是公告与消息，包括 `announcements` 和 `announcement_reads`，用于公告发布和已读状态记录。第三组是商品与库存，包括 `categories`、`products`、`inventory` 和 `inventory_logs`，用于管理商品资料、当前库存和库存变化过程。第四组是销售交易，包括 `sales` 和 `sale_items`，用于保存销售订单和商品明细。第五组是财务与对账，包括财务流水、现金对账、供应商应付、付款记录和月结快照。第六组是二期主数据，包括会员、员工、供应商和系统参数。

我在建模时特别关注数据可追踪性。比如库存模块没有只设计一个库存数量字段，而是把当前库存放在 `inventory` 表，把每次变化放在 `inventory_logs` 表。每条库存流水都会记录变化类型、变化前数量、变化后数量、变化原因、操作人和时间。这样当库存减少时，系统可以追踪是销售出库、人工调整、导入、退货还是其他原因。

销售模块采用订单主表和订单明细表的结构。`sales` 表保存订单号、收银员、应收金额、优惠金额、实收金额、支付方式和状态；`sale_items` 表保存每个商品的数量、成交单价、进价快照和小计。这里保存价格快照很重要，因为商品价格以后可能会修改，但历史订单必须保留当时的成交价格和成本，这样毛利分析才可靠。

收银结算是后端最关键的业务流程。服务函数会先校验支付方式，再规范购物车数据，把重复商品合并，然后查询商品和库存。系统会逐项检查商品是否存在、是否上架、库存是否足够，再计算订单金额、优惠金额和实收金额。校验通过后，系统生成销售订单和销售明细，同时调用库存服务扣减库存并写入库存流水。这个过程涉及多张表，所以如果中间出现异常，会执行事务回滚，避免订单、库存和流水不一致。

财务模块则把经营结果进一步沉淀。系统支持财务概览、收支流水、日结对账、供应商应付、付款记录和月结快照。日结对账会根据当天不同支付方式的销售金额计算系统应收，再和管理员录入的实际金额对比，保存差异。月结快照则把一个月的销售额、其他收入、费用、毛利、净利润、现金流入和现金流出固化下来，方便后续查看。

系统还设计了智能助手模块。前端提供聊天窗口和异步发送交互，后端提供 `/api/assistant/chat` 接口。这个接口先做管理员权限校验，再解析用户问题，交给 `assistant.py` 服务层处理。服务层会先匹配 FAQ，再根据库存、销售、商品、帮助等关键词调用系统已有业务服务生成回答；如果配置了大模型 API，也可以调用兼容 OpenAI 格式的外部模型。为了保证现场演示稳定，外部模型不可用时会自动降级到本地规则回复。

二期课程设计中，我补充了会员、员工、供应商和系统参数模块。会员表保存会员编号、姓名、手机号、等级、积分和状态；员工表保存员工编号、岗位和排班；供应商表保存供应商编码、联系人和结算周期；系统参数表采用键值对结构，保存门店名称、库存预警开关和小票页脚等配置。后端服务层对这些模块做了统一的搜索、分页、启停、唯一性校验和异常处理。

最后，在测试方面，项目使用 pytest 编写自动化测试。测试使用内存 SQLite 数据库，不会污染真实演示数据库。测试覆盖登录、管理员审核、权限拦截、商品创建、库存调整、收银结算、销售详情、财务对账、公告已读、二期 API CRUD 和异常路径。比如测试会验证库存不足时结算失败，结算成功后库存会扣减，库存调整会写入流水，会员积分不能扣成负数。通过这些测试，可以证明后端核心逻辑是可运行、可验证的。

总体来说，我的工作是把业务需求转化成稳定的数据模型和后端服务。这个系统的数据设计不是孤立表结构，而是围绕超市经营流程，把商品、库存、销售、财务、公告和主数据串成一个完整闭环，并通过权限控制、事务回滚、日志记录和自动化测试保证系统可靠性。

我负责本项目的数据建模和后端实现。系统后端采用 Python、Flask、SQLAlchemy 和 SQLite，前端采用 Jinja2、Tailwind CSS、原生 JavaScript、Fetch API 和 Chart.js，按路由层、服务层、模型层组织代码。数据模型围绕超市经营闭环设计，包括用户权限、公告、商品库存、销售订单、财务对账、会员、员工、供应商和系统参数等 19 张核心表。重点设计包括库存当前表和库存流水表分离、销售订单主表和明细表分离、销售明细保存价格快照、财务模块拆分为流水、对账、应付、付款和月结。收银结算时后端会校验商品状态、库存、支付方式和优惠金额，成功后同时生成订单、明细、扣减库存并写库存流水，异常时回滚事务。智能助手模块通过 `/api/assistant/chat` 接收问题，支持 FAQ、库存、销售、商品和帮助类问答，并预留大模型调用与本地规则降级。项目还用 pytest、coverage 和内存 SQLite 覆盖登录权限、商品库存、收银结算、财务对账、公告、智能助手和二期主数据，证明后端逻辑可运行、可验证。

## 二十六、老师可能追问的问题

### 问题 1：为什么销售订单要分成 `sales` 和 `sale_items`？

因为一笔订单可能包含多个商品。`sales` 保存订单级信息，例如订单号、收银员、总金额、支付方式和时间；`sale_items` 保存商品级明细，例如商品、数量、单价和小计。这是一对多关系，结构更符合真实交易。

### 问题 2：为什么销售明细要保存进价和售价快照？

因为商品价格可能后续变化。如果历史订单只引用商品表当前价格，就会导致历史销售金额和毛利不准确。保存快照可以保证历史订单稳定。

### 问题 3：库存为什么要有流水表？

当前库存只能说明“现在有多少”，不能解释“为什么变成这样”。库存流水记录变化前数量、变化后数量、变化类型、原因和操作人，可以追踪销售、入库、盘点、导入和退货等过程。

### 问题 4：收银结算如何保证数据一致？

结算时会同时写销售订单、销售明细、库存数量和库存流水。整个过程在同一个数据库事务中执行。如果中间失败，会 rollback，避免出现订单成功但库存没扣，或者库存扣了但订单没生成的问题。

### 问题 5：权限是前端控制还是后端控制？

前端会根据角色隐藏菜单，这是体验层面的控制。真正的权限控制在后端路由装饰器中，未登录返回 401，角色不符合返回 403。

### 问题 6：二期模块只是简单 CRUD 吗？

不是。二期模块除了新增、查询、编辑、启停，还做了唯一性校验、枚举值校验和业务规则校验。例如会员积分不能为负，会员编号不能重复，供应商结算周期只能是指定值。

### 问题 7：测试怎么证明后端可靠？

测试覆盖核心正常流程和异常路径。比如商品创建后检查库存是否生成，库存调整后检查流水是否存在，库存不足时结算失败，结算成功后检查库存扣减和订单详情，对账保存后检查差异金额，公告已读后检查未读数量变化。

### 问题 8：为什么使用 SQLite？

课程设计和本地演示场景中，SQLite 部署简单，不需要额外数据库服务，便于提交和复现。后端使用 SQLAlchemy ORM，如果未来需要迁移到 MySQL 或 PostgreSQL，模型层和服务层的主要业务逻辑可以继续复用。

### 问题 9：系统参数为什么用键值对？

系统参数通常数量不大，但变化灵活。键值对可以保存门店名称、库存预警开关、小票页脚等配置，后续新增参数不需要频繁改表结构。

### 问题 10：你这部分最大的贡献是什么？

我的主要贡献是把业务流程落成数据模型和后端服务，保证数据能从商品、库存、收银、销售、财务到分析完整流转，并且通过权限控制、库存流水、价格快照、事务回滚和自动化测试保证数据可靠。
