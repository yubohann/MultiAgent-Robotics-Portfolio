# ROBOCON 2025 机器人篮球自主系统

## 基于 Livox MID-360、FAST-LIO2、RGB-D/YOLO 与 ROS 2 的双车竞赛系统

> 本文是一份面向科研交流、技术面试和项目答辩的完整技术说明。它回答的不只是“用了哪些工具”，还回答四个更重要的问题：为什么这样设计、每个模块解决了什么真实问题、模块之间如何形成闭环、以及如何把算法变成一套能在竞赛机器人上稳定执行的系统。

---

## 1. 项目定位

### 1.1 一句话概括

这是一个面向 ABU ROBOCON 2025 机器人篮球任务的双车自主系统：机器人利用 Livox MID-360 与内置 IMU 完成 LiDAR--惯性定位，利用 RGB-D/YOLO 识别篮筐并估计目标距离，通过 ROS 2 组织感知、位姿、任务和通信，再把投篮、传球和底盘动作交给 STM32 执行层完成实时控制。

它不是把若干算法简单拼在一起，而是先把比赛要求翻译成机器人能检查、能执行的条件，再把各模块接成一条完整工作链：

```text
比赛规则与战术目标
        -> 任务状态与动作前置条件
        -> LiDAR/IMU 位姿与地图坐标
        -> RGB-D/YOLO 目标观测
        -> 距离、航向和投篮参数计算
        -> 双车通信与动作确认
        -> STM32/CAN 实时执行
        -> 反馈、计时、恢复和下一任务
```

### 1.2 项目中真正解决的问题

ROBOCON 机器人篮球不是一个单纯的目标检测问题，也不是一个只要机器人能够移动就算完成的导航问题。比赛要求机器人在有限时间内完成运球、推进、传球、接球、瞄准和投篮等连续动作。每个动作都受到场地几何、球权、队友位置、机构状态和裁判规则的共同约束。

因此，项目的核心问题可以表述为：

> 在快速运动、底盘振动、目标遮挡和双车异步的条件下，如何让机器人持续获得可信的位姿和目标观测，并把这些观测转换成满足规则、可被执行器确认的动作？

这个问题有三个层次：

1. **估计层**：机器人当前在哪里，运动是否连续，地图坐标是否可靠；
2. **决策层**：此刻是否具备传球、接球或投篮条件，下一步应该由哪辆车承担；
3. **执行层**：命令是否真正到达底盘和机构，执行结果是否被反馈，出现异常后如何停止或恢复。

### 1.3 用人话解释“按比赛要求设计”

这里说的“按比赛要求设计”，不是做一个抽象的规则软件，也不是把规则全文搬进代码。简单说，就是先问清楚比赛到底要求机器人完成什么，再把这些要求变成真实的计时器、距离检查、位置判断、动作反馈和急停条件：

- 规则要求推进要在规定时间内完成，系统就给推进任务单独计时；
- 规则要求传球双方至少相距 1 m，系统就用两车实时位置检查距离；
- 规则要求球权和动作合法，系统就不把“发出指令”当成“传球完成”，而是等待接球反馈；
- 规则要求投篮在合适区域进行，系统就把地图位姿、篮筐目标和比赛阶段一起交给总控判断；
- 规则允许裁判停止比赛，系统就保留暂停、取消、恢复和急停路径。

所以，这个项目的主线不是“规则引擎”，而是：**我把纸面上的比赛要求，变成了传感器能观测、程序能判断、机构能执行、异常能停下来的机器人动作。**

### 1.4 我的角色

我在团队中负责 LiDAR 与感知方向，并承担定位、导航接口、双车通信和嵌入式控制边界的系统联调。我的工作不是只在电脑上调用一个开源算法，而是直接参与传感器安装、时间与外参标定、ROS 2 节点启动、地图建立、视觉调参、数学解算、无线和串口通信、STM32 接口、底盘与投篮机构联调，再把这些链路放到真实竞赛机器人上反复验证。

具体来说，我需要同时处理四种不同性质的问题：

1. **传感器问题**：点云是否到达、时间是否连续、IMU 轴向和外参是否正确；
2. **算法问题**：FAST-LIO2 是否正常跟踪、地图坐标是否稳定、视觉深度是否可信；
3. **软件系统问题**：ROS 2 topic、QoS、TF、节点启动顺序和参数是否一致；
4. **机械与电控问题**：串口数据是否正确、STM32 是否执行、CAN 电机是否响应、机构是否到位。

这些问题经常同时出现。我的工作方式是把现象拆成可测量的信号，再逐层隔离：先确认传感器输入，再确认估计输出，再确认命令内容，最后对照电机和机构反馈。这样，系统联调不是“反复试试看”，而是一个可以复盘和复现的工程过程。

团队在第 24 届中国大学生机器人大赛 ROBOCON 机器人篮球项目中获得全国二等奖，在机器人篮球投篮专项赛中获得全国二等奖。我的工作直接服务于参赛机器人从实验室调试到赛场运行的迁移。

## 2. ROBOCON 2025 规则背景

### 2.1 规则不是附录，而是系统设计的起点

本项目使用 ABU ROBOCON 2025《Robot Basketball》规则作为任务和状态机的约束来源。工程实现中将规则转换为可检查的时间、距离、空间位置和动作证据，而不是只在比赛前阅读规则。

项目仓库保存了规则版本、来源 URL 和文件哈希，便于把场地模型、仿真配置和总控逻辑绑定到同一版规则：

| 项目 | 规则约束 | 对系统的直接影响 |
| --- | ---: | --- |
| 比赛场地 | 15.0 m x 8.0 m | 地图坐标、导航边界、初始位姿和场地模型必须统一 |
| 场地围栏 | 高 0.10 m、宽 0.05 m | 点云地图和底盘规划要保留边界几何 |
| 篮板 | 1.80 m x 1.05 m | 视觉目标模型不仅是一个二维框，还包含目标结构 |
| 篮筐高度 | 2.43 m | 投篮弹道模型的目标高度 |
| 篮筐内径 | 0.450--0.459 m | 投篮容差、目标中心估计和机构调参的几何依据 |
| 预赛时长 | 120 s | 总控必须有明确的比赛时钟和结束状态 |
| 淘汰赛时长 | 160 s | 赛制 profile 需要与预赛 profile 分开 |
| 单次球权 | 20 s | 持球状态、传球和投篮动作需要受球权计时约束 |
| 推进时限 | 8 s | 从防守侧进入进攻侧的任务需要单独计时 |
| 最小传球距离 | 1.0 m | 双车位置同步和传球前空间检查的阈值 |
| 运球手高度 | 不低于 0.70 m | 运球动作需要机构反馈或视觉证据，而不能只看命令 |
| 普通得分 | 2 分、3 分 | 投篮区域与投篮动作需要进入比赛状态 |
| 灌篮得分 | 7 分 | 灌篮需要额外的空间、跳跃和释放证据 |

规则文件还指出，三分线的数值几何需要独立的场地实现。因此，系统把“规则中明确的数值约束”和“需要通过场地标定确认的几何约束”分开配置。这样，未被规则文字精确给出的边界不会被一个未经验证的常数悄悄替代。

### 2.2 规则如何进入程序

规则约束被组织为四类：

1. **比赛时钟**：比赛开始、球权开始、推进截止、比赛结束；
2. **空间约束**：机器人是否位于进攻侧、两车距离是否满足传球要求、投篮区域如何判定；
3. **动作证据**：传球已经执行、接球已经确认、运球高度合格、投篮已经释放；
4. **得分与结束**：合法投篮、得分类型、裁判停止、比赛完成。

代码中的 `ABURobocon2025RuleEngine` 不根据“已经发送命令”推断动作完成，而是要求外部适配器提供对应的物理证据。例如：

- 发送传球指令不等于传球成功；必须有接收车确认；
- 识别到篮筐不等于可以投篮；还要有位姿、球、机构和队友安全状态；
- 投篮动作被触发不等于得分；得分由球进入篮筐等比赛证据决定。

这种设计体现了一个重要的工程原则：**决策系统判断“是否允许执行”，执行系统反馈“是否已经完成”，比赛规则检查逻辑判断“是否符合比赛定义”。**

### 2.3 规则对真实机器人设计的影响

规则中的数字会直接改变机器人的动作节奏和硬件取舍，而不是只影响最后的计分：

- 8 s 推进时限意味着推进路线要在比赛开始前规划好，现场不能依赖长时间的临时搜索；
- 20 s 球权限制要求传球、接球和投篮之间有明确的任务边界，任何一个环节卡住都必须及时取消或换方案；
- 1 m 最小传球距离要求两车共享位置，单车只看自己的里程计无法判断传球是否合法；
- 2.43 m 篮筐高度和不同得分区域要求投篮参数随距离、航向和比赛位置变化；
- 0.450--0.459 m 的篮筐内径使目标中心、深度测量和机构重复性成为同一个问题；
- 预赛与淘汰赛的比赛时长不同，启动配置、比赛计时和策略 profile 必须明确区分。

因此，我在设计时先把规则翻译成“机器人必须在什么时间、什么位置、收到什么反馈后才能做什么”，再反推定位、视觉、通信和机构需要提供哪些接口。这种倒推过程让软件和硬件的调试目标一致：定位模块不只是输出坐标，还要告诉总控坐标能否用于动作；通信模块不只是发消息，还要告诉任务是否已经被队友接收；机构模块不只是转动电机，还要返回动作是否到位。

## 3. 设计理念

### 3.1 分层，但保持闭环

系统采用分层结构，但每层都通过明确接口反馈状态：

```text
传感器层       MID-360、内置 IMU、RGB-D 相机、机构传感器
估计层         FAST-LIO2、局部里程计、固定地图定位
感知层         YOLO 目标检测、深度测距、稳定性和新鲜度判断
任务层         传球/接球/投篮状态、比赛时钟、角色分工
执行层         ROS 2 高层命令、UART/ESP-NOW、STM32、CAN、电机与机构
安全层         位姿有效性、队友安全、超时、取消、急停和恢复
```

分层不是为了增加软件层数，而是为了让故障具有清晰的传播路径。定位过期时，系统应阻止依赖全局坐标的动作；目标观测过期时，应阻止投篮；STM32 未返回执行确认时，应阻止进入下一个任务。

### 3.2 几何定位与语义感知分工

LiDAR--IMU 负责回答“机器人在场地坐标系中如何运动”，RGB-D/YOLO 负责回答“篮筐在哪里、距离多远、观测是否稳定”。两者的职责不同：

- LiDAR 几何约束对纹理和光照不敏感，适合连续位姿估计；
- RGB-D 目标观测直接连接目标类别和距离，适合确认篮筐与投篮条件；
- 任务层不直接读取原始传感器，而是读取带质量信息的位姿和目标接口。

这种分工让系统能同时利用几何信息和语义信息，而不会把检测框坐标误当作全局位姿，也不会要求 LiDAR 单独完成目标类别识别。

### 3.3 高层决策与实时执行分离

NUC/ROS 2 侧负责地图、感知融合、任务逻辑和双车协作；STM32 侧负责电机 PID、限位、过流、超时、机构时序和急停。高层发送的是“到目标位姿”“准备传球”“执行投篮”等可解释动作，底层将其转换为实时电流、速度和机构控制。

这样做的原因是计算负载和实时性要求不同：

- LIO、视觉和任务规划需要更大的内存、文件系统和消息编排能力；
- 电机控制和安全保护需要确定性的周期、较短的执行路径和硬件级故障响应。

高层不会取代底层保护，底层也不会承担地图和语义任务。两者之间通过带版本、序列号和反馈状态的命令边界连接。

### 3.4 所有动作都必须有状态和反馈

比赛机器人最危险的系统错误之一，是把“函数返回”或“消息发布”当作动作完成。项目中的关键动作都遵循：

```text
请求 -> 条件检查 -> 命令发送 -> ACK/反馈 -> 状态迁移 -> 超时或取消
```

例如投篮：

```text
目标有效
  + 位姿有效
  + 地图已锁定
  + 球存在
  + 机构健康
  + 队友安全
        -> PrepareShot
        -> FireShot
        -> 机构反馈
        -> shot_executed / recovery / fault
```

### 3.5 仿真、接口、真机逐级迁移

系统先在可控环境中验证数据格式、坐标变换、状态机和规则逻辑，再进入台架和真实机器人联调。仿真的价值不是替代比赛，而是把接口级错误和状态迁移错误提前暴露出来；真机验证则关注振动、遮挡、无线干扰、机构延迟和人员安全等真实因素。

## 4. 总体系统架构

### 4.1 硬件组成

| 子系统 | 主要器件/接口 | 作用 |
| --- | --- | --- |
| 三维感知 | Livox MID-360 | 场地几何、障碍和连续点云观测 |
| 惯性测量 | MID-360 内置 IMU | 高频角速度、加速度和运动传播 |
| 视觉感知 | RGB-D 相机 | 篮筐检测、深度测距和目标确认 |
| 高层计算 | Linux 计算机、ROS 2 | LIO、地图、视觉、任务和通信编排 |
| 双车通信 | ESP-NOW、ROS 2 消息 | 位置同步、角色协作、动作确认 |
| 有线控制 | UART | 高层参数和动作指令下发 |
| 实时控制 | STM32 | 底盘、运球、收球、送球、投篮机构控制 |
| 电机总线 | CAN | 电机反馈、电流控制和执行器状态 |

### 4.2 软件数据流

```text
MID-360 CustomMsg + internal IMU
             |
             v
     input validation / timestamp checks
             |
             v
          FAST-LIO2
             |
             +--> local odometry -------------------+
             |                                      |
             v                                      v
     fixed-map localization                  pose quality/status
             |                                      |
             +--> map-frame pose ------------------+
                                                    |
RGB-D frames -> YOLO -> depth -> target gate ------+
                                                    |
                       pose + target + rule state  |
                                                    v
                       game supervisor / task logic
                         |          |          |
                         |          |          +--> safety / cancel / recovery
                         |          v
                         |      dual-robot protocol
                         v
                    pose and shot command bridge
                         |
                    UART / ESP-NOW
                         |
                         v
                     STM32 execution
                         |
                    CAN / motor feedback
                         |
                         +----------> supervisor state update
```

### 4.3 坐标变换所有权

对外使用的 TF 链为：

```text
map -> odom -> base_link -> imu_link -> lidar_mid360
```

其中：

- `map -> odom` 表示固定地图与局部里程计之间的全局锚定关系；
- `odom -> base_link` 由位姿适配器统一发布，保证来源唯一；
- `base_link -> imu_link` 和 `imu_link -> lidar_mid360` 由传感器安装外参确定；
- FAST-LIO2 内部使用的私有 frame 不直接暴露给比赛逻辑。

唯一发布者原则避免多个节点同时发布同一变换造成跳变。所有姿态都通过完整四元数转换平面航向角，不从四元数某一个分量直接读取 yaw。

## 5. 把系统真正装到车上：我的工程实践主线

前面的架构图描述“系统应该怎样工作”，这一章描述“我实际怎样把它做出来”。真实机器人项目的难点通常不在某一个 API，而在于不同专业的接口不匹配：传感器以一种时间格式发数据，估计器期待另一种坐标约定，视觉输出的是像素和深度，电控需要的是串口字节和 CAN 指令，机械结构又有自己的限位和响应时间。我的工作就是把这些差异一个个消化掉。

### 5.1 传感器安装、接线和初始检查

我首先把 MID-360、内置 IMU、RGB-D 相机和计算机放到真实机器人上，检查供电、网口、USB、固定支架和线缆走向。传感器安装不是“能看到数据”就结束，还要确认：

- 雷达和相机不会被投篮机构、球或车体遮挡；
- 支架在急加速和急停时不会产生相对位移；
- 传感器坐标轴方向和机器人 `base_link` 定义一致；
- 网线、串口线和电机动力线分开布置，减少现场干扰；
- 设备上电顺序、节点启动顺序和急停状态明确。

完成机械安装后，我会先做最小输入检查：启动官方驱动，查看 LiDAR 消息是否持续到达；查看内置 IMU 的角速度和加速度是否有合理变化；检查时间戳、消息频率和点数；再用 ROS 2 工具确认 topic 类型、QoS 和发布者数量。只有输入稳定，后面定位和视觉调试才有意义。

### 5.2 时间同步与外参标定

LiDAR、IMU、相机和机器人本体各自有坐标系和时间戳。我的处理顺序是先确定坐标关系，再处理时间关系：

```text
lidar_mid360 -> imu_link -> base_link -> odom -> map
camera_optical -> camera_link -> base_link
```

我会用静态姿态和可控运动检查轴向：让机器人只向前移动、只向左移动、只原地转向，观察位姿输出是否对应；再检查相机目标方向和地图中的篮筐方向是否一致。对时间关系，则通过同时记录 LiDAR、IMU、相机和控制反馈，比较运动突变在各信号中的出现顺序，调整时间偏移并在真实动作中复核。

外参和时间偏移一旦改变，会同时影响点云去畸变、地图匹配、目标坐标和投篮方向。因此我把它们写进配置和运行记录，而不是在不同节点里分别手改一组数字。

### 5.3 ROS 2 启动与 topic/TF 排障

现场最常见的问题不是算法公式错误，而是“节点看似启动了，数据却没有真正连通”。我会按以下顺序排查：

1. `ros2 node list`：确认驱动、FAST-LIO2、地图、视觉、总控和桥接节点都在；
2. `ros2 topic list`：确认输入、位姿、目标、通信和反馈 topic 名称一致；
3. `ros2 topic info -v`：检查消息类型、QoS 和发布者/订阅者；
4. `ros2 topic hz`：检查 LiDAR、IMU、位姿和目标更新频率；
5. `tf2_tools` 或 TF 可视化：确认 `map -> odom -> base_link` 只有一个明确来源；
6. 查看时间戳和 frame：确认没有使用旧消息、错误 frame 或混用仿真时间；
7. 查看日志：将“没有数据”“数据过期”“坐标错误”和“机构未反馈”分开。

这种排障方法的价值在于，每一步都能把问题范围缩小。比如机器人不按目标移动，不能马上去改导航参数；先要确认目标消息是否到达、位姿是否有效、命令中的距离和航向是否正确，最后再看 STM32 是否执行。

### 5.4 建图、定位和真实场地复核

我使用真实场地建立地图，并把篮筐、围栏、边界和机器人初始位置放到同一坐标参考下。建图时重点观察：

- 机器人快速转弯时点云是否出现明显拉伸；
- 围栏和篮架在地图中是否保持固定形状；
- 地图坐标与场地实际尺寸是否一致；
- 机器人重新启动后，通过 initial pose 能否回到同一地图位置；
- 局部里程计连续运动和固定地图校正是否相互冲突。

地图不是一个“保存后就不会改变”的文件。现场换位置、换支架、换传感器高度或改动场地设施，都可能改变地图适用条件，所以我会同时记录地图版本、传感器安装状态和运行场地。

### 5.5 视觉、深度与投篮链路联调

视觉联调从单帧检测开始，再逐步加入深度、位姿和机构：

```text
单帧检测框
  -> 目标区域深度统计
  -> 连续帧稳定性
  -> 与机器人位姿结合
  -> 计算距离/航向
  -> 计算发射参数
  -> 发送 STM32
  -> 机构反馈
```

我会用已知距离的篮筐位置检查深度值，用机器人已知转角检查目标方向，用不同距离的静态投篮记录发射结果，再将参数回写到离线标定模型。这样，视觉问题、坐标问题和机构问题不会被混在一起。

### 5.6 双车和机构的联调方法

双车联调先不用球，从消息开始：

1. 让接收车发布自己的位置和 `receiver_ready`；
2. 让传球车检查队友位置、距离和消息年龄；
3. 发送 `pass_armed`，确认接收车只记录一次；
4. 模拟或真实触发 `pass_executed`，等待接收确认；
5. 再连接收球机构，检查球到位反馈；
6. 最后才把完整传球动作和投篮动作串起来。

出现问题时，我会分别记录无线消息、ROS 2 消息、UART 字节流、STM32 状态字和 CAN 反馈。这样可以判断是消息没有发出、消息到了但被拒绝、命令格式错误，还是机构确实没有完成。

### 5.7 现场故障的处理闭环

我采用“现象--假设--测量--修复--复测”的闭环：

| 现场现象 | 首先检查 | 常见处理方向 |
| --- | --- | --- |
| 位姿突然跳变 | 时间戳、TF 发布者、支架固定、点云去畸变 | 修正 frame/外参/时间，重新建图或恢复定位 |
| 机器人到位但不投篮 | target gate、pose age、map lock、球和机构状态 | 补齐观测或反馈，修正状态迁移条件 |
| 投篮距离变化大 | 深度稳定性、目标坐标、弹道标定、电池状态 | 重新做距离标定，检查坐标和发射参数 |
| 双车动作重复 | sequence、task_id、ACK 幂等 | 修正重复消息处理和任务生命周期 |
| 传球后流程卡住 | 接收确认、球到位、机构限位、超时 | 增加真实反馈路径，进入可恢复状态 |
| 底盘不响应 | UART、STM32 状态、CAN、电机使能和急停 | 从高层命令逐级追到电机反馈 |
| 比赛中通信变慢 | ESP-NOW 心跳、消息年龄和网络负载 | 暂停依赖队友的动作，恢复后重新握手 |

这套方法体现的是工程判断力：不把所有问题都归结为“算法不稳定”，而是用数据和接口把故障定位到具体层次，并在修复后做同一场景复测。

## 6. MID-360、内置 IMU 与 FAST-LIO2 定位链

### 6.1 为什么选择 LiDAR--IMU 融合

竞赛机器人会急加速、急转向、制动，并且底盘和投篮机构会引入高频振动。只依赖轮速计会受到打滑影响，只依赖视觉会受到遮挡、光照和纹理影响。MID-360 提供空间几何，内置 IMU 提供高频运动变化，两者融合可以在短时快速运动过程中保持连续位姿。

选择 FAST-LIO2 的工程考虑包括：

1. 它直接利用 LiDAR 点的几何信息和 IMU 传播，适合三维室内场地；
2. 它保留逐点时间语义，可以进行扫描运动畸变校正；
3. 它能提供连续局部里程计，适合接入导航和投篮参数计算；
4. 它的 ROS 生态和配置方式适合在竞赛工作空间中进行 profile 管理。

FAST-LIO2 是系统采用的基础估计器，项目的工程贡献在于将其输入、坐标、地图、质量状态和下游动作接口组织成符合比赛需求的闭环。

### 6.2 `CustomMsg` 与逐点时间

MID-360 驱动发布的 `livox_ros_driver2/msg/CustomMsg` 包含帧级 `timebase` 和点级 `offset_time`。系统保留这些字段，而不是在前端直接复制 header 时间戳生成普通点云，原因是同一帧点云并非在同一时刻采集。

对点 `i`，其采样时间可表示为：

```text
t_i = timebase + offset_time_i
```

在机器人发生角速度和线速度变化时，点云去畸变需要使用 `t_i` 对应的姿态。若把整帧点云错误地视为同时采样，墙面、篮架和围栏会出现几何拉伸，进而影响 scan-to-map 配准和地图坐标。

输入守门器检查：

- 点坐标是否为有限值；
- 点数是否达到配置下限；
- `offset_time` 是否单调或处于合法范围；
- `timebase` 是否有效；
- LiDAR 与 IMU 时间戳是否新鲜；
- 消息序列是否出现丢失或异常跳变。

### 6.3 IMU 传播与 LiDAR 几何约束

LiDAR--IMU 估计可以用状态向量表示：

```text
x = (R, p, v, b_g, b_a)
```

其中 `R` 为姿态，`p` 为位置，`v` 为速度，`b_g` 和 `b_a` 分别为陀螺仪与加速度计偏置。IMU 在高频率上完成状态传播；LiDAR 通过点到地图局部平面或邻域几何的残差修正传播误差。一个简化的点到平面残差为：

```text
r_i = n_i^T (R p_i + p - q_i)
```

`p_i` 是传感器坐标系中的点，`q_i` 是地图中的对应点，`n_i` 是局部平面法向。滤波器使用这些残差判断当前姿态与地图几何的一致性。

工程上真正关键的不是公式本身，而是公式使用的时间、frame、外参和数据顺序必须一致：

```text
驱动时间基准 -> 点级去畸变 -> IMU传播 -> scan-to-map -> 局部里程计
```

### 6.4 局部里程计与固定地图定位

项目把定位分成两个职责：

- **局部里程计**：强调连续性，用于短时运动和控制反馈；
- **固定地图定位**：强调全局一致性，用于场地坐标、篮筐位置和比赛任务。

全局位姿可写成：

```text
T_map_base = T_map_odom * T_odom_base
```

FAST-LIO2 输出连续的 `T_odom_base`；固定地图模块根据初始位姿和 scan-to-map 匹配估计 `T_map_odom`。这样，地图定位的校正不会直接破坏局部轨迹连续性。

### 6.5 定位质量状态

定位模块使用显式状态机：

```text
UNINITIALIZED -> TRACKING -> RELOCALIZING -> LOST
                       ^             |
                       +-------------+
```

- `UNINITIALIZED`：尚未建立全局锚点；
- `TRACKING`：局部位姿、地图匹配和新鲜度满足要求；
- `RELOCALIZING`：匹配质量下降，系统正在寻找新的地图对应关系；
- `LOST`：当前位姿不足以支持全局动作，需要人工初始位姿或恢复流程。

质量信息包括：

| 类别 | 诊断字段 | 用途 |
| --- | --- | --- |
| 输入 | `point_count`、`offset_span_ns`、`timebase` | 判断点云结构和时间语义 |
| 流状态 | `lidar_fresh`、`imu_fresh`、`drop_count` | 判断传感器是否持续输入 |
| 位姿 | `pose_age_sec`、`source_sequence`、`accepted_sequence` | 判断位姿能否驱动动作 |
| 地图 | `map_locked`、`anchor_source`、`anchor_age_sec` | 判断全局坐标是否可用 |
| 匹配 | `map_fitness`、`scan_points`、`scan_map_overlap` | 判断 scan-to-map 质量 |
| 退化 | `degeneracy_score`、`correction_rejected_reason` | 解释几何不足或校正被拒绝 |
| 环境 | `dynamic_point_ratio` | 识别运动物体对地图匹配的影响 |
| 资源 | 队列水位、处理耗时和保护等级 | 解释计算负载与降级行为 |

不可用的测量使用 `unknown` 或 `TBD`，避免将没有传感器来源的数字伪装成零误差。

## 7. RGB-D 与 YOLO 目标感知

### 7.1 从检测框到可执行目标

视觉链路不是“检测到篮筐就结束”，而是：

```text
RGB-D 图像
  -> YOLO 检测篮筐/篮板
  -> 从检测区域提取深度
  -> 深度平滑与异常值过滤
  -> 计算目标距离和方向
  -> 检查置信度、稳定性和时间新鲜度
  -> 发布 target_observation
```

检测框提供语义类别和像素区域，深度相机提供尺度，机器人位姿提供场地坐标中的运动参考。目标接口至少包含：

```json
{
  "confidence": 0.0,
  "distance_m": 0.0,
  "stable": true,
  "observed_at_ns": 0,
  "target_type": "basket"
}
```

### 7.2 目标有效性门控

项目中的 target gate 对目标观测做统一检查。默认 profile 使用以下工程阈值：

| 条件 | 默认值 | 设计目的 |
| --- | ---: | --- |
| 检测置信度 | `>= 0.70` | 避免低置信度框直接驱动机构 |
| 目标距离 | `1.0--10.0 m` | 排除异常深度和明显越界值 |
| 观测最大年龄 | `0.50 s` | 防止使用过期画面 |
| 稳定性 | 必须为真 | 要求连续观测或跟踪器确认 |

目标状态同时发布布尔值、JSON 状态和诊断信息。失败原因采用可读代码，例如：

- `target_observation_stale`：观测时间过旧；
- `target_confidence_below_threshold`：置信度不足；
- `target_distance_out_of_range`：深度距离不在工作范围；
- `target_observation_unstable`：检测框在时间上不稳定。

### 7.3 为什么需要新鲜度

机器人在向篮筐运动时，距离和视角会持续变化。使用一帧旧目标位置计算投篮参数，可能导致机器人在不同位置执行与当前几何不匹配的动作。因此目标观测和位姿都带有时间戳，任务层只接受处于允许年龄范围内的观测。

## 8. 位姿到投篮参数的数学接口

### 8.1 几何量计算

设机器人在地图坐标中的位置和航向为：

```text
robot = (x_r, y_r, psi_r)
```

篮筐目标中心为：

```text
target = (x_t, y_t, z_t)
```

平面距离和目标方向为：

```text
d_xy = sqrt((x_t - x_r)^2 + (y_t - y_r)^2)
psi_t = atan2(y_t - y_r, x_t - x_r)
e_psi = wrap(psi_t - psi_r)
```

这两个量分别描述“离篮筐有多远”和“机器人还需要转多少角度”。它们通过 pose command bridge 形成统一的目标命令，不让视觉模块、导航模块和 STM32 各自重复计算。

### 8.2 弹道模型

工程中使用包含重力、空气阻力和马格努斯效应的数值模型描述球的飞行过程。模型输入包括目标距离、篮筐高度差、发射角和机构状态，输出是适合当前距离的初始速度或机构设定值。

基本运动方程可以抽象为：

```text
m dv/dt = F_gravity + F_drag + F_magnus
dp/dt = v
```

其中：

- `F_gravity` 描述重力；
- `F_drag` 描述速度相关的空气阻力；
- `F_magnus` 描述球旋转带来的侧向力；
- `m` 为球质量，`p` 和 `v` 分别为位置和速度。

实际机构存在电机响应、摩擦、轮胎压缩、球体释放误差和电池电压变化，因此模型参数通过离线轨迹和实测结果进行标定。计算模块输出的是经过标定的控制参数，而不是把理想抛体公式直接发送给电机。

### 8.3 为什么采用“计算 + 标定”而不是固定速度表

固定速度表在一个距离上可能有效，但比赛中机器人位置、目标距离和电池状态都会变化。采用物理模型可以提供可解释的初值，离线标定可以吸收机构误差，在线目标观测可以更新距离。三者结合后，系统具备更清晰的调参路径：

```text
位姿/目标 -> 距离与航向 -> 物理模型 -> 标定参数 -> STM32 执行
```

## 9. 双机器人协作与通信

### 9.1 角色分工

比赛任务中，两辆机器人承担不同但相互依赖的职责：

- **运球/传球车**：获取和运送篮球，在满足推进与传球条件后将球传给队友；
- **接球/投篮车**：确认接球位置，建立稳定目标观测，完成瞄准和投篮。

角色不是写死的字符串，而是与任务阶段、位置和反馈状态绑定的行为约束。某个角色完成动作后，另一辆车只有在收到对应确认后才推进状态。

### 9.2 通信消息的最小内容

双车消息需要能回答“谁发的、针对哪项任务、何时发送、是否已经处理、当前是否仍然有效”：

| 字段 | 作用 |
| --- | --- |
| `protocol_version` | 区分消息格式和兼容版本 |
| `task_id` | 把消息绑定到一次具体传球或投篮任务 |
| `sender_id` / `receiver_id` | 明确角色和目标机器人 |
| `sequence` | 检测重复、丢失和乱序 |
| `stamp_ns` | 判断消息新鲜度 |
| `command` | 任务请求，如 receiver_ready、pass_armed |
| `ack` | 确认消息已经被接收和处理 |
| `status` | 报告执行中、完成、取消或故障 |
| `pose` / `relative_pose` | 提供协作所需的位置关系 |
| `reason` | 让失败和取消可诊断 |

### 9.3 ACK、幂等和过期

通信系统采用三个基本机制：

1. **ACK**：发送动作后等待接收方确认，避免发送方把“发出”当成“完成”；
2. **幂等**：重复收到同一 `task_id + sequence` 时不重复执行传球或投篮；
3. **过期**：超过消息年龄上限后，位置和动作许可自动失效。

在无线质量下降时，系统优先保证安全：暂停需要队友确认的动作，保持底盘和机构处于可控状态，并通过恢复流程重新建立协作上下文。

### 9.4 ESP-NOW、UART 与 ROS 2 的分工

- ROS 2 负责高层状态、任务和诊断；
- ESP-NOW 用于双车之间的轻量位置同步和协同信号；
- UART 用于计算机向 STM32 发送高层参数和动作命令；
- CAN 负责 STM32 与电机和机构控制器之间的实时总线通信。

每种通信方式都位于明确边界内，避免把 ROS 2 的高层消息直接当作电机控制周期，也避免让 MCU 承担地图和目标语义。

## 10. STM32 与执行器边界

### 10.1 高层命令的语义

上位机向 STM32 发送的是带版本和时间戳的高层命令，例如：

```json
{
  "version": 1,
  "type": "pose_target",
  "stamp_ns": 0,
  "x": 0.0,
  "y": 0.0,
  "yaw": 0.0,
  "distance": 0.0,
  "heading_error": 0.0
}
```

或者发送机构层动作：

```text
prepare_receive
prepare_pass
execute_pass
collect_ball
prepare_shot
fire_shot
abort_task
emergency_stop
```

STM32 侧根据当前机构状态、限位、过流和控制器反馈执行或拒绝命令，并返回结果。

### 10.2 为什么不能用固定延时代替反馈

不同电池电压、负载、球的姿态和机构摩擦都会改变动作完成时间。固定等待只能表达“我猜动作已经完成”，而反馈才能表达“传感器确认动作已经完成”。因此：

- 收球要看球存在或机构到位反馈；
- 传球要看发射机构完成并等待接收车确认；
- 投篮要看机构释放反馈和比赛结果；
- 超时后要进入取消或恢复，而不是继续发送下一条动作。

### 10.3 MCU 的安全职责

STM32 保留以下底层保护：

- 电机 PID 与电流限制；
- 行程限位和机构互锁；
- CAN 节点掉线处理；
- 命令超时和看门狗；
- 急停输入；
- 过流、堵转和异常温升处理。

这条边界使得上位机即使因为视觉或地图暂时失效，也不会绕过底层安全保护。

## 11. 比赛总控与有限状态机

### 11.1 系统级状态

总控状态机包含：

```text
BOOT
  -> PREFLIGHT
  -> WAIT_START
  -> ACTIVE
  -> PAUSED
  -> RECOVERY
  -> FAULT
  -> ESTOP
  -> FINISHED
```

状态含义：

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| `BOOT` | 节点和硬件启动 | 进程初始化 |
| `PREFLIGHT` | 检查传感器、TF、地图、通信和机构 | 启动预检 |
| `WAIT_START` | 等待裁判或操作员开始 | 预检通过 |
| `ACTIVE` | 允许比赛任务执行 | 比赛开始 |
| `PAUSED` | 暂停新任务，保持安全状态 | 操作员暂停或短时异常 |
| `RECOVERY` | 执行重定位、重连或动作取消 | 质量下降或动作失败 |
| `FAULT` | 需要人工处理的故障 | 不可自动恢复 |
| `ESTOP` | 急停锁定 | 急停输入或严重风险 |
| `FINISHED` | 比赛或任务结束 | 时间到、裁判结束或任务完成 |

### 11.2 双车任务状态

投篮任务的角色状态按证据推进：

```text
IDLE
  -> RECEIVER_READY
  -> PASS_ARMED
  -> PASS_EXECUTED
  -> RECEIPT_CONFIRMED
  -> PREPARING_SHOT
  -> SHOT_EXECUTED
```

任何一步都可以进入 `RECOVERY`。例如，接收车没有确认准备就绪，传球车不能进入 `PASS_ARMED`；接球反馈没有到达，投篮车不能进入 `RECEIPT_CONFIRMED`。

### 11.3 `preflight_ready` 的含义

`preflight_ready` 不是“ROS 节点都启动了”，而是以下条件同时满足：

```text
LiDAR 输入新鲜
AND IMU 输入新鲜
AND FAST-LIO2 有效
AND TF 唯一且坐标正确
AND 地图已经锁定
AND 初始位姿已经建立
AND 目标与任务接口可用
AND 双车通信正常
AND UART/CAN/机构健康
```

只有 `preflight_ready=true`，总控才允许开始比赛阶段。这样可以把大量现场问题从“比赛进行中突然发现”变成“开始前明确处理”。

## 12. 规则、观测与动作的对应关系

| 比赛动作 | 需要的观测 | 需要的规则条件 | 允许的执行动作 |
| --- | --- | --- | --- |
| 进入进攻侧 | 机器人位姿、持球状态、运球/传球反馈 | 8 s 推进时限 | 继续推进或进入恢复 |
| 准备传球 | 接收车位置、队友安全、通信新鲜度 | 传球距离至少 1 m | `PreparePass` |
| 执行传球 | 发射机构状态、两车 ACK | 接收方完全位于进攻侧 | `ExecutePass` |
| 确认接球 | 接收车球存在、机构到位 | 球权转移证据 | `CollectBall` / `receipt_confirmed` |
| 准备投篮 | 位姿、篮筐目标、距离、航向、地图锁定 | 投篮位于合法进攻侧 | `PrepareShot` |
| 执行投篮 | 目标稳定、球存在、机构健康、队友安全 | 球权和动作阶段合法 | `FireShot` |
| 灌篮 | 额外空间、跳跃和释放证据 | 灌篮规则条件 | 专用机构动作 |
| 异常中止 | 任何质量状态、超时或急停 | 安全优先 | `AbortTask` / `EmergencyStop` |

这张表体现了系统的科学化设计：每一个动作都有可观察的前置条件，每一个条件都能追溯到传感器、通信或规则来源。

## 13. 一次完整任务的时序

### 13.1 开局预检

```text
BOOT
  -> 启动 MID-360 驱动与 IMU
  -> 检查 CustomMsg 时间字段与点数
  -> 启动 FAST-LIO2
  -> 建立 local odometry
  -> 加载带版本的场地地图
  -> 设置 initial pose
  -> 验证 map -> odom -> base_link TF
  -> 检查 RGB-D/YOLO、ESP-NOW、UART、CAN 和机构反馈
  -> preflight_ready = true
```

### 13.2 传球与接球

```text
运球车：持球确认
  -> 发送 receiver_ready 请求
投篮车：检查位置与队友安全
  -> 返回 receiver_ready
运球车：检查距离 >= 1 m 与推进时限
  -> pass_armed
  -> execute_pass
投篮车：确认球到达与机构状态
  -> receipt_confirmed
```

### 13.3 瞄准与投篮

```text
RGB-D/YOLO 识别篮筐
  -> 深度测距与稳定性检查
FAST-LIO2/地图定位提供机器人位姿
  -> 计算距离与航向误差
  -> 弹道模型计算发射参数
  -> UART 下发至 STM32
  -> STM32 返回机构准备完成
  -> supervisor 检查球、地图、目标和队友安全
  -> FireShot
  -> 记录释放反馈与比赛结果
```

### 13.4 异常路径

```text
定位过期       -> PAUSED/RECOVERY -> 重定位或人工确认
目标观测过期   -> 等待新目标，不发送投篮
双车消息过期   -> 取消当前协作动作，保持安全
机构超时       -> RECOVERY -> 回到安全位置或请求人工处理
CAN 掉线       -> FAULT/ESTOP，禁止继续驱动
急停           -> ESTOP，锁定危险动作
```

## 14. 定位质量如何影响比赛动作

### 14.1 位姿质量门

全局位姿只有在以下条件同时满足时才允许驱动场地相关动作：

```text
pose_available
AND pose_valid
AND map_locked
AND 0 <= pose_age_sec <= max_pose_age_sec
```

如果任意条件不满足，pose command bridge 返回明确原因：

- `pose_unavailable`；
- `pose_invalid`；
- `map_unlocked`；
- `pose_stale`。

### 14.2 投篮互锁

投篮允许条件是逻辑合取：

```text
FireShotEnabled =
  stage_active
  AND pose_valid
  AND map_locked
  AND pose_fresh
  AND target_valid
  AND target_fresh
  AND ball_present
  AND mechanism_healthy
  AND teammate_safe
```

这个公式把“安全”从口号变成程序行为。比如目标检测仍然显示篮筐，但地图已失锁时，系统仍然拒绝投篮，因为目标方向和场地动作之间缺少可靠的全局关系。

## 15. 从仿真到真实竞赛机器人的迁移

### 15.1 为什么要先做接口仿真

仿真阶段优先验证四类不依赖具体硬件的内容：

1. 消息字段、单位和时间戳是否一致；
2. TF 链和四元数到 yaw 的计算是否正确；
3. 状态机在正常、超时、重复和取消情况下是否按预期迁移；
4. 规则约束能否被任务流程调用。

这一步减少真机调试时的变量数量，让现场问题集中在传感器、网络和机构本身。

### 15.2 真实迁移的关键差异

仿真和真机之间的差异主要来自：

- MID-360 的实际点云密度、扫描模式和网络传输；
- 内置 IMU 与 LiDAR 的时间同步和安装外参；
- 底盘振动造成的扫描运动畸变；
- RGB-D 深度在篮架、反光表面和遮挡条件下的变化；
- ESP-NOW 无线环境与双车距离变化；
- STM32 机构响应和电池电压变化；
- 比赛人员、围栏和临场碰撞造成的动态遮挡。

因此迁移不是把一个 launch 文件换成另一个 launch 文件，而是逐项复核时间、坐标、质量和反馈。

### 15.3 真机联调顺序

```text
1. 单独检查 MID-360 与内置 IMU 输入
2. 检查 FAST-LIO2 局部位姿和点云去畸变
3. 建图并冻结场地地图
4. 验证 initial pose 与 map -> odom
5. 低速验证位姿到目标距离/航向
6. 接入 RGB-D/YOLO 目标门控
7. 单车验证 UART 与 STM32 底盘/机构
8. 双车验证位置同步、ACK、过期和取消
9. 无球完成移动与状态机演练
10. 有球完成收球、传球和接球
11. 静态投篮标定
12. 动态移动、完整任务和赛场流程
```

### 15.4 竞赛现场的运行策略

比赛前保存与本次运行绑定的 manifest：

```text
rulebook_revision
map_version
extrinsic_version
software_commit
FAST-LIO2 profile
camera/YOLO profile
communication profile
STM32 firmware version
robot identifier
run timestamp
```

这样每次现场调试都能回答：使用了哪一张地图、哪一版外参、哪一版固件、哪一版规则和哪一套参数。

## 18. 测试与验证方法

### 18.1 输入和接口测试

首先使用合成消息测试：

- 非有限点坐标能否被拒绝；
- `offset_time` 异常能否触发输入无效；
- IMU 时间戳不新鲜时是否阻止 `preflight_ready`；
- TF 是否存在重复发布者；
- 四元数归一化和 yaw 计算是否正确；
- 消息版本、单位和 frame 是否符合合同。

### 18.2 定位回放测试

使用 rosbag 或录制数据验证：

1. MID-360 点云与内置 IMU 的时间关系；
2. FAST-LIO2 局部里程计的连续性；
3. 地图加载、initial pose 和 `map -> odom` 更新；
4. tracking、relocalizing、lost 状态的转换；
5. 位姿年龄、丢包计数和匹配质量是否进入诊断。

### 18.3 视觉目标测试

针对 target gate 构造：

- 高置信度、稳定、距离合法的新鲜目标；
- 低置信度目标；
- 超出距离范围的目标；
- 时间戳过期的目标；
- 深度为 NaN 或无效的目标；
- 检测框跳动导致的非稳定目标。

测试目标不是追求一个漂亮的布尔值，而是保证每种拒绝都有可读原因。

### 18.4 总控与通信测试

至少覆盖：

| 场景 | 预期行为 |
| --- | --- |
| 正常开始比赛 | `BOOT -> PREFLIGHT -> WAIT_START -> ACTIVE` |
| 位姿过期 | 进入 `RECOVERY`，停止全局动作 |
| 目标过期 | 拒绝 `FireShot`，等待新观测 |
| 重复 ACK | 不重复执行同一任务 |
| 消息乱序 | 按 sequence 拒绝旧消息 |
| 双车断链 | 取消依赖队友的动作 |
| UART 超时 | STM32 进入安全控制，ROS 侧记录故障 |
| CAN 掉线 | 禁止继续发出危险动作 |
| 操作员急停 | `ESTOP` 锁定 |
| 规则时钟到期 | 进入 `FINISHED` |

### 18.5 真机验证指标

现场应记录条件化指标，而不是只记录“成功/失败”：

- LiDAR/IMU 输入频率、时间偏移和丢包；
- FAST-LIO2 局部位姿更新频率、短时漂移和失锁次数；
- 地图匹配质量与重定位时间；
- 目标检测置信度、深度稳定性和目标年龄；
- 位姿到目标距离/航向误差；
- 传球 ACK 延迟、重复消息和过期比例；
- STM32 动作完成时间、超时、限位和过流；
- 每个比赛阶段的耗时和动作结果；
- 正常、暂停、恢复和急停次数。

这些指标能把“系统表现不稳定”拆成可定位的问题：是输入、估计、目标观测、无线通信，还是机构执行。

## 19. 关键工程决策与权衡

### 19.1 保留逐点时间，而不是立即转成普通点云

优点：保留去畸变所需的信息，适合高速运动；代价：输入接口更严格，需要维护 `CustomMsg` 的字段语义。对于比赛机器人，时间正确性比接口表面简单更重要。

### 19.2 局部里程计与固定地图分开

优点：局部运动连续，地图校正不会直接破坏控制；代价：需要维护 `map -> odom` 锚点和状态机。对于有固定场地和目标坐标的比赛，这种职责分离能让导航和投篮共享同一全局参考。

### 19.3 高层 ROS 2 与 STM32 分工

优点：感知和任务具有可读性，电机和机构具有实时性；代价：必须设计 UART/CAN 协议、ACK、超时和取消。系统因此拥有可解释的控制边界，也保留 MCU 级安全保护。

### 19.4 反馈驱动而不是固定 sleep

优点：动作完成定义来自实际机构；代价：需要更多传感器状态和异常分支。这个选择直接提高了系统对电压、负载和机械误差的适应能力。

### 19.5 共享接口而不是直接 topic 耦合

优点：可以更换 FAST-LIO2 profile、视觉模型或通信实现而不重写总控；代价：需要维护版本化数据合同。长期来看，接口合同使调试证据和实验记录更可靠。

## 20. 科学问题、工程方法和可迁移经验

### 20.1 科学问题如何落到实验变量

项目中的每个设计都可以转成可比较的变量：

| 科学问题 | 可控变量 | 可观察指标 |
| --- | --- | --- |
| 逐点时间是否影响高速定位 | 保留/丢弃 `offset_time` | 配准质量、短时漂移、失锁次数 |
| 固定地图是否改善场地动作 | local-only / map-anchored | 全局位姿一致性、目标到位误差 |
| 目标门控是否减少误投篮 | 开启/关闭置信度、深度、新鲜度 | 拒绝原因、有效投篮率、误触发次数 |
| ACK 是否提高双车协作可靠性 | 有/无 ACK 与幂等 | 重复动作、过期任务、传球完成率 |
| 反馈是否优于固定延时 | 反馈驱动 / 固定等待 | 动作完成时间、超时和机构冲突 |

这使得系统不仅适合比赛，也适合形成可重复的工程实验。

### 20.2 失败模式不是附属信息

高质量机器人系统需要保留失败链：

```text
输入缺失
  -> 估计质量下降
  -> pose_valid=false
  -> 全局动作被拒绝
  -> supervisor 进入 recovery
  -> 重定位/重连/人工确认
```

如果只记录最终“投篮成功或失败”，就无法知道问题发生在视觉、定位还是机构。项目通过状态、原因、序列号和时间戳把失败变成可分析数据。

### 20.3 我如何把工程调试做成科研问题

真实机器人调试往往从一句很模糊的话开始：“车跑偏了”“投篮不稳”“两车配合不上”。我的处理方式是把这类描述拆成一个可以检验的假设，再设计最小实验：

| 模糊现象 | 可检验假设 | 最小对照 | 记录的量 |
| --- | --- | --- | --- |
| 运动时定位变差 | 点云去畸变使用了错误时间 | 保留/忽略逐点时间 | 配准残差、轨迹连续性、失锁次数 |
| 车到目标旁却不投篮 | 目标观测或地图位姿已过期 | 新鲜/过期消息 | target age、pose age、拒绝原因 |
| 投篮距离改变后命中率下降 | 深度测距或弹道参数未按距离更新 | 固定参数/标定参数 | 距离误差、发射参数、落点 |
| 传球流程偶尔重复 | 无线重发没有幂等处理 | 单次/重复消息 | sequence、task_id、重复执行次数 |
| 机构偶尔提前进入下一步 | 固定延时短于实际完成时间 | 固定等待/反馈确认 | 机构状态、完成时间、超时 |

对照实验的价值在于，它把“感觉不稳定”变成能被日志、波形、位姿轨迹或比赛结果支持的判断。修复后我会复现原场景，确认改动解决的是目标问题，而不是通过改变多个参数碰巧得到一次好结果。

### 20.4 我在项目中形成的工作习惯

1. **先保留现场事实**：保存日志、参数、视频、消息和版本，不凭记忆修改结论；
2. **一次只改变一个主要因素**：传感器、算法、通信和机构分开验证；
3. **先做小规模复现，再扩大测试**：单模块、单车、双车、完整比赛逐级推进；
4. **把成功和失败放在同一张表里**：记录失败发生在哪个状态、哪条消息和哪个机构反馈；
5. **修复后重新做原来的测试**：不以“代码编译通过”替代系统行为验证。

这套习惯让我的工程工作具有科研上的可解释性，也让团队成员能够复用排障过程，而不是只能依赖某一个人的现场经验。

### 20.5 这套方法如何迁移到其他机器人

虽然项目针对 ROBOCON 机器人篮球，但其方法可以迁移到：

- 室内移动机器人：固定地图、位姿质量和动作互锁；
- 多机器人搬运：角色、ACK、幂等和相对位置；
- 物流分拣：目标观测新鲜度、机构反馈和任务取消；
- 无人机协同：观测质量、通信过期和高低层控制分离。

可迁移的不是某个比赛常数，而是“观测--状态--动作--反馈”的系统化组织方式。

## 22. 个人贡献的技术化表达

### 22.1 适合简历的一句话

负责 ROBOCON 机器人篮球系统的 LiDAR/感知与定位链路：基于 Livox MID-360 内置 IMU 与 FAST-LIO2 建立 ROS 2 位姿接口，将 RGB-D/YOLO 篮筐检测、距离与航向计算、投篮弹道参数、双车通信和 STM32 执行层接入统一比赛状态机，并完成仿真到真实竞赛机器人的迁移与现场联调。

### 22.2 适合面试的技术版

我负责的是系统里最容易互相影响的几条链路：LiDAR--IMU 定位、视觉目标观测、投篮参数计算和双车执行。我的设计重点是把它们通过明确的数据合同连接起来。MID-360 的点云保留逐点时间，FAST-LIO2 提供连续局部位姿，固定地图模块提供场地坐标，RGB-D/YOLO 提供篮筐距离和目标稳定性，状态机只有在位姿、目标、球、机构和队友安全都满足时才放行投篮，最终通过 UART/ESP-NOW 把高层动作交给 STM32，再由 CAN 和机构反馈确认执行结果。这样系统每一步都有输入、判据和恢复路径。

### 22.3 适合科研交流的版本

我的思路不是单独优化一个模块，而是研究如何让异构观测在竞赛任务中形成可信的闭环。LiDAR--IMU 提供几何连续性，RGB-D/YOLO 提供语义目标，比赛规则检查逻辑提供任务合法性，双车协议提供协作一致性，STM32 提供确定性的执行和安全边界。通过显式的时间、坐标、状态和反馈接口，系统可以解释为什么执行或拒绝一个动作，也可以在定位、通信或机构异常时进入恢复流程。

## 25. 最终的系统理解

如果只记住这个项目的主线，可以用下面的五句话概括：

1. **规则决定任务边界**：时间、距离、球权和得分定义进入状态机；
2. **MID-360 + 内置 IMU + FAST-LIO2 提供几何连续性**：机器人知道自己在场地坐标中的运动状态；
3. **RGB-D/YOLO 提供语义目标**：系统知道篮筐在哪里、距离多远、观测是否可信；
4. **ROS 2、双车协议和状态机把观测变成协作动作**：传球、接球和投篮按照证据推进；
5. **STM32/CAN 把高层动作变成真实执行**：底层负责实时控制和安全反馈，上位机根据反馈继续或恢复。

完整闭环可以再次写成：

```text
规则约束
  -> 比赛状态
  -> 传感器输入
  -> LiDAR--IMU 位姿与 RGB-D/YOLO 目标
  -> 距离、航向、弹道和协作决策
  -> UART/ESP-NOW 高层命令
  -> STM32/CAN 底盘与机构执行
  -> ACK、反馈、诊断与恢复
  -> 下一阶段任务或比赛结束
```

这套系统体现的核心能力是：把论文中的估计和感知方法放进真实竞赛约束中，用明确的接口、可验证的条件和可恢复的状态机，把它们组织成一套真正能够在机器人上工作的工程系统。
