# 共建指南（CONTRIBUTING）

## 谁可以贡献

- 队内学弟学妹：纠正错误，补充真实案例
- 其他队伍同学：提 Issue，提交 PR

## 可以贡献什么

- **勘误**：参数错误，错别字，失效链接
- **案例**：你的真实调试案例，按下方卡片格式
- **章节扩充**：把某个知识点写得更清楚，更贴近实战

## 不能贡献什么（红线）

- 队内机密：比赛战术，内部事故与纠纷细节，未公开的参数与图纸
- 他人原文与个人故事：不整段搬运，技术内容请提炼为通用故障模式与方法表述
- 他人隐私：队友真名，除本人同意外不放，含人脸且未授权传播的照片不放

## 案例卡格式（统一模板）

```
### 案例标题
一句话概括现象

- 现象：
- 排查路径：按时间顺序，写当时怎么想的
- 根因：
- 解决：
- 预防与复盘启示：
- 涉及知识：第 X 章
```

## 章节写作规范

- 每章结构：一段亲历场景开章，正文分节展开，常见问题，检查清单收尾
- 选型与案例章节用真实配置和数据说话，写清对比与取舍
- 标点纪律：禁用括号，分号，顿号，破折号，列表用逗号或分行表达
- 语气纪律：不写防御型叙事，少用否定句，直接讲事实与做法
- 口语纪律：禁止过于口语化，不用网络流行语与梗，讲平实的话
- 行文纪律：禁止金句收尾，口号排比，拟人比喻，设问自答，对仗升华
- 术语首次出现给出全称与缩写，参数必须带单位
- 图优先用 Mermaid 或图片，图片统一放 `assets/章号/` 目录
- 代码块用三反引号标注语言，单块 40 行以内，先讲用途再贴代码，注释只标关键行
- 不整段引用他人原文，技术内容统一转为自己的表述

## 提交流程

1. Fork 或拉新分支
2. 提交前自查：链接可达，术语一致，无红线内容
3. PR 与 Merge Request 描述写清：改了什么，为什么改
