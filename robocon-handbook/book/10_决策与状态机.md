## 状态机基础

四个概念：状态，事件，转移，超时。

- **状态**：机器当前所处的环节。自检，待命，搜索篮筐，对齐，蓄力，发射，等确认。
- **事件**：外部输入或者内部条件满足。看到篮筐，位姿就绪，队友确认。
- **转移**：从一个状态到另一个状态，带条件与动作。条件写具体，动作写最小。
- **超时**：每个等待态都配一个超时。等目标超时，回搜索。等确认超时，重发或者放弃。

主链先画出来：上电自检，进待命。收到任务进搜索，目标检查四个条件全过进对齐。对齐完成且位姿有效且地图锁定进蓄力，发射前八项检查全过允许发射，回读释放状态确认这一发完成，回待命。

四个概念落到工程上各有一条纪律。状态的职责要单一，一个状态只干一件事，一个状态里塞两件事，超时和错误处理就要写两套，状态图跟着膨胀。状态总数压在二十个以内，超过就先分层，主链一层，子流程一层，每层各自成图。转移条件写具体，对齐完成这种说法不算条件，航向误差进窗口且底盘停稳才算，条件越具体，代码与状态图越容易对上。转移动作写最小，只做状态清点与标志位更新，重活留给状态自己的执行体。

事件分三类：外部输入，比如按键与收到的消息。内部条件，比如位姿就绪与机构到位。时间，超时本身也是一种事件。三类事件在代码里的入口各不相同，画图时都用同一支箭头表示，时间这一类最容易被漏掉，幽灵状态的教训大多从这里来。

超时值这样定：大于最坏情况下的正常等待时长，小于这个任务允许失去的时效。等目标的超时按帧率和任务节奏估，等确认的超时按链路往返估，等机构动作的超时按动作行程估。超时值写进状态表，与代码里的常量对表，改一处两边都要动。

## async 与 await 写法

ROS 2 的 python 节点里，状态机用 asyncio 写比较自然。每个 await 都是状态转移的落点。

- 等目标：await 一个事件。
- 等位姿：await 一个 future。
- 等确认：await 一个 future，配 wait_for 设超时。
- 超时：wait_for 抛超时异常，抓到就转移。

纪律两条：await 之前把状态写进黑板，醒来之后重新读一遍条件，等待期间外部状态可能已经变化。醒来还按进入等待时的条件继续走，就会出竞态。

asyncio 是单线程事件循环，协程在 await 处让出执行权，循环去跑别的任务，等待不占 CPU。三个原语覆盖状态机的全部等待形态：Event 适合等单个信号这类场景，wait_for 给单个 future 加超时，wait 配 FIRST_COMPLETED 等一组任务里最先完成的那个。取消语义要善用，等待结束后把没有胜出的任务取消掉，否则会留下悬挂任务与无人取回的异常。事件残留是另一类坑：置位过的 Event 不清，下一轮等待会直接被旧信号放行。

一发进攻里两个等待点的代码骨架如下。

```python
import asyncio

class AttackFlow:
    """一发进攻的状态机片段，事件在别处 set，黑板共享状态"""

    async def wait_target(self) -> str:
        """等目标或急停，谁先到算谁，到点超时"""
        self.bb.set("state", "search")          # await 前先写黑板
        target = asyncio.create_task(self.ev_target.wait())
        estop = asyncio.create_task(self.ev_estop.wait())
        done, pending = await asyncio.wait(
            {target, estop},
            timeout=self.timeout_target,        # 超时值按任务时效定
            return_when=asyncio.FIRST_COMPLETED)
        for t in pending:
            t.cancel()                          # 收掉没有胜出的任务
        if estop in done:
            raise EStop()                       # 急停打断，最高优先级
        if target in done and self.target_valid():
            return "align"                      # 醒来重新读条件
        return "search"                         # 超时或条件失效

    async def wait_ack(self, seq: int) -> bool:
        """等队友确认，只认对应序号的确认，超时返回失败"""
        self.ev_ack.clear()                     # 清掉上一轮的残留置位
        self.expect_seq = seq                   # 确认回调按这个序号匹配
        try:
            await asyncio.wait_for(self.ev_ack.wait(), self.timeout_ack)
            return True
        except asyncio.TimeoutError:
            return False                        # 交给上层重发或放弃

    async def run(self):
        while not self.ev_estop.is_set():
            nxt = await self.wait_target()      # 一个 await 一次转移落点
            self.bb.set("state", nxt)
            if nxt == "align" and not await self.wait_ack(self.seq):
                continue                        # 确认没到，回搜索重试
```

关键行对照如下。两个等待点用了两种原语，这是刻意的：等目标要同时盯着多个事件，用 wait 加 FIRST_COMPLETED，目标和急停谁先到算谁，急停任务赢了就抛异常，这次等待当场结束。急停入口在每个等待点都留一个，代码形态就长这样。等确认只盯一个信号，用 wait_for 加超时，超时抛 TimeoutError，抓回来转成失败返回值，由上层决定重发还是放弃。

等待结束先取消没赢的任务，最后两行注释里的悬挂任务与残留置位就是被这一步和 clear 挡住的。确认环节还有两个细节：等待前先清一遍确认事件，防止上一轮的残留置位把这次等待直接放行。确认回调收到的序号与期待的序号对上才置位，对不上的确认丢弃。另有一个线程模型的坑要记住，rclpy 的回调不在事件循环线程里，回调里置事件要用 call_soon_threadsafe 转一道，直接 set 在边界工况下会丢唤醒。醒来之后 target_valid 重新读一遍条件，对应纪律第二条，等待期间外部状态可能已经变化。黑板写入放在 await 之前，每次转移落点写一次，监控和日志从这里读状态。

## 事件竞态

等任意一个事件：asyncio.wait 配 FIRST_COMPLETED，同时等目标事件，超时事件，急停事件，以最先完成的为准。急停的优先级最高，所以每个等待点都留一个急停入口，急停包一到，立刻打断当前等待。

竞态有两种典型形态。第一种，等待期间条件已经变化：等到到位事件之后，直接按进入等待时的预定计划继续走，实际上车已经被碰撞挪了位，或者目标已经被队友取走。修复方式固定，醒来重新读一遍条件，条件失效就原地重等。第二种，事件晚到：上一步超时已经触发，动作切走了，迟到的事件把当前状态又推一次，动作被重复触发。修复方式两个，等待结束时统一取消没赢的任务，加上事件处理带序号或时间戳，过了时效的事件直接丢。两条合起来是一句纪律：await 返回之后，条件要重新校验一遍再继续走。

## 黑板与共享状态

黑板是一个共享字典加锁，放传感器快照，任务参数，队友状态。读写纪律：写入只写带时间戳的快照，读取先检查时间戳的新旧。位姿质量三项，跟踪状态，地图锁定，位姿年龄，跟位姿一起上黑板。超时报进恢复流程，恢复流程本身也是一个状态。

锁的粒度要小，读写各是一把短锁，临界区里只放赋值，不放计算与 IO，事件循环里更不允许阻塞。位姿，质量三项，来源，按组原子写入，一次落盘，读方拿到的是完整一组，不会出现位姿更新了而质量还是上一拍的错配。读取先查时间戳，读到超过阈值没有更新的字段，按失效处理，不拿旧值凑合。位姿年龄这个字段是这个纪律的样板：超 0.30 秒直接进恢复流程，恢复流程自身有状态图，它会暂停发射联锁，等位姿回来再放行。

## 赛场热重置

热重置是赛场的硬需求：按一个键或者收一条消息，状态机清回待命，参数重新加载，进程不动。好处是恢复时间从拉闸重开的几分钟降到几秒。

三个做法：状态清空走统一的 reset 函数，各自负责清各自的状态，清完打一条日志。热重置要做成幂等的，连按三次跟按一次效果一样。电机使能状态单独考虑，重进待命的时候底盘保持使能还是断电，按当时的安全条件定。

幂等靠设计保证：清态函数只做置默认值，不做累加，不做硬件动作，连按的第二次是在第一次的结果上再置一遍同样的值，结果不变。参数重新加载走同一套加载路径，与开机加载共用代码。电机使能的判定条件写清楚，练习场上下手慢，先断电再确认，正式比赛节奏紧，保持使能但锁速度。热重置的验证方式就是连按三次，看状态，看参数，看日志，与按一次完全一样才算过。

## 流程编排实战

一发完整进攻的状态图，我们把每个跳转旁边的条件都写成一行的检查。

- 搜索：目标检查四个条件，置信度，距离范围，连续帧稳定，观测时效，全过才走。
- 对齐：底盘横移微调，航向误差进窗口就算完成。
- 蓄力：发射前八项检查逐项过，急停，球在位，机构就绪，释放反馈，位姿有效，地图锁定，目标有效，队友位置安全。
- 发射与确认：释放回读才算这一发完成，确认没到就等或者重试，重试次数画在图上。
- 队友协作：传球或接球按对方确认推进，对方没确认，这一步不往前走。

三个幽灵状态的教训：超时转移漏画，确认分支漏画，急停之后状态没清。下面逐个说开。第一个，等目标的那条超时箭头当时没画，代码里也没有，练习赛上一帧目标突然消失，状态卡在等待里，车停在原地，等人工处置。修复是把每个等待态配的超时补进图和代码，超时回搜索。第二个，发射之后的确认分支漏画，队友的确认消息正常时一切正常，确认丢失时状态机没有路径可走，代码里靠一个临时补丁硬扛，图上根本没有这条线，两条线各说各话。修复是把确认没到的分支画实，重试计数写在箭头上。第三个，急停之后状态没清，急停解开回待命，机构却还停在中途的样子，参数还是那一发的值。修复是急停恢复路径显式执行一次统一 reset。

流程图与代码要一一对应，代码里每个 await 都能在图上找到那条箭头。图上找不到对应箭头的 await，都可能是故障点。反过来也查一遍，图上每条箭头在代码里找落点，找不到的箭头是没实现的分支，通常是幽灵状态的下一个来源。
