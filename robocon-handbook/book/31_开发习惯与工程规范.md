# 第 31 章 开发习惯与工程规范

> 联调那天编译不过。git log 最后一条提交写着修 bug，点进去改了三十个文件，没人知道哪一处动了编译开关，也没人敢退回，因为退回会带上三天的改动。那天下午，全组帮一个人追溯提交历史。

## Git 工作流

主分支保持随时能编译。功能开分支，联调合回来，赛前定点打标签冻结版本。提交信息写清楚三件事：改了什么，为什么改，影响哪个模块。大改动拆成小提交，退回的时候更容易定位。接口冻结之后再动结构要谨慎，串口帧格式这类接口文件尤其要保守，固件和上位机两头对齐了才修改。

分支与标签的命名直接写用途。功能分支 feature 开头，修复分支 fix 开头，名字里带模块与日期。标签用带日期的冻结名，赛前每过一轮联调打一个，现场退回旧版本是一条命令的事。

提交粒度按可独立退回的单元切。一次提交只做一件事，改格式的提交不夹带逻辑修改，退回时不用手工挑拣。提交信息按三段式写：先写改动，再写原因，最后写影响模块。第三段的作用在半年之后显现，接手的人靠它判断影响面。

退回旧版用 revert，不用 reset。revert 生成一条反向提交，历史保留，队友的本地仓库不受影响。reset 改写历史，只允许留在自己的本地分支上，没有协调不推到共享远端。

一个功能从开发到冻结的常规操作，走下面这条序列。

```bash
# 从主干开功能分支
git switch main
git pull
git switch -c feature/ballistic-table-v2

# 提交: 小步多次, 信息写清改动与影响
git add src/ballistic/table.cpp config/ballistic.yaml
git commit -m "弹道表: 增加罚球线到三分线插值, 影响发射参数查询"

# 联调通过后合回主干
git switch main
git merge --no-ff feature/ballistic-table-v2
git push

# 赛前冻结: 打标签
git tag -a v2025.07-pretest -m "赛前联调冻结版本"
git push origin v2025.07-pretest

# 定位要退回的提交: 先看历史, 再撤销
git log --oneline -10
git revert 3f2a1bc
```

关键行四处。switch -c 从当前主干开分支，开工前先 pull，不基于旧代码开发。merge 加 no-ff 保留分支形态，回看历史能看清一个功能由哪些提交组成。tag -a 建带说明的标签并推到远端，现场退回旧版本用 git switch --detach v2025.07-pretest 一步到位。revert 按提交号反向应用，出问题的提交在历史里仍然可见，排查不受影响。

## 日志分级

日志分四级：DEBUG 看细节，INFO 记流程，WARN 报异常，ERROR 报故障。高频控制环少打印，打印过多会影响控制节拍。关键节点必打：状态迁移，目标确认，发射指令，重定位修正，带上时间戳和关键数值。现场出问题先查日志，所以日志要落到固定路径，字段要便于解析。

MCU 侧的日志用宏实现，这段代码进到进阶档：编译期等级开关把低于等级的调用整段裁掉，发布固件改一个宏就关闭调试输出，不占 flash，也不占执行时间。

```c
#include <stdio.h>

/* log.h: 分级日志宏, 编译期开关 */
#define LOG_DEBUG 0
#define LOG_INFO  1
#define LOG_WARN  2
#define LOG_ERROR 3

#ifndef LOG_MIN_LEVEL
#define LOG_MIN_LEVEL LOG_INFO        /* 发布固件改成 LOG_WARN */
#endif

extern unsigned long millis(void);    /* 由时基模块提供 */

#define LOG(level, tag, fmt, ...)                                  \
    do {                                                           \
        if ((level) >= LOG_MIN_LEVEL)                              \
            printf("[%s][%lu] " fmt "\r\n", tag,                   \
                   (unsigned long)millis(), ##__VA_ARGS__);        \
    } while (0)

#define LOGD(...) LOG(LOG_DEBUG, "D", __VA_ARGS__)
#define LOGI(...) LOG(LOG_INFO,  "I", __VA_ARGS__)
#define LOGW(...) LOG(LOG_WARN,  "W", __VA_ARGS__)
#define LOGE(...) LOG(LOG_ERROR, "E", __VA_ARGS__)

/* 高频环限流: 每 n 次调用打一条 */
#define LOG_EVERY(n, log_call)                                     \
    do {                                                           \
        static unsigned int cnt_ = 0;                              \
        if (++cnt_ % (n) == 0) { log_call; }                       \
    } while (0)

/* 用法: LOGI("ready"); LOG_EVERY(100, LOGI("spd=%d", spd)); */
```

关键行四处。do while(0) 包一层，宏在 if 不带花括号的语境里展开仍然安全。等级比较在编译期常量上完成，低于等级的调用被编译器直接裁掉。millis 由时基模块提供，每行日志带机器时间，跨设备对齐时间线靠它。限流宏的计数变量是函数内 static，每个调用点各计各的，高频环里按 100 次一条的密度打印，控制节拍不受影响。

两条纪律配套。其一，中断服务函数里不用这套宏，串口打印阻塞的时间会破坏节拍，这条在第 27 章写过。其二，日志一行一条，字段顺序固定为时间，等级，模块，正文，便于 grep 与脚本解析。现场导出日志时先按模块过滤，再按时间排序，把现场时间线还原出来。

## 单元测试与离线仿真

测试的第一形态是录包回放：同一段录包，改前改后各跑一遍，输出对齐看差异。CRC 计算，弹道解算，坐标变换这类纯函数写几行断言，改一处跑一遍，回归成本接近零。仿真环境先跑通接口，把逐点扫描的时序也模拟上，接口对上再上真机。真机时间有限，能在离线环境验证的内容先离线验证。

测试分三层，各管各的。纯函数层用断言，每次提交都能跑。模块回放层用同一段录包，改完模块跑一次，对比频率，残差，轨迹偏差，完整度四项，指标不退才算过。实机层资源最贵，只留给跨过联合逻辑的改动。三层里成本最低的是第一层，收益最大的一段代码经常就是它。

CRC 与帧协议这类纯函数的用例写法如下，用一个文件把算法锁住，顺带把组帧与解析的往返也盯上。

```python
# test_crc16.py: 固定向量加往返测试, 盯住帧协议
import pytest
from pack.crc16 import crc16_ccitt, build_frame, parse_frame

def test_known_vectors():
    assert crc16_ccitt(b"123456789") == 0x29B1   # 标准检查向量
    assert crc16_ccitt(b"") == 0xFFFF            # 空载荷等于初值

def test_frame_roundtrip():
    payload = bytes([0x01, 0x02, 0x03, 0x04])
    frame = build_frame(0xAA, payload)
    ok, got = parse_frame(frame)
    assert ok and got == payload

def test_corrupt_bit_rejected():
    frame = bytearray(build_frame(0xAA, b"\x01\x02\x03"))
    frame[4] ^= 0x01                             # 翻一个数据位
    ok, _ = parse_frame(frame)
    assert not ok
```

关键行三处。标准检查向量 0x29B1 是 CCITT 版的公开校验值，任何算法改动先过这一关，改坏了这里立刻报出来。往返测试让组帧与解析共用一套实现互验，比手工拼字节数组可靠。翻位测试改动数据位再解析，确认校验在拦错，防的是校验范围写错这类隐蔽问题。

跑法一条命令：pytest test_crc16.py。队里的规矩是改完 CRC，帧解析，坐标变换这三类代码，先跑本地用例再上机，上机时间留给用例覆盖不到的部分。

## 文档规范

接口文档四条纪律：字段，单位，频率，超时。四个都写清，联调少对半天的表。联调清单和预检清单随手维护，每次遇到问题往清单里加一条，现场按清单走就不容易漏项。README 写清楚怎么编译，怎么跑，依赖什么版本，半年后重新接手的人首先看的就是它。

接口文档先画字段表，一行一个字段，偏移与长度按字节算，类型注明字节序，说明写用途，物理量注明单位。米与毫米混用是联调返工的高发点，单位这一列不省。串口协议这张表的示例：

| 字段 | 偏移 | 长度 | 类型 | 说明 |
| --- | --- | --- | --- | --- |
| 帧头 | 0 | 2 | 字节 | 固定 0xAA 0x55 |
| 长度 | 2 | 1 | uint8 | 载荷字节数，上限锁在 255 字节以内 |
| 序号 | 3 | 1 | uint8 | 指令去重 |
| 载荷 | 4 | N | 字节流 | 按字段表序列化 |
| CRC16 | 4+N | 2 | uint16 小端 | 覆盖长度，序号与载荷，低字节在前 |

变更记录表跟着接口走：日期，版本，改动点，影响范围。谁改谁记，改完发到队群对表。接口文件的改动要双端确认，串口帧格式这类文件，固件和上位机两边对齐之后才动。

README 再加一条常见问题清单，把踩过的坑按条目写上，300 毫秒断链这类口径也写进去，接手的同学先读 README 再读代码。

## 复盘制度

每次故障填一张卡：现象，排查路径，根因，解决，预防。根因可以转化为检查项的，分别加入启动自检或赛前预检。每周开一次短会，对齐进度也对齐问题。复盘记录事实和方法，为下一次同类故障提供参考。

填卡的时机是当场填框架，趁记忆新鲜补细节，隔天再回忆，排查路径的顺序会记混。卡片统一归档，按系统与日期检索，一张卡一个文件。

每周的短会十分钟，每人两句话：做了什么，卡在哪。卡点当场认领责任人，下次短会回报进展。群聊里的结论要同步进仓库文档，群消息不承担存档职责，翻聊天记录找结论是费时间的做法。

根因到检查项有三条去向：进启动自检，上电自动跑。进赛前预检，人按清单查。进回归脚本，代码层面防复发。舵机烧毁那次的复盘产出是限位与过流保护两条对策，落在控制器代码里，选型留余量写进下一次选型的要求。

## 代码评审

联调前互查一轮，重点看接口边界：越界检查，空指针，超时分支，异常兜底。参数硬编码查一遍，能进配置文件的搬进配置。评审把个人的经验扩散到全队，新人担任 reviewer 时收获最大，读别人的代码能补充自己的盲区。

评审按风险顺序看：接口边界第一，资源与并发第二，命名与注释第三。资源与并发这一段查三件事：动态内存有没有进 MCU 代码，共享变量有没有 volatile 与临界区保护，中断服务函数有没有超长逻辑。这三条在第 27 章有出处，评审时逐条核对。

评审的操作口径：看 diff 不看整个文件，小步提测小步评。意见对事不对人，拿不准的地方用提问句写。没有发现问题的评审也回一句看过，提测的人才知道可以往下走。评审里发现的问题，修完之后补一条用例进回归脚本，同一个问题不出现第二次。

## 嵌入式编码规范

MCU 侧代码另有一套纪律，来自电控组多年的实践，条目不多，执行的刚性比上位机侧强。

- 禁止动态内存。不用 malloc，不用 new。缓冲区全部定长分配，长度按协议上限取，收到超限长度立即丢弃，第 29 章收包状态机里的上限检查就是这条规矩。
- 命名统一。函数用模块前缀加动作，变量带单位后缀，宏全大写。临时变量不用单字母，判读代码时字母变量的含义全靠猜。
- 魔数进宏或枚举。同一字面量出现两次以上，必须有一个名字，改参数只改一处。
- 共享变量加 volatile。跨中断与主循环的数据用临界区或原子保护，规则与第 27 章一致。
- 中断服务函数短小。只置标志与搬数据，长逻辑放主循环，中断里禁止打印与延时。
- 头文件加防护宏，只放声明与宏定义，实现放源文件。
- 编译警告开到最高档，警告清零再提交。类型不匹配这类警告放着不管，换编译器版本的时候会集中爆发。

## 几条小结

- 提交信息要写清楚，未来接手的人最先看到的就是它。
- 日志的用处主要出现在故障排查时。
- 能离线复现的问题，排查成本最低。
- 规范在任何阶段都要执行，赛前紧张阶段尤其不能跳过。
