# 第 6 章 软件环境与迁移：Ubuntu 与 ROS 1 到 ROS 2

> 车在 ROS 1 上跑通了，往 Jazzy 与 Ubuntu 24.04 迁移的时候，功能看着全对，数据一条没到。我盯着空白的 RViz 坐了半小时，才想起 QoS 不匹配这种事从来不报错。迁移那两周学到的东西，比入门那一年加起来还多。

## 迁移的账，先算清楚

我们队的迁移目标是 Ubuntu 24.04 加 ROS 2 Jazzy，构建换到 colcon。动手前先算三笔账：接口要改多少，串口帧动不动，历史录包还能不能用。结论写在最前面：接口先冻结，底层框架后换。串口帧格式保持与固件兼容，车与 STM32 之间的字节流一个字节都不动，动的只是上位机内部的话题名与包名。

迁移这件事的框架，我们按三条原则执行。依赖先行：驱动与第三方先在 ROS 2 里跑通，雷达出点云，相机出图，定位出位姿，自研代码随后跟上。双轨并行：旧系统保底可跑，新系统逐模块替换，过渡期用跨代桥接工具对照关键话题，每迁完一个模块拆一座桥。数据说话：每迁完一个模块，用同一段录包在两边各跑一遍，比指标，指标不退才算过。

动手前先把家底盘一遍，一天完成，产出四张表加一份清单。话题表：名字，类型，频率，每个话题标注是否要求可靠传输。服务与动作表：一问一答的服务，长任务的动作接口，动作的目标，结果，反馈三段都要列。参数表：参数名，默认值，量纲，归属哪个节点。坐标帧表：帧名，父子关系，静态还是动态。录包数据集清单：每个关键场景一段包，标注当时的路面与光照条件。四张表加一份清单到手，接口才算真正冻结。冻结的意思是迁移期间字段名，单位，频率三样只读不改，谁要动先过联调对表。

两代系统的差别集中在几处。

- 构建：catkin 换成 colcon 与 ament，package.xml 与 CMakeLists 的写法都要改，launch 从老 xml 的写法换到 python 或新 xml。
- 接口：msg 包名与生成的头文件路径全变，include 与 import 需要逐处修改。
- 运行：QoS 从没有这个概念，变成每个话题都要对齐的参数。TF，参数声明，受管节点都是新的运行模型。
- 驱动：雷达，相机，串口驱动都要找 ROS 2 版本，有的只有第三方重写版。
- 工具：跨代桥接工具只支持部分消息类型，应急可以，正路是两边同代。

还有两处差异容易在手册里翻过去。时间 API 全换：节点时钟取代全局时间，定时器分成仿真时钟与墙钟两种创建方式，时间运算要带着时钟来源的意识写。消息类型有三处要改：时间类型变成秒与纳秒两段的内置结构，字节数组统一成 uint8 数组，部分枚举与常量的命名规范化。这两处不改全，编译能过，运行行为对不上。

常用命令贴一张对照表在工位上，迁移期省事。

| 用途 | ROS 1 | ROS 2 |
| --- | --- | --- |
| 跑节点 | rosrun | ros2 run |
| 跑一组 | roslaunch | ros2 launch |
| 话题列表与内容 | rostopic list 与 echo | ros2 topic list 与 echo |
| 频率与带宽 | rostopic hz 与 bw | ros2 topic hz 与 bw |
| 话题信息 | rostopic info | ros2 topic info 加 verbose |
| 录播 | rosbag record 与 play | ros2 bag record 与 play |
| 坐标系工具 | tf 回显与树查看 | tf2 对应可执行文件 |
| 参数 | rosparam | ros2 param |
| 构建 | catkin_make | colcon build |
| 体检 | roswtf | ros2 doctor |

两个新习惯跟着来：看话题先看服务质量信息，录包先看记录信息。这两条在后面反复用到。

## 常见问题清单

下面每一条都是真实遇到的，按卡住的时长从长到短排。

**QoS 静默丢数据。** 传感器话题默认 best effort，订阅端默认 reliable，两边档位对不上，端点静默不匹配，数据一条到不了，也不报错。表现是 RViz 空白，topic hz 为零。处理办法是传感器订阅端显式写 best effort，命令类话题显式写 reliable，联调第一步先看话题有没有数据。

机制在匹配规则上。QoS 有五组参数：可靠性分 best effort 与 reliable 两档，持久性分 volatile 与 transient local，另有历史与深度，deadline，liveliness。匹配的时候，订阅方要求的档位不能高于发布方提供的档位，雷达驱动按 best effort 发，订阅端按 reliable 要，两边对不上，连接静默地建不起来，中间件不抛异常也不重试提示。命令行排查时，topic echo 默认按 reliable 去连，正好错过 best effort 的话题，要显式指定服务质量再看。数据看不见的疑难，多半落在这一条上。

**TF 迟到订阅者。** 静态变换发布的时候用了默认配置，晚启动的节点查不到这条变换，lookup 直接超时。静态变换要发成 transient local，或者写进 urdf，启动时统一发布。

机制在持久性参数上。静态变换只发布一次，晚启动的订阅者在它发布之后才连上来。volatile 持久性下，发布者不为后来者保留消息，订阅者等不到那一条。transient local 让发布者在内存里保留最后一条，新订阅者连上立刻补发。tf2_ros 的静态广播者天生按 transient local 工作，自己拿普通话题发静态变换就会踩这个坑。相关的还有唯一发布者原则，迁移期旧节点残留加新节点同时发同一对父子帧，帧树上出现两个发布者，表现是变换跳变，排查时先数发布者。

**参数未声明。** ROS 2 里参数要先声明再读，直接取会抛异常，节点当场退出。launch 里看起来就像闪退，日志要翻到最下面才看得到原因。

机制在参数的归属上。参数变成节点私有，注册在节点自己的命名空间下，要先声明名称与类型，注册之后才允许读写。参数文件也从全局命名空间改成按节点名分组的 YAML 结构。好处是类型检查和动态回调有了落脚点，代价是老代码里随手取参数的写法要全部补声明。适配路径是声明，设默认值，再读。

**仿真时间混用。** 一半节点用仿真钟，一半用墙钟，时间戳在两条时基上来回跳，TF 报时间外推错误。use_sim_time 要么全开，要么全关，录包与回放时尤其要对表。这个问题我们在回放验证里遇到过，排查了大半天。

机制在时钟来源上。use_sim_time 打开之后，节点时钟不再读系统时间，改成读仿真器广播的时钟话题。两条时基上的 now() 各算各的，时间戳自然对不上。外推错误的原理也在这里：查询一个还没发生的时刻，或者时钟停住之后查询超出容忍窗口的时刻，查询失败。录包回放时特别要对表，回放的时间推进速度与真实时间不同，容忍窗口的边界会提前出现。

**串口设备名漂移。** ttyUSB0 今天插是雷达，明天插是 STM32。udev 规则按序列号绑别名，脚本里只认别名。权限问题一并处理，把用户加进 dialout 组。

机制在枚举规则上。内核按插入顺序分配设备名，先插谁谁就是 ttyUSB0，断电重插顺序一变，名字跟着变。udev 规则按设备自身的属性匹配，厂商号，产品号，序列号三样里挑最稳定的写进规则，绑定固定别名，脚本里只认别名。权限归组管理，用户加进 dialout 组之后，上电即可用，不用每次补权限命令。

**多播被禁。** 场馆网络或者交换机把多播关掉，两台机互相看不见，topic list 里看不到对方。做法是配置 unicast 发现地址，把对端 IP 显式列出来。

机制在发现方式上。ROS 2 没有 roscore，节点靠中间件自动发现，默认靠多播报文打招呼。多播被关，打招呼的报文出不去，两台机互相看不见。两条出路：给中间件配置对端发现地址，把对方 IP 显式列出来走单播，或者启用发现服务器，让所有节点到同一个地址报到。排查顺序先查域号是否一致，再查多播可达性，最后查防火墙。

**受管节点停在未激活态。** 生命周期节点启动后停在未配置或者未激活，话题存在但没有数据。上电自检里加一步查节点状态。

机制在生命周期上。受管节点把启动拆成创建，配置，激活几个阶段，每个阶段之间等人推进。节点起来了停在未配置，或者配置完停在未激活，话题出现在图上，数据没有。驱动与导航组件里这类节点不少，迁移后启动脚本只拉起进程，没人执行推进动作，链路上就缺一段。做法是把状态推进写进启动流程，或者对不需要管理的节点退回普通写法。

**执行器被长回调阻塞。** 一个回调里执行了三秒，其他话题全排队。回调组拆开，改用多线程执行器，重任务交给独立线程。

机制在调度上。单线程执行器一次只跑一个回调，三秒的重活把后面所有回调压住，队列满后开始丢弃。两条拆法：把重活从回调里挪出去，交给独立线程处理，或者上多线程执行器给回调分组，慢回调独占一组，快回调用另一组，互不排队。

**库版本冲突。** PCL 与 Eigen 版本在系统源与源码安装之间冲突，编译通过，运行崩溃。锁定版本，写进环境文档，换机器照着装。

机制在装载顺序上。同一个库存在两个版本，运行时先被搜到哪个全看环境变量顺序，编译期连的是一个版本，运行期加载的是另一个，符号对不上，运行期就出错。对策是锁定版本写进环境文档，第三方库优先统一走源码编译进工作区，换机器照着文档装。

**多传感器时间未对齐。** 相机与雷达各走各的时间戳，融合出来有重影。时间戳对齐加时延标定，急转弯工况验证。

机制在时间戳的产生点上。相机在曝光时刻打戳，雷达按逐点时间戳打包，各自的时钟与处理延迟不同，同一物理时刻在两条数据流里差着一段时间。融合按时间戳取最近邻，差多少错多少。对齐加时延标定之后，在急转弯工况里验证，激烈运动会把残余误差放大出来。

下面几条坑卡住的时间短一些，但都属于迁移期高频项。

**时间戳类型与精度未适配。** 老代码里自定义的时间字段与内置时间结构混用，精度截断或者高低位顺序搞反，表现为时序数据偶尔乱序。全部换成内置时间类型，秒与纳秒两段检查一遍。

**包名与头文件路径改一半。** include 与 import 只改了一半，编译通过，运行加载的还是旧库，行为对不上。构建之后全量扫一遍旧包名，一个不留。

**命名空间与节点重名。** 两个节点同名或者注册在同一个命名空间，话题被合并，消息互相覆盖。多车场景尤其多，按车加命名空间，坐标帧加前缀。

**桥接工具只支持部分消息类型。** 跨代桥接对消息类型的覆盖不全，自定义消息常常最晚支持，表现为消息桥过去了但字段是空。桥只当过渡的应急手段，限制在少数关键话题，正路是两边同代。

**全量并行编译打爆内存。** colcon 默认并行编译，内存不够时编译器被杀，报错却指向代码。并行度设上限，或者分批构建，再跑一次全量确认。

**录包写满磁盘。** 现场录包量大，磁盘写满之后任务中断，还可能把系统文件挤掉。录包目录设容量上限，写满滚动，长时间录制前先看剩余空间。

## 录包回放验证

迁移期最重要的一件事，是同一段录包跑两条链：老系统的处理结果与新系统的处理结果，同一段 bag，同一套参数协议，对齐之后逐项比较。差异逐条记录，能解释的写下原因。回放还能顺带验证 QoS 配置是否正确。录包时显式设置 QoS，默认策略会漏掉一些大话题。录包目录设容量上限，写满滚动。

比较指标分四样：话题频率，算法输出残差，位姿轨迹偏差，消息完整度。频率看链路的健康度，残差看数据质量，轨迹偏差看结果一致性，完整度看有没有漏消息。四项都不退，这个模块才算迁完。解释不了的差异单独记录，不带着未解释的差异往下一个模块走，攒到最后一起查，顺序就乱了。存储格式默认用 SQLite，长录包可以换 MCAP，回放前先看记录信息，确认话题齐全再开播。

## 给 2027 届的建议

先用 Humble 加 Ubuntu 22.04。生态成熟，教程多，问题也少，出了故障能搜到答案。Jazzy 加 24.04 等站稳了再上。不要一上来就追新版本。迁移的前提是接口冻结，固件与上位机之间的字节流不动，上层怎么替换都行。

双轨并行的节奏供参考。第一周打通环境与构建，再上雷达驱动，数据质量节点，定位接入，坐标系与固定地图，每一步用录包验收。第二周迁感知与任务状态机，双车通信与命名空间，规划与控制接口，最后端到端联调与异常演练。全程旧链保底，每迁完一个模块才拆一座桥。构建失败先别急着改代码，先确认是不是并行编译打爆内存，再确认依赖版本，最后才怀疑代码。

## 迁移清单

- 接口表冻结，串口帧格式对一遍，固件侧不改
- 关键场景各录一段包，含急转弯
- 新环境构建全绿，colcon build 一包不落
- 每个包跑通回放，话题有数据，频率对得上
- QoS 逐话题过一遍
- 设备名 udev 别名落盘，权限配好
- 多机发现改 unicast，双机互相可见
- 受管节点状态自检进开机脚本
- 回归：同一段包，新旧结果对齐之后再交回
- 消息包名与头文件路径全量替换，旧名零残留
- 参数声明补齐，参数文件按节点名分组
- 时间源全链一致，回放单独验证一遍

这张单子后来沉淀成一个固定套路，六件套：消息与话题含服务质量，坐标系，launch，参数，录包，构建。每迁一个模块过一遍六项，过了才拆桥。
