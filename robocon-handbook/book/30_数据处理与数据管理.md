# 第 30 章 数据处理与数据管理

> 深夜给仓库推代码，一个点云数据包卡在推送那一步，仓库提示文件太大。学长探过头来说，大文件走 Git LFS，代码和数据的仓库分家。那晚之后，我们的代码和数据分开管理。

## 数据流总览

车上的数据分三条流。感知流：雷达点云和相机图像进定位和检测。状态流：电机反馈，机构状态，心跳进决策。记录流：录包存成回放资产。再往外是训练流：数据集训练模型，量化之后部署回 Jetson。每条流的格式，频率，存储位置都写清楚，交接时按文档执行。

管理上加一条硬约束：录包不可再生。训练集可以从录包重算，标定表可以从录包复检，参数可以从录包回归，录包本身丢了就没法补。规矩定死：原始数据只增不改，任何处理产出新的派生文件，不覆盖原件。派生文件命名带处理标记，随时找回来源。

录包用 rosbag2。录制时显式指定 QoS，best effort 的话题在默认策略下会漏录，数据对不上账时先查这一条。录包目录单独放一块盘，按日期分目录，写满之前报警，盘满之后进程会以难以定位的方式出错，第 28 章讲过这个坑。

录完包跑三项检查：点数与帧数是否齐，时间戳是否单调，最新帧年龄是否新鲜。三项做成一条脚本，录包结束自动跑，比人工翻文件快，也比事后争论快。

## 滤波三件套

原始数据过完滤波再进决策。一是平均类，滑动平均压高频噪声，代价是延迟。二是中值类，用于抑制偶发野点，深度读数出现跳变时用它处理。三是状态估计，卡尔曼滤波族把预测和观测按噪声权重融合，IMU 和里程计的组合就是典型场景。视觉另有一套确认逻辑：置信度阈值，连续多帧稳定，观测年龄上限，三项条件全部满足，目标才被确认。

深度读数做近场辅助时跳变频繁，反光面，边缘像素，遮挡都会吐出偏离的读数。这类点用平均压不住，会把均值拖偏，常用的组合先中值摘野点，再平均压噪声，顺序不能反。先平均会把野点的影响摊进整个窗口，拖尾更久。

```python
# 基础档: depth_filter.py, 深度读数去野点, 先中值后滑动平均
from collections import deque

class DepthFilter:
    def __init__(self, med_n=5, avg_n=10):
        self.med_win = deque(maxlen=med_n)   # 中值窗, 摘偶发跳变
        self.avg_win = deque(maxlen=avg_n)   # 平均窗, 压高频噪声
        self.last_out = None

    def update(self, raw_m):
        if raw_m is None or not (0.1 <= raw_m <= 10.0):
            return self.last_out             # 无效读数沿用上一次输出
        self.med_win.append(raw_m)
        med = sorted(self.med_win)[len(self.med_win) // 2]
        if self.last_out is not None and abs(med - self.last_out) > 1.0:
            return self.last_out             # 超跳变阈值按野点丢弃
        self.avg_win.append(med)
        self.last_out = sum(self.avg_win) / len(self.avg_win)
        return self.last_out
```

关键行四处。第一道门槛做有效性检查，空值与超量程拒收，返回上一次输出兜底。两个窗口长度是起点值，按延迟预算调，控制环里用的小窗口按第 26 章的定长数组加环形索引实现，不在循环里整窗排序。跳变判定的参考取上一次输出，原始读数只进中值窗，野点影响不到参考基准。无效读数沿用旧值的策略有代价，下游不知道数据已经变老，配合新鲜度检查一起用，超龄数据由下游自行降级。

野点要留记录。被丢弃的读数进计数器与最近值日志，野点比例突然升高，通常是传感器表面脏了，或者光照条件变了，这时候处理物理层，继续加窗口长度只会把问题拖下去。窗口长度，跳变阈值，有效范围三个参数都进配置文件，现场可调，调完按数据流一节的检查口径复测。

## 数据集与标注

自采数据主要是赛场光照下的球和篮筐。标注要一致，框画多大算标准先确定，两个人标同一张图差一半，模型就会学到错误的边界。负样本专门收，观众席，走廊，反光地面这些误检源头都进数据集。训练集和验证集按场景分，同一段视频的相邻帧不要分到两边。数据增强补光照和角度，标定表和数据集版本一一对应。

采集按场景表推进。光照分顶光与侧光，距离分段覆盖，角度覆盖正对与斜视，遮挡场景单独收，目标只露一半的情况赛场经常出现。场景表列在采集计划里，采一段勾一行，开训之前过一遍，缺的场景补上再开始。

从录包到标注集的流程固定五步：录包归档，按间隔抽帧，抽帧结果连同来源信息写进清单，标注工具读清单出标注，导出统一格式进数据集版本目录。每一步留中间产物，哪一步出错都退回上一步重跑，不用从头来。抽帧清单里每张图都带来源录包名与帧号，出现争议时能回到原视频逐帧对。

标注质检两条。其一，抽检复标，同一个人隔开时间标两遍，或者两个人标同一批，比对框位置，差异大的图退回重标，差异率记进版本说明。其二，模型误检回收，训练出模型之后把误检的图收进负样本，或者补标准确框，直接变成下一版数据集的输入。

数据集版本三件套：数据文件，清单文件，版本说明。版本说明写新增多少图，来自哪些场景，修了哪些标注问题。训练记录表把模型权重与数据集版本绑在一起，某版模型用哪版数据训的，指标在哪一档，表上查一行就有答案。模型指标回头看时，先核数据版本，再谈调参。

标定表与数据集版本一一对应，标定表改一个数，依赖它算出的距离标签全部受影响，改表要同步重算，重算产物进新版本目录，不就地覆盖。

## Git 与 Git LFS

代码进 Git，分支，提交，标签，改坏了随时退回旧版。点云包，模型权重，视频这些大文件进 Git LFS，仓库里只存指针。.gitignore 挡住编译产物，临时日志，录包目录。提交前看一眼 git status，确认没有不该传的内容。历史里混进过大文件的仓库，清历史要趁早，赛前不要安排这件事。

LFS 规则在仓库建起来的那一天就登记，比事后迁移省事。命令序列：先启用 LFS，登记大文件类型，再写忽略清单，最后确认状态再提交。

```bash
# 进阶档: 启用 Git LFS 并登记大文件类型
git lfs install
git lfs track "*.pcd"
git lfs track "*.bag"
git lfs track "*.db3"
git lfs track "*.mcap"
git lfs track "*.onnx"
git lfs track "*.engine"
git add .gitattributes

# .gitignore 示例: 产物与临时文件挡在仓库外
cat > .gitignore <<'EOF'
build/
install/
log/
__pycache__/
*.tmp
*.log
.vscode/
EOF

# 提交前检查, 确认大文件走了指针
git status
git lfs ls-files
git add .
git commit -m "添加 LFS 规则与忽略清单"
git push
```

关键行四处。git lfs track 生成的 .gitattributes 必须提交，队友拉下仓库才拿到同样的规则，这一行最容易漏。.gitignore 一次写全，赛前再改属于高风险动作，改完要全队同步。git status 是提交前的固定动作，查有没有意外文件进来。git lfs ls-files 确认大文件真走了指针，普通方式加进来的大文件要到 push 才报错，那时清理已经麻烦。

队友侧还有一条环境纪律：没装 LFS 客户端的机器拉仓库，指针文件会被当成正文收下来，打开只有几行文本，数据看着像坏了，其实是环境没配好。新机器上车的流程里把 LFS 安装列为第一步。

仓库分家的策略：代码仓库保持小，录包与数据集放服务器和移动盘，仓库里只留清单与版本说明。LFS 有配额，批量上传大文件之前先在队群打招呼，避免把配额用满。清历史要用重写工具，涉及所有人重新克隆，这个操作排在赛季之外的维护窗口里。

## 命名与目录规范

文件名和目录名让人一眼看懂时间和内容。日期前缀，不用猜。一车一套参，R1 还是 R2 写进路径。同名不同版本用版本号隔开，改版不覆盖旧版，现场退回旧版接得上。目录深度控制在三层以内，更深的路径很少有人逐个点开。这套规范执行起来显得繁琐，但现场排查时能最快定位到文件。

命名模板三段：日期，对象，内容，版本号跟在最后。日期用 20250706 这种无分隔格式，排序就是时间线。对象写车号或模块，内容写数据种类。示例：20250706_R1_lidar_map_v3.pcd，20250706_R2_ball_dataset_v2.zip。不点开文件，从名字上就能判断该用哪一份。

版本留存按一条纪律执行：每次改版标日期和改动点。机械改了零件没说，电控照着旧图写完的控制参数全要重来，这类事靠一份改版记录就能避免。记录放仓库 docs 目录，改版当天更新，不攒到赛后。

目录结构固定几块：源码，配置，脚本，文档，数据挂载点。数据不进源码仓库，用挂载或软链接指到数据盘。配置按车分子目录，公共部分单独一层，覆盖关系写进 README，两车参数不混用。

## 备份与恢复

备份三份：车上，移动盘，队里的服务器。赛前把能镜像的全镜像，系统盘做整盘镜像，参数文件每日一存。备份是否可用要靠恢复演练确认，平时演练一次从烧盘到跑通自检的全流程。全队数据只认仓库和备份，U 盘里只放副本，不把唯一的文件放在 U 盘。

介质分开摆：车上留一份，服务器一份，移动盘一份，移动盘随队走。服务器侧做每日同步，同步脚本只增不删，误删的文件还能从服务器捞回来。镜像文件连同校验和归档，恢复时先校验再烧写。

恢复演练的内容：从镜像烧盘，起系统，跑自检，拉参数，通链路，按比赛前的开机流程走一遍，记卡表。演练暴露的问题经常不在备份文件本身，在恢复步骤的描述上，步骤描述改完再演一次。换介质或换机器之后补演一轮，把结论更新到演练记录里。

日常校验的做法：备份完对目录算一次校验和清单，恢复后比对，确认文件没有损坏。录包这类大文件按目录级清单管，不逐个人工点。

## 几条小结

- 数据平时不显眼，丢失之后的恢复代价很高。
- 标注一致性比标注数量重要。
- 仓库管理提前做好，联调阶段能省下大量协调时间。
- 备份要经过恢复演练才算可用。
