# 第 9 章 通信协议设计实战

> 双车联调第一晚，两边日志的时间差了 300 毫秒，传球指令发出去，接球车没有响应。排查到半夜，发现两边系统时间没有对齐。

## 串口帧格式

上位机到 STM32 的 UART 链路，帧结构用成熟的做法，我们当时用的是这一种。

- **帧头**：两个字节，比如 0xAA 0x55。接收端状态机靠它对齐字节流。
- **长度**：一个字节，载荷的字节数。
- **序号**：一个字节，同方向发送时递增，接收端拿它做去重与丢帧统计。
- **载荷**：定长结构体，字段顺序，单位，缩放系数写进接口文档。
- **校验**：CRC16，覆盖长度，序号与载荷。校验不过直接丢，不回调。
- **帧尾**：可以留一个字节，也可以省，接收端靠长度收满即出。

六个字段各自有存在的理由。帧头给了两个字节，单字节的误对齐概率是 1/256，双字节把这个基线拉到 1/65536，再叠一层 CRC16，误收的概率压到可以忽略。长度一字节，载荷上限锁在 255 字节以内，STM32 端的接收缓冲按这个量级设计，两端对齐。序号一字节，回绕周期 256 帧，接收端的去重窗口记住最近十来个序号就够用。CRC16 能检出全部单比特与双比特错误，对突发错误的检出率也高，计算量在 STM32 上可以忽略，比简单的累加和强得多。帧尾可以省，长度收满本身就是定界动作，省掉一个字节，也少一处误判源。

载荷用定长结构体，不用变长编码。定长解析简单，收发两端照同一份字段表写死，解析开销归零，出错的地方只剩字段对齐。字节序在文档里写明，全车统一。浮点数不要直接进帧，两端的浮点实现不保证逐位一致，涉及小数的一律转定点整数再传，比如角度按 0.1 度一格，距离按毫米一格，缩放系数跟在字段说明后面。方向性参数在接收端加限幅，超范围的先夹到边界再进执行器，一帧写错的参数顶多让动作迟钝一点，不会让机构过冲。

解析用环形缓冲区加状态机：在缓存里找帧头，找不到就把最老的字节扔掉，找到后按长度收满再做校验。这个写法在半包，粘包，乱码三种情况同时出现的时候都能稳定处理。

解析器的骨架值得贴出来，它是全车所有串口链路的共同底座。

```c
/* 串口收帧：环形缓冲加状态机，粘包半包都按帧头重新对齐 */
#define RB_SIZE 512                        /* 容量取 2 的幂，取模用位与 */
static uint8_t rb[RB_SIZE];
static volatile uint16_t head, tail;       /* 中断侧写 head，主循环读 tail */

void uart_isr(uint8_t b) {                 /* 中断只做入缓冲 */
    uint16_t next = (head + 1) & (RB_SIZE - 1);
    if (next != tail) { rb[head] = b; head = next; }  /* 满则丢新字节 */
}

typedef enum { H0, H1, LEN, NUM, DATA, CRC0, CRC1 } state_t;
#define PAYLOAD_MAX 64
static state_t st = H0;
static uint8_t len, num, buf[PAYLOAD_MAX], idx, crc_lo;

static void feed(uint8_t b) {
    switch (st) {
    case H0:   if (b == 0xAA) st = H1;                       break;
    case H1:   if (b == 0x55) st = LEN;
               else st = (b == 0xAA) ? H1 : H0;              break;
    case LEN:  if (b == 0 || b > PAYLOAD_MAX) { st = H0; break; }
               len = b; st = NUM;                            break;
    case NUM:  num = b; idx = 0; st = DATA;                  break;
    case DATA: buf[idx++] = b; if (idx >= len) st = CRC0;    break;
    case CRC0: crc_lo = b; st = CRC1;                        break;
    case CRC1: {
        uint16_t rx = (uint16_t)((b << 8) | crc_lo);           /* 低字节在前 */
        if (rx == crc16(len, num, buf)) dispatch(num, buf, len);
        st = H0;                                             break;
    }
    }
}

void rx_poll(void) {                       /* 主循环周期调用 */
    while (head != tail) {
        feed(rb[tail]);
        tail = (tail + 1) & (RB_SIZE - 1);
    }
}
```

对照几行关键的。中断侧只有入缓冲一件事，写指针前进，满了丢新字节，具体丢新还是丢旧在队内统一之后不许两头混用。H0 到 LEN 三个状态负责对齐，乱码段里任何字节只有当它等于 0xAA 时才有资格进入 H1，H1 里遇到的字节不是 0x55 就回到起点，是 0x55 进 LEN，恰好又碰到 0xAA 就停在 H1 等下一个字节，这个分支覆盖了双帧头尾首相连的字节流。长度校验把零长度和超缓冲的帧当场拒掉，这两个值出现就说明对齐错了，不必继续。

DATA 状态收满长度就进校验，粘包因此自然消化，剩下的字节回头从 H0 继续找帧头。半包由静态状态变量跨调用保留，这次收一半，下次接着收。CRC 对不上，当前帧丢弃，回到找帧头，不回溯重扫已经消费的字节，理论上数据区里可能藏着下一帧的帧头，代价是等下一个帧头才能重新对齐，概率很低，换来的是实现短，可测，跑一小时异常字节流不崩。

单位与缩放要写死：角度用度还是弧度，速度用 rpm 还是 rad/s，文档里定死，上下位机各写一份解析代码，联调前先对表。一次教训：单位混用，上位机发米每秒，下位机按厘米每秒执行，车直接冲了出去。

## 先挂号后发指令

双车无线的确认与重发，做成独立的一层，业务层不碰链路细节。

发送端先把指令放进待确认队列：带序号，带有效期，然后才发出去。接收端执行并回确认帧，确认到了，发送端才从队列销号。有效期过了就撤单，业务层收到失败通知，由它决定降级还是重试。

状态机四态：空闲，已发待确认，确认收到，失败。重发不超过 3 次，重发的帧带同样的序号，接收端见过这个序号就丢弃，执行过一次的指令不会执行第二次。

四态的转移与动作各归各位。空闲态收到业务层的发送请求，挂号进队列，帧发出去，进已发待确认。确认帧到，销号，通知业务层成功。定时器发现超过判定间隔还没确认，重发，留在已发待确认。重发次数到上限，或者过了有效期，进失败，通知业务层。业务层收到的只有成功与失败两种结局，中间的等待，重发，去重都在链路层内部消化。去重窗口的大小要覆盖一次任务里可能同时在途的序号数，窗口开小了，最早的序号被挤出去，重发的帧会被当成新指令执行第二次，这类错误在双车配合里代价很大。超时判定间隔要大于一次往返时间加抖动，定小了，正常在途的帧被当成丢失，重发帧把信道灌满。

核心逻辑的代码骨架如下，三个约束都在里面：序号去重，超时重发上限 3 次，有效期作废。

```c
/* 挂号重发：序号去重，超时重发上限 3 次，有效期到点作废 */
typedef struct {
    uint8_t  seq;               /* 指令序号，同方向递增 */
    uint32_t t_send, t_expire;  /* 最近发送时刻，有效期截止时刻 */
    uint8_t  retry, payload[16], used;
} pending_t;
static pending_t q[8];          /* 待确认队列，深度按参数表配 */
static uint16_t seen;           /* 接收侧去重位图，记最近 16 个序号 */

void cmd_tick(uint32_t now_ms) {           /* 主循环周期调用 */
    for (int i = 0; i < 8; i++) {
        pending_t *p = &q[i];
        if (!p->used) continue;
        if (now_ms > p->t_expire) {        /* 过期，作废并上报 */
            p->used = 0; on_cmd_failed(p->seq); continue;
        }
        if (now_ms - p->t_send <= 100) continue;   /* 重发判定间隔 */
        if (p->retry >= 3) {               /* 重发上限 3 次 */
            p->used = 0; on_cmd_failed(p->seq); continue;
        }
        p->retry++;
        p->t_send = now_ms;
        send_frame(p->seq, p->payload);    /* 同一序号重发 */
    }
}

void on_ack(uint8_t seq) {                 /* 确认到，销号 */
    for (int i = 0; i < 8; i++)
        if (q[i].used && q[i].seq == seq) { q[i].used = 0; return; }
}

bool rx_first_time(uint8_t seq) {          /* 去重：滑动窗口，只记最近 16 个序号 */
    static uint8_t  base = 0;              /* 窗口下沿序号 */
    static uint16_t seen = 0;
    uint8_t diff = (uint8_t)(seq - base);
    if (diff >= 16) {                      /* 序号走出窗口，整窗滑到新位置 */
        base = (uint8_t)(seq - 15);
        seen = 0x8000;                     /* 只保留当前这个序号 */
        return true;
    }
    uint16_t bit = (uint16_t)(1u << diff);
    if (seen & bit) return false;
    seen |= bit;
    return true;
}
/* 接收流程：if (rx_first_time(seq)) execute(payload); 然后照常回 ACK */
```

对照关键行。待确认队列里的每条记录带四个字段：序号，最近发送时刻，有效期截止时刻，已重发次数，业务层挂号时填好，tick 只管维护。过期检查放在重发检查前面，优先级更高，一条指令快到有效期了，即使重发次数没用完也不再发，避免指令到对端时已经失去时效。重发判定间隔的示例值是 100 毫秒，具体数值进参数表，原则是大于一次往返时间加抖动。重发上限 3 次是取舍，连续丢包说明链路进了坏窗口，硬重发救不回来，把信道让给心跳和急停更值钱。on_ack 找到对应序号销号，业务层收到成功。去重位图记住最近 16 个序号，窗口跟着最新序号滑动，滑出窗口的旧位整批清掉，序号绕一轮以上，重复帧识别依然有效。重复帧直接丢弃，注意重复帧的确认照回，不回确认的话发送端会一路重发到上限，然后把一次成功送达的指令报成失败。

## ESP-NOW 五机制

ESP-NOW 是 2.4 吉赫兹无连接传输，单包上限 250 字节，链路本身尽力而为，可靠性全靠应用层这五个机制。

- **心跳报活**：我们当时的设置是 20 赫兹，50 毫秒一帧，包很小，报活与状态位。300 毫秒收不到心跳，判定链路断，进安全降级，底盘限速，等待恢复，心跳连续回来若干帧之后自动回正常档。
- **应答确认**：指令带序号进待确认队列，接收端执行后回确认帧，超时重发，重发不超过 3 次，重发不重复执行。
- **消息去重**：接收端记住最近处理过的序号，重复帧直接丢弃，确认照回。
- **超时过期**：每条指令带有效期，过期即作废，不执行。
- **紧急急停**：最高优先级，锁存加人工复位。收到急停立刻执行并锁住，对方心跳恢复也保持锁住，按复位键才解开。

心跳的带宽账先算清。一帧几十字节，50 毫秒一帧，占用远小于链路的可用带宽，换来的是每秒 20 次的链路采样，车一动起来，链路质量的变化几分钟内就能看出来。300 毫秒的判定窗口大约等于 6 个心跳周期，容忍连续丢几帧，又不至于让降级进来得太晚。这个窗口开大一点，降级迟钝，开小一点，场馆里正常的突发干扰就会反复触发降级，车走走停停。降级期间的行为要写死：底盘限速，发射联锁挂起，等待恢复，恢复条件写成明确判定，比如心跳连续回来若干帧才算恢复，避免链路在临界状态上反复横跳。恢复之后自动回正常档，不需要人工重新上电。

重发的设计里，序号是去重与统计两件事共用的钥匙。帧头之外再放一个任务标识，重发的帧与原帧完全一致，接收端见过的序号直接丢弃，执行过一次的指令不会执行第二次。跳过的序号也是信息，序号不连续说明中间丢过帧，丢帧率进日志，联调时先看这个曲线。急停走独立通道，不排队，不重发，锁存加人工复位，对方心跳恢复也保持锁住，按复位键才解开。这五个机制在协议文档里各占一节，新人接手时只加字段，不改机制。

## 时间同步

双车时钟对齐的做法：主车周期发对时帧，从车收到立刻回环，主车取往返时间的一半做偏移估计，多点平均之后供业务使用。软同步的精度受发送抖动限制，所以控制层的做法是显式携带时间信息：指令带发送时刻与有效期，接收端按本地时基换算执行窗口。

抖动来自排队和中断延迟，平均能压掉一部分，压不掉尾部。所以对时服务于日志对齐与数据统计，控制时效一律由有效期兜底：指令的时间戳只用来判断新旧，执行窗口按接收时刻加上有效期来算，两边的时钟差一些，业务逻辑不受影响。第一版不是这么做的，执行窗口卡在绝对时间上，时钟差了 300 毫秒，指令到手时窗口已经错过，接球车没有响应就是这么来的，改成按接收时基算窗口之后不再发生。

验证口径：急转弯工况跑一遍。角速度 180 度每秒时，10 毫秒偏差约等于 1.8 度旋转错位，这个偏差在双车配合里会被放大。

## CAN 报文设计

STM32 到电机的 CAN 是另一套设计。3508 用标准帧，ID 里带电机编号与功能位。控制帧固定周期发，反馈帧按 ID 解析。达妙电机的 MIT 模式帧结构按厂商文档来，不要自行发明。设计纪律：ID 划分先画表，谁用哪段写进文档，避免两个功能号段冲突。

ID 表画的时候给未来留余量：电机控制一段，状态反馈一段，参数配置一段，每段按电机的最大编号留空位。控制帧固定节拍发，不随事件突发，总线负载平稳，急停与参数帧才有插进来的空间。达妙电机的 MIT 模式先在单电机上跑通厂商例程，再接进整车，帧结构一个字都不改。

## 协议测试

三件套：丢包注入，延迟注入，异常帧注入。

- 丢包：故意丢一部分包，看重发与降级是否按设计走。
- 延迟：人为加延迟，看超时逻辑的边界。
- 异常帧：往解析器里灌随机字节流，跑一小时不崩溃，才算过关。

实现方式：丢包注入放在收发中间层，拦截一部分帧丢掉，比例可调，从百分之一到三成，分级测。延迟注入把帧放进延迟队列，滞后一段时间再放行，专门压超时逻辑的边界，延迟值卡在判定间隔的上下两侧各测一轮。异常帧注入往解析器直接灌随机字节流与半截帧，看解析器会不会错过真正的帧，看缓冲区会不会溢出，跑一小时不崩才算过关。第三样平时用不上，出一次就是事故。

验收那天，把车摆到场上，两边对着跑半小时，丢包率与恢复时间记进日志。通过条件写进赛前预检。
