# 第 26 章 数据结构与算法：赛队应用版

> 训练赛复盘时发现串口偶尔丢整帧，波特率没错，帧头也认得出。查到收包那一段，发现读写位置重叠，一帧数据被覆盖掉半截。那天之后，串口收包统一换成环形缓冲区。

## 环形缓冲区：串口收包的标准做法

串口每来一个字节进一次中断。中断只管把字节塞进环形缓冲区，头指针写，尾指针读，绕圈靠位掩码取模。生产者快，消费者慢，两边互不阻塞，这个结构适合中断加主循环的组合。要点记三条。容量定长，取两的幂方便取模。指针两边都在动，该 volatile 就 volatile。写满策略提前定死，丢新留旧还是丢旧留新，全队统一。无线收包同样适用这套结构。

开头那次丢帧，先用代码讲透。最朴素的收包写法，是一个数组一路往后写。

```c
// 基础写法：数组累积，记录当前长度
#define FRAME_MAX 64
static uint8_t  rx_buf[FRAME_MAX];
static uint16_t rx_len = 0;

void uart_rx_isr(uint8_t byte)
{
    rx_buf[rx_len++] = byte;
    if (rx_len >= FRAME_MAX)
        rx_len = 0;            // 写满从头开始，旧数据被直接覆盖
}
```

这段写法在处理速度跟得上时看不出问题。车一跑起来，主循环被其他任务占住几十毫秒，新字节从数组头部重新写入，把还没取走的整帧覆盖半截，就是我们训练赛遇到的那次丢帧。问题出在结构上：读写位置没有分家，写方不知道读方取到哪了。

```c
// 进阶写法：环形缓冲区，中断写，主循环读
#define RING_SIZE 256            // 容量取 2 的幂
#define RING_MASK (RING_SIZE - 1)
static volatile uint8_t  ring[RING_SIZE];
static volatile uint16_t head = 0;   // 中断里推进
static volatile uint16_t tail = 0;   // 主循环里推进

void uart_rx_isr(uint8_t byte)
{
    uint16_t next = (head + 1) & RING_MASK;
    if (next != tail) {              // 留一格空位，区分满与空
        ring[head] = byte;
        head = next;
    }                                // 满了丢新留旧，按约定执行
}

int ring_get(uint8_t *out)
{
    if (head == tail)
        return 0;                    // 空
    *out = ring[tail];
    tail = (tail + 1) & RING_MASK;
    return 1;
}
```

关键行四处。容量取 2 的幂，取模换成位与，中断里的开销降到一条指令。头部不会追上尾部，差一格就判满，满和空的判断条件不会混。head 与 tail 一个在中断里动，一个在主循环里动，各动各的，这个结构天然免锁，前提出在单生产者单消费者这一条上，多来源写入就另说。满了怎么办按约定走，我们定的是丢新留旧，旧数据是上位机要的完整帧，新数据丢了下一帧还会来。

取样频率和缓冲深度的账要提前算。高频数据流按最坏情况估，最长的处理停顿乘上字节速率，就是缓冲的最小深度，留出一倍余量。第 9 章那套帧解析状态机，吃进去的字节就来自这个结构，缓冲区稳了，解析层才有稳定的输入。

## 队列与事件

状态机处理的是一串事件，队列用于按顺序存放这些事件。谁产生谁入队，决策层按序取用。急停这类高优先级事件走独立通道，或者直接置标志位，优先于其他所有事件。指令队列带序号去重，重发进来的旧指令先查序号，执行过就丢弃。队列深度不要设得太大，积压的事件宁可标记过期，也不要延迟执行。

事件队列的写法与环形缓冲同源，只是装的从字节变成结构体。

```c
// 进阶写法：事件队列，急停走独立标志
#define EVT_QUEUE_MAX 16
typedef struct {
    uint8_t  type;
    uint16_t seq;
} event_t;

static volatile uint8_t estop_flag = 0;   // 急停永远走标志位
static event_t evt_q[EVT_QUEUE_MAX];
static volatile uint8_t evt_head = 0, evt_tail = 0;

void push_event(uint8_t type, uint16_t seq)
{
    uint8_t next = (evt_head + 1) % EVT_QUEUE_MAX;
    if (next == evt_tail)
        return;                           // 队列满：丢弃新事件，防积压
    evt_q[evt_head].type = type;
    evt_q[evt_head].seq  = seq;
    evt_head = next;
}

int pop_event(event_t *out)
{
    if (estop_flag) {                     // 急停优先，先于一切排队事件
        out->type = EVT_ESTOP;
        out->seq  = 0;
        return 1;                         // 标志保持锁存，等人工复位流程清除
    }
    if (evt_head == evt_tail)
        return 0;                         // 空
    *out = evt_q[evt_tail];
    evt_tail = (evt_tail + 1) % EVT_QUEUE_MAX;
    return 1;
}
```

三处设计值得对照。急停不进队列，走独立标志，任何时刻取出即处理，排队顺序对它无效。队列满时丢弃新事件，让已经排队的尽快被处理，超时的由有效期机制作废，这套规则和指令链路一致。结构体里带序号，去重逻辑在协议层做，队列只负责顺序，两层各管一件事。

队列深度按最坏积压估。决策循环一拍处理一条事件，出一波连续事件时，队列长度要覆盖一次突发。深度定死之后写进参数表，改动走记录。

## 图与最短路：取球顺序

场上的球位和关键点画成一张图，两两之间的行驶距离当边权，取球顺序就变成一个最短路问题。球少的时候直接枚举所有顺序，挑总路程最短的那条，实现只要几分钟。球多了改用贪心，每次走最近的，工程上够用。障碍和对方车的位置一变，边权跟着变，图重算。场地导航里的 A 星是同源思路，只是节点换成了任务点。

两版写法都短，差别在代价与效果。

```python
# 进阶写法：取球顺序，枚举与贪心两版
import itertools

def best_enum(start, balls, dist):
    best, best_order = None, None
    for order in itertools.permutations(balls):
        cur, total = start, 0
        for b in order:
            total += dist[cur][b]
            cur = b
        if best is None or total < best:
            best, best_order = total, order
    return best_order, best

def best_greedy(start, balls, dist):
    cur, order, total = start, [], 0
    rest = list(balls)
    while rest:
        nxt = min(rest, key=lambda b: dist[cur][b])   # 每步就近
        total += dist[cur][nxt]
        order.append(nxt)
        rest.remove(nxt)
        cur = nxt
    return order, total
```

枚举版把全排列走一遍，五个球 120 条路线，毫秒级跑完，结果保证最短。球再多几个，路线按阶乘涨到几千几万条，这份开销就进不了在线循环。贪心版每步选最近的球，复杂度是平方级，秒出结果，但不保证全局最短，就近一步偶尔会把路线绕长。现场的取舍是球少走枚举，球多走贪心，贪心结果再用一次局部交换做修补，两条路线交换位置能变短就换。

边权重算的时机也固定。球位来自视觉，位置一变就重算对应几条边，全部重算在小规模下也就几十次浮点运算，不值得为它做增量结构。球图这种做法还有个好处，任务层拿到的是顺序列表，车怎么走交给局部控制，两层各管一件事。

## 滑动窗口与滤波

视觉确认目标用连续多帧的窗口，置信度够，位置稳，窗口内一致，三条全过才算数。雷达测距抖，滑动平均压噪声，代价是延迟，窗口越长越平滑也越迟钝，窗口长度要对着延迟预算算。中值滤波用于去除离群点，窗口里排个序取中间值。采样快了窗口能短，采样慢了只能用平滑换稳定。

窗口的账用例子说清。相机 120 赫兹出图，5 帧窗口对应 40 毫秒上下，够滤掉单帧的检测抖动，这个延迟在投篮链路里可以接受。窗口拉到 15 帧，平滑度上去了，120 多毫秒的延迟会顶到发射时序上。先算延迟预算，再定窗口长度，顺序不能反。

两个滤波器往往串着用。先中值后平均，中值把野点剔掉，平均再压高频抖动。反过来先平均，野点会被摊进整段窗口，中值再取也救不回来。滤波顺序的教训是，先把顺序调对，再定窗口长度，调序比调参见效快。

实现上不需要新结构。读数先进环形缓冲，求平均是把窗口内元素加起来除以个数，求中值是复制一份窗口排序取中间，窗口长度取奇数，中值才落在正中间。一帧图像几十毫秒的控制链路里，这两个操作的开销都可以忽略。

## 复杂度与实时预算

控制环一个周期就几毫秒，这个预算里不许出现排序，内存分配，文件读写。一个操作能不能放进环里，看的是最坏耗时，平均耗时不能作依据。规模小的时候 O(n²) 和 O(n log n) 差不出多少，先测量再优化。优化之前先定位，把工作放在占比最大的函数上。

几个常被低估的开销点。浮点除法和三角函数在没有硬件加速的小片子上是几十个周期起步，能查表就查表，能移位就移位。动态内存分配进不了环里，理由在上一章讲过。打印也进不了环里，格式化字符串的开销远大于运算本身。这些账不用背，把最坏耗时测出来贴到预算表旁边，每次改动对着看。

测量本身也有纪律。函数耗时用 GPIO 翻转加示波器来量，比在代码里插打印可信，插桩本身就会改变节拍。同一段代码在实验室和满负载工况下的最坏值可能差出一截，预算按满负载的记。

## 几条小结

- 数据结构选对之后，代码量会明显下降。
- 缓冲区溢出不会当场报错，它会直接改写相邻的数据。
- 延迟按最坏情况记录，平均值会误导判断。
- 复杂度落在控制环里，表现出来就是电机节拍的抖动，控制环里只看最坏耗时。
- 读写分家是缓冲结构的第一步，剩下的是容量，满了怎么办，谁写谁读这三件事。
