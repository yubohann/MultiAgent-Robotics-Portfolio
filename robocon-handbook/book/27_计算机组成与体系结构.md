# 第 27 章 计算机组成与体系结构

> 上位机发速度指令，代码里一个 int 直接塞进字节数组就发往串口。STM32 那头解出的数值完全不对，电机满转，车原地转圈。查了一晚上，问题出在这个 int 跨字节边界的拼法上，两边对同一段字节的理解对不上。修好之后，所有跨设备字段都改成按字节手写。

第 25 章开头给出了 25 到 31 章的代码进阶路线，代码按三档推进：基础档先写对，进阶档写稳，再往上写快。这一章围着上下位机交界处展开，三段代码分别落在基础档与进阶档，每段先讲它解决什么问题，再对照关键行。

## 整数的表示

一个字节八位，能表示 256 种状态，十六进制两位就写得完。同样的 0xFF，按无符号读是 255，按补码读是负 1。补码的规则是取反加一，好处是加减法不用区分符号，硬件一套加法器通吃。这类读法差异在赛场上有实际后果：速度指令按有符号发出，接收端按无符号解，负速度会变成几万的巨大正数，车满速冲出去。int16 的范围是负 32768 到正 32767，越界回绕，32767 加一直接变负 32768，电机指令瞬间反向，这也是收包之后先限幅的原因之一。

位操作是每天都要做的事：置位用或，清位用与上取反的掩码，取某几位先右移再与掩码。STM32 里配 GPIO 和寄存器就是这几个基本动作。协议字段在文档里除了单位，还要写符号性与取值范围，负速度是有符号数的合法值，计数才有回绕语义，两种读法先定死，编码才不容易错。

## 字节序

多字节数字在内存里的排布有大小端之分。x86 和 ARM 日常用小端，网络协议习惯大端。一边按小端拼，另一边按大端解，数字就完全错了。规矩简单：跨设备传输不直接发送结构体，字段逐个序列化成字节，协议文档写死字节序。速度指令和转速回传，每个字段都按文档拼装，拼完写个小测试验一遍。

先看内存里发生了什么。数值 0x12345678 存进内存，小端机器低地址放低字节 78 56 34 12，大端机器低地址放高字节 12 34 56 78。Cortex-M 系列默认小端，但这条纪律不靠平台兜底：平台换一代，编译参数改一次，默认行为不保证跟着走，可靠的做法是协议写死加手写拼装，两个动作各管一半。

下面是这段的基础写法，把一帧速度指令按字节拼出来，五段式格式与第 9 章一致，帧头 0xAA 0x55，长度，序号，载荷，CRC16。载荷是两个字段，速度按毫米每秒用 int16 装，角度按 0.1 度一格用 int16 装，多字节字段小端在前。

```c
/* 基础写法: 上位机到 STM32 的速度帧, 五段式, 逐字节手写拼装
   载荷: 速度 int16 毫米每秒, 角度 int16 0.1 度, 多字节小端在前 */
#include <stdint.h>

static uint8_t frame[16];
static uint8_t seq = 0;

uint8_t build_speed_frame(int16_t speed, int16_t angle)
{
    uint16_t v = (uint16_t)speed;      /* 先转无符号, 避开负数右移的不确定性 */
    uint16_t a = (uint16_t)angle;
    uint8_t  payload[4];
    uint8_t  n = 0;

    payload[0] = (uint8_t)(v & 0xFF);  /* 速度低字节 */
    payload[1] = (uint8_t)(v >> 8);    /* 速度高字节 */
    payload[2] = (uint8_t)(a & 0xFF);  /* 角度低字节 */
    payload[3] = (uint8_t)(a >> 8);

    frame[n++] = 0xAA;                 /* 帧头两字节 */
    frame[n++] = 0x55;
    frame[n++] = 4;                    /* 载荷长度, 字节数 */
    frame[n++] = seq;                  /* 序号, 去重与丢帧统计共用 */

    for (uint8_t i = 0; i < 4; i++)
        frame[n++] = payload[i];

    uint16_t crc = crc16(4, seq, payload);  /* 与第 9 章同签名的校验函数 */
    frame[n++] = (uint8_t)(crc & 0xFF);     /* CRC16 小端, 低字节在前 */
    frame[n++] = (uint8_t)(crc >> 8);

    seq++;                             /* 下一帧换新序号 */
    return n;                          /* 返回整帧长度, 交给发送 */
}
```

对照关键行。两个量先转成 uint16_t 再拆字节，因为对负数做右移在 C 语言里由实现决定，先转无符号就绕开了这条不确定性。低字节用与 0xFF 取，高字节右移八位，这就是小端排法，协议若定大端，两行对调，出错的情形只有一种：两端按不同的排法理解同一段字节。长度字段写的是载荷字节数，序号在计算校验之前先落地。CRC16 的调用签名与第 9 章收包状态机用的是同一个函数，覆盖长度，序号与载荷，校验值本身也按小端跟随。拼完的自检用例：发速度负 500，负 500 的补码是 0xFE0C，帧里应当出现 0C FE 两个字节，位置在序号之后。这个用例进单元测试，改协议时先跑它。

## 结构体对齐

编译器为了访问效率会对结构体做对齐，char 后面跟 int，中间插入几个填充字节，sizeof 出来的长度大于字段之和。串口帧按 sizeof 发出去，两边对齐策略一不一致，字段全错位。收发帧的结构体加打包属性，或者干脆不用结构体，手动按字节写。在上位机和 MCU 的交界处把这些规则执行到位，后面的调试会省很多事。

机制的细节值得看清楚。CPU 读内存按字长访问，把一个 uint16_t 放在偶数地址上，一条指令就取到，放在奇数地址上，有的内核要两条指令拼，有的内核直接触发硬件异常。编译器为了绕开这件事，让每个成员落在自身大小的整数倍地址上，不够就插填充字节，结构体总大小再向上取到最大成员对齐的倍数。这套规则是编译器默认，换编译器，换优化等级，换平台都可能变。

上面的基础档已经手写字节，不走结构体直发这条路。下面这段进阶内容回答一个常见的想法：字段少的帧直接用结构体加打包属性发出去，更省事。用一段对照实验先看清代价。

```c
/* 进阶档的反例：对齐陷阱对照实验
   同一组字段两种声明, sizeof 与成员偏移都不同 */
#include <stdint.h>
#include <stddef.h>
#include <stdio.h>

struct frame_a {                  /* 默认对齐: 编译器按需插填充字节 */
    uint8_t  head;                /* 偏移 0 */
    uint16_t speed;               /* 对齐到 2, 实际偏移 2 */
    uint16_t angle;               /* 偏移 4 */
    uint8_t  crc;                 /* 偏移 6, 末尾再补 1 字节 */
};

struct __attribute__((packed)) frame_b {  /* 打包: 不许插填充 */
    uint8_t  head;
    uint16_t speed;
    uint16_t angle;
    uint8_t  crc;
};

int main(void)
{
    printf("A sizeof=%zu off_speed=%zu\n",
           sizeof(struct frame_a), offsetof(struct frame_a, speed));
    printf("B sizeof=%zu\n", sizeof(struct frame_b));
    return 0;
}
/* 常见输出: A sizeof=8 off_speed=2, B sizeof=6 */
```

这段程序的常见输出是 A 结构体 8 字节，speed 偏移 2，B 结构体 6 字节。A 里 head 之后插了一个填充字节，crc 之后又补了一个，8 是这么来的。B 打了打包属性，没有任何填充，6 字节严丝合缝，代价是成员可能落在非对齐地址上，处理器取 speed 时要么多花指令，要么直接进异常，行为随内核而变。工具链的打包写法还不统一，gcc 与 clang 写 __attribute__((packed))，Keil 写 __packed 或用 #pragma pack(1)，两端用了不同写法，同一个结构体的偏移就不同。

从基础档迈向进阶档，改掉的是捷径本身：帧长不用 sizeof 现算，字段偏移不用 offsetof 现推，一切以协议表为准。跨设备的帧不传结构体，发送端手写字节，接收端逐字节解析，结构体只留在各自的内存里，收到之后再把字段填进去。这条纪律执行到位，后面每一轮联调都少一类错位问题。

## 浮点与定点

float 按 IEEE 754 存，符号位，指数位，尾数位。MCU 的 FPU 通常单精度快，双精度慢，中断里做 double 运算会拖节拍。没有 FPU 的小片子上用定点数，小数放大成整数来算，省算力。传输浮点字段同样要约定格式，两端的二进制排布不会自动一致。

单精度的构成再具体一点：1 位符号，8 位指数，23 位尾数，约 7 位十进制有效数字。二进制浮点表示不了多数十进制小数，0.1 存进去是 0.100000001 这样的近似值，累加几千次之后偏差显出来。所以协议里不传浮点，角度按 0.1 度一格，距离按毫米一格，小数在上位机侧就换算成整数，这条在第 9 章的帧格式里已经写死。

定点数的记法是 Q 格式，Q15 指 15 位小数位，数值范围是负 1 到接近正 1，单位是 1/32768。下面是这段的进阶写法，把参与控制计算的小数提前转成定点，控制环里全程整数，浮点运算只剩入口处的一次换算。

```c
/* 进阶写法: 浮点转定点参与控制计算, 环内全程整数
   Q15: 1 位符号 + 15 位小数, 单位是 1/32768 */
#include <stdint.h>

#define KP_Q15 11469                 /* 0.35 x 32768, 编译期算好 */

static int16_t err_q15;
static int16_t out_q15;

void on_error(float err_norm)        /* 输入已归一化到 -1 到 1 */
{
    float x = err_norm;
    if (x > 0.99997f) x = 0.99997f;  /* 饱和, 防止绕回 */
    if (x < -1.0f)    x = -1.0f;

    err_q15 = (int16_t)(x * 32768.0f);        /* 小数放大 2 的 15 次方取整 */
    int32_t t = (int32_t)KP_Q15 * err_q15;    /* 乘积用 32 位装, 否则溢出 */
    out_q15 = (int16_t)(t >> 15);             /* 右移 15 位还原比例 */
}
```

对照关键行。增益 0.35 乘 32768 是 11468.8，写成常量 11469 由编译器在编译期算好，运行时不花时间。入口两行饱和是必写的，误差一旦超出范围，不饱和就会绕回成反号的小数，控制瞬间反向。换算用乘 32768 再取整，误差最多一格，控制上可以接受，要更准可以在移位前加半格再取整。乘法把两个 int16 先升到 int32 再乘，直接以 int16 相乘会溢出，乘积右移 15 位还原比例。负数右移依赖的是算术右移，gcc 与 Keil 都这么处理，换编译器时把负值这一档验一遍。变量名带 Q15 后缀，格式在调用处一眼可见，两个模块之间交换定点数时，Q 格式与字段一起写进接口文档。

改了什么，为什么必须改：基础档直接拿浮点乘，依赖 FPU 与浮点上下文，进阶档把浮点面收到入口一次，环内只剩整数乘和移位。没有 FPU 的内核浮点靠软件模拟，一次乘法几百个周期，控制环放不下。有 FPU 的内核单精度虽快，中断里用浮点会让编译器保存额外的寄存器，响应时间跟着变长。定点全程整数，周期数可预期，精度损失被 Q 格式锁在约定的格子里。

## 缓存与内存布局

Jetson 这类 CPU 有各级缓存，连续访问一片内存很快，跳着访问就慢。点云处理按行遍历比按列遍历快，原因在此。多线程里两个线程改同一缓存行上的不同变量，缓存一致性协议来回协调，性能突然变差，这叫伪共享，变量之间插入填充就能化解。

量级放在这里做参照：L1 缓存几十 KB，命中一次十几拍，读写内存几百拍，两者差一个量级以上。缓存按行粒度搬运，一行 64 字节，读一个字段就顺带把整行搬上来，紧接着用相邻字段是顺手的，跳着访问则每用一次搬一行，带宽和延迟一起变差。点云的 x y z 按点连排，按点顺序遍历是顺序访存，按维度把 x 全取完再取 y，每读一个字段浪费一行的大部分。位姿这类小结构怎么访问都行，点云与图像这类大数组要顺着内存排布走。伪共享的现场是并排的两个计数器，落进同一缓存行，两个核各改各的，缓存行在核间来回搬，计数不快反而慢，把两个变量隔开 64 字节以上，或合并成一个计数器，问题就没了。

## 中断与 DMA

外设来数据，CPU 停下来处理，这一过程叫中断。串口和 CAN 这类高频数据流用 DMA，数据自己进内存，CPU 等搬完再被叫醒。纪律：中断服务函数只搬数据置标志，复杂逻辑回主循环。共享变量加 volatile。中断优先级排好，安全相关的排前面。中断里杜绝阻塞和打印。

STM32 的中断由 NVIC 管理，每个中断有抢占优先级与子优先级两组数字，数值小的级别高，抢占级别不同的可以嵌套，相同的排队。急停与限位这类安全相关的排最高档，原因在于中断延迟直接等于安全响应时间，这个延迟通常是微秒量级，值得花时间把优先级表画清楚。volatile 拦的是编译器优化，它不产生原子性，四字节以内的对齐读写是单条指令，跨结构的复合数据仍然要在临界区里改。Cortex-M 的 32 位对齐读写天然原子，这条经常被当成不加锁的理由，多字节结构上不成立。

DMA 的常见用法是双缓冲：缓冲 A 在收的时候，主逻辑处理缓冲 B，半满与全满各来一次中断，CPU 介入次数减半。有一条边界要记清：DMA 搬完一批字节不等于一帧收完，帧的边界仍然由第 9 章的状态机来判。Jetson 这侧的外设 DMA 还有缓存一致性问题，外设写进内存的数据，CPU 可能读到旧的缓存副本，这件事由驱动处理，应用层不直接碰，但排查数据晚一拍的怪现象时要想到这一层。

## 系统总线与设备互连

整车三层链路对应三种总线形态：上位机到 STM32 走 UART，STM32 到电机走 CAN，车到车走 ESP-NOW。总线解决的是多个设备共用一组线，谁在什么时刻说话的问题，CAN 的做法值得拆开看，它是电机链路的标准答案。

物理层先把抗干扰讲清。CAN 用两根差分线，CAN_H 与 CAN_L，显性状态两根线差约两伏，隐性差接近零。线与逻辑是基础，任一节点拉显性，总线就是显性。仲裁发生在多个节点同时发送时：逐位比较标识符，发显性的节点继续，发隐性的自动退出转接收，帧不被打断，这叫非破坏性仲裁，标识符数值越小优先级越高。终端电阻两个，装在总线两端，各 120 欧，吸收信号反射。拓扑走线型，支线要短，星型与长支线都要避免。速率与线长是一对矛盾，一兆速率对应几十米以内，线长上去就得降速。采样点一般放在位时间的四分之三附近，速率越高，可漂移的余量越小。

帧与错误处理是另外两层。数据帧按帧起始，仲裁段，控制段，数据段，校验段，应答槽，帧结束排列，经典格式数据段零到八字节。位填充规则是连续五个相同位之后插一个相反位，保证边沿持续供给同步。应答槽是链路级确认，任何一个正确接收的节点都可以拉显性，发送方据此知道至少有一个节点收到，应用层的确认仍要自己设计。错误计数分发送与接收两个，超过阈值先进入错误被动，再严重进入总线关闭，节点自动退出总线，严重故障把节点摘下去走的就是这条路径。排查按四类走：完全不通先查终端电阻与共地，偶发丢帧查线长与支线与负载，个别节点掉线查编号冲突与供电，跑一段进总线关闭就追错误计数的来源。

落到电机链路：3508 走标准帧，一个控制标识符装四台电机的电流指令，每台两字节，反馈帧按驱动器编号分别回传角度，转速，电流，温度，控制周期在一毫秒量级，一个控制帧管四台，八台分两帧。总线负载按每帧位数乘帧率求和再除以波特率估算，七成是经验上限，留出的余量给急停与参数帧。高优先级帧留给安全相关动作，周期控制帧按驱动器错开，避免多个节点同一时刻齐发。

邻居总线各自归位：UART 点对点无仲裁，秩序靠帧格式。I2C 与 SPI 是板级主从总线，管板内器件。RS485 多点但无仲裁。EtherCAT 是主从实时以太网，工业高同步场合用。板内器件走 I2C 与 SPI，上下位机走 UART，电机走 CAN，点云这类大流量走以太网，一层一个链路，互相不抢。

## 程序在内存里的样子

编译产物在内存里分几块：代码段放指令与常量，初始化的全局变量在 flash 和 ram 各占一份，未初始化的全局变量只占 ram，启动时清零。堆从低地址往上长，栈从高地址往下长。栈上放函数局部变量，返回地址，中断现场，中断来时用的还是栈。链接脚本决定各段的地址，map 文件列出每个函数与变量的占地，空间紧张时先看 map 再动手。栈溢出的表现有欺骗性：栈长过了头踩进相邻变量的区域，现象是某个不相关的参数自己变了，或者直接进硬件异常，排查时从头到尾翻代码找不到，看栈水位一眼就明白。做法是启动时给栈区填特征值，跑完整套流程之后回看用了多少。代码里禁 malloc 的理由不止碎片一条：分配失败要在哪一层处理，分配耗时的不确定性有多大，这两件事在实时控制里都不划算，MCU 侧的内存全部按编译期静态分配，上位机侧相对宽松，但长跑节点要盯常驻内存曲线，第 28 章展开讲。

## MCU 与工控机的分工

教科书的分工是 MCU 管实时，工控机管上层。我们的实战版本是 STM32 管实时控制和安全，NUC 和 Jetson 管感知，定位，决策。判断标准一条：这段逻辑怕不怕抖动。怕抖动的 PID，急停，限位，全部下沉到 STM32，CAN 直连 STM32，路径最短。不怕抖动的识别，规划，通信，放上位机跑。分工定了，两边的接口就照着这个写。

三条链路与这个分工一一对应：UART 搬运参数与状态，CAN 承载毫秒级控制环，ESP-NOW 承担车与车的协同。数据在下层多等一毫秒是迟到，在上层多等一毫秒多半无感，划接口时按这条差别来分。

## 常见坑清单

- 跨设备传输不用结构体直发，字段逐个手写拼装，字节序写进协议表。
- 有符号数先转无符号再拆字节，不依赖负数右移的默认行为。
- 帧长与字段偏移以协议表为准，不用 sizeof 与 offsetof 现算。
- 定点数的 Q 格式与字段一起约定，换算函数带饱和与 32 位中间量。
- 中断与主循环共享的标志变量加 volatile，但别指望它带来原子性。
- 中断服务函数只搬数据置标志，打印与阻塞操作留在主循环。
- CAN 的问题按不通，丢帧，掉线，总线关闭四类分，先物理层后调度。
- 点云与图像这类大数组顺着内存顺序访问，别按维度跳跃读。

## 几条小结

- 字节序问题每届都会出现，在协议文档里写死可以避免。
- sizeof 的结果由编译器决定，加上对齐填充后不等于字段长度之和。
- 中断服务函数里每多一行代码，整机节拍都会受到影响。
- 分层分工的依据是这段逻辑对抖动的敏感程度。
- 同一种字节，有符号与无符号是两套读法，符号性在协议里先定死。
- 浮点不直接进帧也不直接进控制环，小数换算成定点或整数，格式跟着字段走。
