# 第 16 章 协作案例

> 机器的问题大多有迹可循，人的问题没有现成的排查路径。这一章不讲电，不讲代码，讲四件在协作上花时间最多的事。

## 案例 1：参数被覆盖事件

**现象**：今天调好的参数，第二天上车表现全变。手感回来了，数值却对不上。同样的情况连着两天出现，调参的人开始互相怀疑对方的操作。

**排查路径**：

1. 上锁，把参数文件改成只读，第二天照样被改。改动走的是另一个写入口，参数在好几个目录里各有一份
2. 查修改时间，改动发生在深夜，那个时段另一个人在车上操作
3. 核对操作顺序，两个人各自启动过车，一个带新参数保存退出，一个带旧参数启动，覆盖了前一次保存。先保存的人操作本身没有错，问题出在启动顺序与保存时机，这类覆盖用版本号加锁就能防住
4. 查版本，参数文件没有版本号，谁都没法证明自己手里的是哪一版。争论没有依据，只能靠回忆

**根因**：一车一套参数的规矩有，执行只靠自觉。参数文件散落在多个目录，没有版本号，没有锁，启动时读到哪份用哪份。多人共用车时，当天调好的参数很难保留到第二天。多处副本各自演化，最后一次写入者覆盖前面所有版本，覆盖发生后连追溯的依据都没有。深夜操作与记录缺失又放大了这个问题，改动没有旁证。覆盖还有一个隐蔽来源，从备份恢复，把旧备份整个拷回目录，新版本会被一并冲掉，恢复动作同样要走记录。参数文件的命名也乱，靠日期相近的文件名分辨版本，容易看错。

**解决**：参数收口到唯一目录，带版本号，开机自检读参数并打印摘要，车上的人一眼看到当前值。改动走记录，谁改的，改了什么，为什么改，改完复测没有。参数进版本管理，改完提交，重启前后各看一次摘要。摘要一行打全，版本号，修改时间，几个关键数值。四项记录齐了才算一次合规改动。参数摘要同时显示在屏幕常显的一角，上车先看它。

**预防**：

- 多人同时用一台车，先在群里点个名，说清楚各自用哪份参数
- 参数目录默认只读加版本号，新人不设锁就上不了车
- 每天收尾把当天认可的参数提交一次，历史随时可查，提交信息写清楚改动点
- 参数文件的目录结构固定，配置，标定表，日志分开放，找东西不靠翻

延伸：参数治理可以归到三条，单一来源，显式版本，改动留痕。参数汇总页，开机摘要，提交记录，都围绕这三条建立。把参数状态放到谁都看得见的地方，覆盖一类的事故自然减少。

## 案例 2：人员断层与传承断裂的修复

**现象**：毕业季一到，老队员陆续离开。某天车出故障，围了一圈人，懂这块系统的学长已经毕业。供应商联系人只存在前任队长的电脑里，那台电脑蓝屏后再没能开机。后勤联系先断，技术传承跟着也断了。

**排查路径**：

1. 盘家底，把每块系统标注谁懂，懂到什么程度，标完心里一沉。每块写上一手人与二手人，几块系统只有一个名字
2. 找文档，图纸与注释零散，关键逻辑只掌握在少数人手里
3. 复盘交接，上一年没有交接清单，全靠口口相传，人走线断。没有清单，没有验收动作
4. 定补救，先写再训，文档补起来，人跟着文档学，学会一个放手一个。放手按清单来，哪块过了验收哪块交出去

**根因**：知识存在人脑里，没进文档和仓库。老队员习惯包办，学弟只做辅助，拿不到动手机会。人一走，系统就出现盲区。组织上没有要求知识落地，交接就变成个人行为，遇到毕业，电脑故障这类意外，链条直接断。供应商这类对外关系也算知识，联系人只在一台电脑里，那台电脑开机失败的那一刻，先断的是后勤。单点依赖一年年复制，老队员包办，学弟拿不到完整动手机会，成长不起来。

**解决**：文档入库，关键系统的原理，参数，操作与故障处理逐块补齐。师徒结对，老手带新手做完整一遍之后主动放手，让新手独立跑通。供应商与联系人清单整理成共享文档，谁都拿得到。师徒结对的验收标准是新手独立跑通一遍完整流程，供应商清单用队伍公共账号维护，本地再加一份备份。文档写清为什么，不只写怎么做，决策的原因留下来，下一届才敢改。传承还有一层是习惯，改动留记录，参数留版本，这些习惯比单个知识点更耐用，交接时要把做法一并交出去。

**预防**：

- 交接清单写进换届流程，文档不全不得离队，按系统逐块打钩，文档与实操双双过手
- 重要系统至少两人掌握，禁止单点依赖，双人名单每学期更新一次，写在文档首页
- 复盘制度落地，每周十分钟短会，经验当场变文字
- 对外联系用队伍公共账号，联系人信息不做个人收藏
- 换届前的最后一次全员会，逐块确认双人名单与文档状态，当场过
- 文档配一页术语表，把队内叫法与系统里的正式名称对上，新人看文档先过术语表
- 学弟的动手机会按清单分配，每块系统轮着来

## 案例 3：需求变更与补丁代码的治理

**现象**：规则细则修订，战术跟着改，代码跟着打补丁。补丁叠补丁，一份主程序长到几千行，改一处会连带影响三处。新人看了一次，直接问还有没有别的任务。

**排查路径**：

1. 梳理依赖，谁调谁画一张图，画完才知道有多乱。箭头一多，改一处牵动一片
2. 查历史，每次变更都是就地加 if，接口没有约定，字段约定不一。典型的痛点是单位混用，角度有的用度有的用弧度，联调时才发现
3. 找爆发点，一次小改动引发一连串故障，大家同意停下来处理
4. 定方案，先冻结接口再动内部结构，按模块逐层拆分。拆分按依赖图从叶到根推进

**根因**：变更是常态，架构却没给变更留位置。需求来了就在最上层加一块，累积起来以后，模块之间互相牵连，任何改动都有风险。规则细则一年修订数次，战术与代码跟着动，需求一来就往最上层叠，模块之间的隐式依赖越来越多，任何小改动都可能踩到别处的假设。接口字段没有成文的含义与单位，上下游各按自己的理解用，错误在联调时才集中爆发。接口没有成文约定时，模块之间的暗依赖只能靠口口相传，改动的人不知道下游在看哪个字段，风险在联调时才暴露。

**解决**：接口先冻结，串口帧这些边界一个字节不动，上位机内部按模块拆分重建。状态机接管流程，原来靠 if 堆出的分支，变成状态，事件，转移，超时。拆完重测，三个长期存在的老问题一起解决。拆分顺序先内部查询类模块，后主流程主干。边界现状先落进文档，字段清单，示例报文，时序图，评审有参照。拆分完成后的代码加了一轮阅读会，每块模块由留守的人讲一遍给其他人。

**预防**：

- 变更走记录，改前写清楚为什么，改后留测试
- 新代码进评审，接口约定四条纪律，字段，单位，频率，超时，对着审，四项全对才进主干
- 新人第一个任务是给老模块写文档，写完就懂一半
- 边界扩展守一条规则，新字段只往尾部加，老字段的含义与位置不动
- 评审记录留档，四条纪律逐项打钩，缺项不入主干
- 主干合并前跑一遍回归脚本，脚本清单随模块维护

延伸：构建流程也踩过同类问题。工作区里先跑过一遍旧构建命令，中间产物留在目录里，之后换正确流程重建，报错却指向新写的模块，查半天查不出所以然。后来的规矩是换构建流程先清工作区，构建命令与顺序写进文档，新人照抄。

## 案例 4：队长传承，运营手册的由来

**现象**：队长换届的前两个月，新队长几乎住在训练馆里，工作仍然千头万绪。报名节点差点错过，供应商对账对不上，酒店名单收到半夜。技术之外的事务消耗了大量精力。

**排查路径**：

1. 复盘一任队长到底在忙什么，把日常事务列全。报名，采购，对账，联络，内部协调，一项项都要花时间。列全之后按周排开，哪周忙哪周闲就显出来了
2. 分类，事务分成赛季节点，对外对接，采购后勤，内部制度四类
3. 找缺口，四类里只有技术有传承，其余全靠临场记忆。每任从零摸索
4. 定产物，把这些年的经验做成一本运营手册，随届交接

**根因**：队伍的传承一直是技术导向，运营知识没人把它当知识。每任队长从零摸索，一年任期里小半时间花在这些事务上。任期一年，从零摸到熟悉已经消耗小半时间，剩下半年才进入状态，下一任又从头开始。事务性错误的代价也不小，错过报名节点，对账对不上，结果与技术失误一样，都直接影响参赛。对外对接的责任也集中，组委会与供应商的沟通一人主责，避免多头联系引起信息混乱。

**解决**：运营手册成形。一年备赛节奏的时间线，供应商与组委会的联系人，采购与记账流程，每周短会的习惯，全部写进去。责任到人，资产统一登记，组委会对接专人负责。酒店，医院，车辆这些出行信息，每人一份。信息发布的口径也收口，通知走固定渠道，重要事项留文字记录。出问题先组织处置，再同步队长。手册里每类事务配一名当届负责人，名单与联系方式随届更新。

**预防**：

- 手册随届更新，队长离任前完成修订，作为交接的一部分，下一任接手时按手册过一遍关键节点
- 重要节点提前在日历上做双提醒，报名与提交类节点提前一个月做校对
- 手册放仓库，谁都能看，谁都能改，改完记录一笔
- 手册每章配一页检查单，节点，联系人，流程，模板四栏，照单执行
- 手册修订留改动记录，哪一届改了什么，为什么改，一年一页

延伸：运营手册与故障案例库是一对，一个管流程，一个管技术，都随届交接。手册的价值不在写得多全，在有人读，有人改，每届留下自己的修订。
