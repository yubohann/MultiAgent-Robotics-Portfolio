# 第 29 章 计算机网络与通信基础

> 双机联调第一天，两台电脑各自跑得好好的，一连起来互相看不见。端口查了，防火墙查了，最后是交换机把多播挡了。换个口，两台机器恢复通信。那天我记住的原则是：网络问题分层排查，一层的问题不要在另一层里找原因。

## 选型总表

我们把通信分四段：上位机到 STM32 走 UART，STM32 到电机走 CAN，车到车走 ESP-NOW，雷达点云走以太网。选型看四个维度：带宽，距离，延迟，丢包容忍度。原则：短距离高可靠的控制链走有线，跨车移动的链路走无线，大带宽数据流走网线。遥控链路按规则限在 WiFi 和 Zigbee 这类无线方案里，蓝牙在赛场失灵是老问题，每一届都有人重新遇到。

四条链路的工作方式分开看。UART 是一对一链路，线接对了，波特率对上了就能跑，跑的是参数下发与状态回读，收发节奏由帧格式约束。CAN 是差分总线，多主结构，带优先级仲裁，STM32 与电机驱动器之间就这一条线，高优先级的帧先走，硬件层自带错误检测与计数。ESP-NOW 是无连接无线链路，2.4 吉赫兹，单包上限 250 字节，小报文的指令与心跳全靠它，链路的可靠性由应用层补。以太网承载点云与图像这类大流量，也承载上位机之间的数据交换，带宽是四条链路里最高的。

四条链路的对照整理成一张表，选型和排查先查这张表。

| 链路 | 介质与形态 | 典型数据 | 可靠性来源 |
| --- | --- | --- | --- |
| 上位机到 STM32 | UART，点对点有线 | 参数下发与状态回读 | 帧格式加 CRC16 加序号重发 |
| STM32 到电机 | CAN，差分多主 | 控制帧与反馈帧 | 总线硬件校验与优先级仲裁 |
| 车到车 | ESP-NOW，无线无连接 | 指令，心跳，急停 | 应用层五个机制 |
| 雷达到上位机 | 以太网 | 点云，图像 | UDP 加序号与时间戳连续性检查 |

故障排查按层推进，顺序固定：物理层先查线缆，水晶头，接口指示灯，供电。地址层查网段，IP 冲突，设备名。协议层查域号，多播，QoS 配置。应用层查话题频率，时间戳，字段解析。动手前先 ping，ping 不通就不往上找。引言里那次多播被挡，表象出现在应用层，根因在协议层，分层顺序能最快把它归位。

## 串口的边界与秩序

串口简单，线接对，波特率对上就能跑。边界也明显：一对一连接，距离短，速率有限。秩序靠帧格式，我们用五段式：帧头，长度，序号，载荷，CRC16。收包用环形缓冲区，粘包分包都按帧头重新对齐。波特率往高提会放大线材和干扰的问题，线缆尽量短，走线尽量直。设备名漂移的问题在前面讲过，解决办法是用 udev 规则固定。

五段式逐字段的口径定死，两端照同一张表实现。

| 字段 | 长度 | 口径 |
| --- | --- | --- |
| 帧头 | 2 字节 | 固定 0xAA 0x55，收到即按帧头处理 |
| 长度 | 1 字节 | 载荷字节数，上限锁在 255 字节以内 |
| 序号 | 1 字节 | 指令去重用，状态帧可置零 |
| 载荷 | N 字节 | 指令或状态，按字段表逐个序列化 |
| CRC16 | 2 字节 | 覆盖长度，序号与载荷，低字节在前 |

多字节字段的字节序在第 27 章写过纪律，跨设备不直接发结构体，逐字段按文档拼字节。帧头固定两个字节的价值在重同步：数据流里任何位置出现 0xAA 0x55，解析器都可以从这里起一帧重新对齐。

收包的失败形态有两类。粘包是两次发送的数据连在一起到达，缓冲里出现完整两帧。分包是一帧跨了两次读取，或者半帧后面跟了一串乱码。处理方式统一：字节进环形缓冲区，解析器逐字节推进状态机，见帧头才起帧，长度不合法或校验不过就丢，回到找帧头的状态。这套处理不依赖任何一次读取的边界，粘与分都不影响结果。

CRC 选 CCITT 版，多项式 0x1021，初值 0xFFFF。位运算版实现最短，适合讲原理，上线版本换成查表版省 CPU。下面的函数两端共用，组帧与收帧调的是同一份实现。

```c
#include <stdint.h>

/* 进阶档: CRC16-CCITT-FALSE, 多项式 0x1021, 初值 0xFFFF */
uint16_t crc16_ccitt(const uint8_t *data, uint16_t len)
{
    uint16_t crc = 0xFFFF;
    for (uint16_t i = 0; i < len; i++) {
        crc ^= (uint16_t)data[i] << 8;        /* 新字节并入高位 */
        for (uint8_t bit = 0; bit < 8; bit++) {
            if (crc & 0x8000)
                crc = (uint16_t)((crc << 1) ^ 0x1021);
            else
                crc = (uint16_t)(crc << 1);
        }
    }
    return crc;
}

/* 校验范围: 长度, 序号与载荷, 帧头不参与 */
uint16_t frame_crc(const uint8_t *frame, uint16_t payload_len)
{
    return crc16_ccitt(&frame[2], (uint16_t)(2 + payload_len));
}
```

关键行三处。初值必须两端一致，CCITT 系有 0xFFFF 与 0x0000 两种常用初值，两端选得不一致，校验就永远对不上，排查时先核这一条。字节先异或进高 8 位，再逐位做模 2 除法，余数最高位为 1 就左移后异或多项式。收方校验：把帧里的校验值取出来，对同样范围重算一遍，相等才收下，不等直接丢弃，不进入上层逻辑。

位运算版每字节循环 8 次，耗时随帧长线性增长。200 字节的帧放主循环没有压力，放高频中断里要留意占用，压 CPU 的常规做法是换 256 项查表版，位运算版留着讲原理和对拍验证。查表版与位运算版对同一批数据必须算出同一个值，这条对拍用例写进回归脚本。

## TCP 与 UDP

TCP 有连接有重传，数据完整送达，代价是延迟不确定。UDP 无连接，发送后不等待确认，延迟稳定，个别丢包不影响整体。选择逻辑：指令和状态走可靠机制，点云和图像这类丢一帧无影响的走 UDP。ROS 底层是 DDS，默认靠多播发现邻居，交换机的多播一旦被禁，机器之间互相看不见。点云流的带宽大，话题频率和裁剪范围都要提前计算，网络跑满之后会出现各种难以解释的现象。

TCP 的重传对延迟的影响要单独说。丢包重传会把单次延迟拉长几倍，而且拉长的是尾部延迟，平均延迟看着正常，偶发的大延迟会把时序链路打乱。TCP 适合文件传输，参数读写，远程登录这类场景，把它放进控制回路要谨慎。TCP 是字节流，没有消息边界，应用层要自己划帧，帧格式可以照搬串口那套五段式。

UDP 的丢包要靠应用层可见。做法是给数据加序号，收方检查序号连续性，发现缺口就知道丢了几帧。缺口按数据种类处理：点云缺一帧就用下一帧，图像缺帧可以请求重发，也可以跳过。缓冲里的半帧数据宁可丢掉，不允许进算法。

QoS 是 ROS 2 里把可靠与尽力做成档位的地方。传感器话题用 best effort，控制指令用 reliable。订阅方要求的档位高于发布方提供的档位时，两端静默连不上，没有数据也不报错，这是迁移期最难查的坑之一。查话题先看档位。

带宽估算的方法：单帧大小乘发布频率，得到理论带宽，再对照链路容量留出余量。点云是全链路的流量大头，先算清它要不要跨机，必须跨机的再上链路，不跨机的不发。把估算写进接口文档的字段表，联调时按数字核对。

## ROS 多机通信

多机要通，先决条件三条：同一网段，同一 ROS_DOMAIN_ID，DDS 能在网络上发现彼此。老 ROS 1 时代配 ROS_MASTER_URI 和 ROS_IP，两头都得对。联调之前先 ping，能通再谈 ROS 层。车上两块网卡分属两个网段时容易互相干扰，地址冲突的表现是通信时好时坏，启动自检里加一条链路检查项，能省掉大量排查时间。

发现机制展开一层。ROS 2 没有中心节点，节点之间靠多播自动发现，域号一致且多播可达才互相可见。交换机禁多播或跨网段时，改用发现服务器，两端配置同一个服务器地址。多机排查的顺序：先 ping 网络，再看 ros2 topic list 是否发现，再对 ros2 topic hz 看频率，最后用 ros2 topic info 加 verbose 看 QoS 档位。能看见话题但收不到数据，第一嫌疑是 QoS 不匹配。

双车场景再叠两条纪律。其一，命名空间分区，两车的话题名与坐标系帧各带前缀，防止串树。其二，有线网卡与无线网卡并存时，DDS 用哪块网卡由配置决定，选错时另一端只能看见自己，把网卡选择与域号一起写进启动脚本，按车分发配置。

带宽纪律与上节一致：点云是否需要跨机先评估。跨机的大流量话题降频或者裁剪范围，遥控链路按规则限在 WiFi 和 Zigbee 里，大流量不走无线。

## CRC，ACK 与重发

校验和确认是可靠传输的两个基本机制。CRC16 拦截传坏的帧，收方算一遍，对不上就丢。ACK 让发方确认对方收到，超时没确认就重发。重发要有约束：序号去重保证重发的指令只执行一次，有效期保证过期指令自动作废，次数封顶 3 次，链路判定断开后停止发送。ESP-NOW 这条链上我们固定了五条规则：心跳 20 赫兹，300 毫秒收不到心跳判链路断，指令带序号，重发的指令只执行一次，急停最高优先级且锁存。

帧解析的第一段代码是收包状态机。所有字节从串口中断进环形缓冲区，解析器在主循环逐字节推进状态机。乱码，半帧，粘包三种情况由它统一处理：状态只停留在合法的下一步，当前帧被判定无效就立刻回到找帧头的位置。代码按五段式帧格式写。

```c
#include <stdint.h>

/* 进阶档: 收包状态机, 逐字节推进, 乱码后靠帧头重新对齐 */
typedef enum { RX_H1, RX_H2, RX_LEN, RX_SEQ, RX_PAYLOAD, RX_CRC_LO, RX_CRC_HI } rx_state_t;

static rx_state_t st = RX_H1;
static uint8_t payload[250];              /* 上限对齐 ESP-NOW 单包 250 字节 */
static uint8_t seq_rx = 0;
static uint16_t idx = 0, need = 0, crc_calc = 0, crc_rx = 0;
volatile uint8_t frame_ready = 0, frame_seq = 0;

static void crc_push(uint8_t b)           /* 长度, 序号与载荷边收边算 */
{
    crc_calc ^= (uint16_t)b << 8;
    for (int i = 0; i < 8; i++)
        crc_calc = (crc_calc & 0x8000) ? (uint16_t)((crc_calc << 1) ^ 0x1021)
                                       : (uint16_t)(crc_calc << 1);
}

void rx_byte(uint8_t b)
{
    switch (st) {
    case RX_H1:  if (b == 0xAA) st = RX_H2; break;
    case RX_H2:  st = (b == 0x55) ? RX_LEN : ((b == 0xAA) ? RX_H2 : RX_H1); break;
    case RX_LEN: crc_calc = 0xFFFF; crc_push(b); need = b;
                 if (need == 0 || need > (uint16_t)sizeof(payload)) { st = RX_H1; break; }
                 idx = 0; st = RX_SEQ; break;   /* 长度一字节, 落地即检 */
    case RX_SEQ: crc_push(b); seq_rx = b; st = RX_PAYLOAD; break;
    case RX_PAYLOAD:
        crc_push(b); payload[idx++] = b;
        if (idx == need) st = RX_CRC_LO; break;
    case RX_CRC_LO: crc_rx = b; st = RX_CRC_HI; break;
    case RX_CRC_HI:
        crc_rx |= (uint16_t)b << 8;        /* 低字节在前, 拼回完整值 */
        if (crc_rx == crc_calc) { frame_seq = seq_rx; frame_ready = 1; }
        st = RX_H1; break;                 /* 校验成败都回找帧头 */
    }
}
```

关键行四处。RX_H2 状态里再遇到 0xAA 不后撤，连着的 0xAA 0xAA 0x55 也能锁住。长度字段一字节，落地就做合法性检查，零与超上限都直接丢弃，避免噪声把状态机拖在长帧里空等。CRC 从长度字段起边收边算，覆盖长度，序号与载荷，收到最后两字节立即比对，不需要把整帧缓存完再回扫一遍。解析全程在主循环里推进，frame_ready 与 frame_seq 是解析器交给消费端的标志，取走一帧后要记得清标志。

这套状态机对乱码的抗性来自一条：任何错误路径都收敛回 RX_H1，不在错误状态里停留。丢一帧的代价是等下一帧，不会锁死。

第二段代码是发方的重发循环。指令带任务标识与序号，一个槽位管一条在途指令，等待确认期间不新发。超时重发同一序号，重发上限 3 次，到顶或过期就放弃并上报。链路判据与心跳共用，300 毫秒收不到心跳，发送直接拒绝。

```c
#include <string.h>

/* 进阶档: 指令发送槽, 超时重发, 序号去重, 有效期约束 */
typedef struct {
    uint8_t  state;               /* 0 空闲, 1 等待确认 */
    uint8_t  task_id, seq, retries, len;
    uint8_t  payload[32];
    uint32_t first_ms, last_ms;   /* 首发与最近发送时刻 */
} tx_slot_t;
#define TX_MAX_RETRY  3
#define TX_TIMEOUT_MS 50              /* 与心跳 20 赫兹同节拍 */
#define CMD_TTL_MS    300             /* 过期作废, 与断链判据同口径 */

int tx_send(tx_slot_t *s, uint8_t task_id, const uint8_t *data, uint8_t len, uint32_t now)
{
    if (s->state != 0 || len > sizeof(s->payload) || !link_alive(now))
        return -1;                    /* 忙, 越界, 链路断都不发 */
    s->task_id = task_id;
    s->seq++;
    s->retries = 0;
    s->len = len;
    memcpy(s->payload, data, len);
    s->first_ms = s->last_ms = now; s->state = 1;
    radio_send(s->task_id, s->seq, s->payload, s->len);
    return 0;
}
void tx_poll(tx_slot_t *s, uint32_t now)
{
    if (s->state == 0) return;
    if (ack_seen(s->task_id, s->seq)) { s->state = 0; return; }
    if (now - s->last_ms < TX_TIMEOUT_MS) return;       /* 未到重发点 */
    if (s->retries >= TX_MAX_RETRY || now - s->first_ms > CMD_TTL_MS) {
        s->state = 0;
        report_fail(s->task_id);      /* 到上限或过期, 放弃并上报 */
        return;
    }
    s->retries++; s->last_ms = now;
    radio_send(s->task_id, s->seq, s->payload, s->len); /* 序号不变, 收方去重 */
}
```

关键行四处。发送前先查链路存活，断链状态继续排队只会堆出一批永远发不出去的指令。重发沿用首包的序号，收方按任务标识加序号查重，重复包不再执行但仍然回确认，避免首次确认在路上丢了之后发方一直重发到上限。首发时刻单独记录，重发次数与有效期是两条独立约束，任一触发即放弃。放弃的动作要上报给任务层，让上层决定重试还是改走别的策略。

收方一侧补一条对称逻辑：执行前查指令年龄，超过有效期的直接丢弃并回确认。指令积压在队列里变老，执行它比不执行更危险，传球这类对接动作尤其如此。

心跳把两边串在一起。20 赫兹的心跳就是 50 毫秒一帧，连丢几帧就该警觉，300 毫秒没收到判链路断，进安全降级。断链之后发方停发新指令，收方按预案停机构动作，这是紧急急停之外的常规降级路径。急停走最高优先级，锁存，人工复位，不排队。

## 时间同步

双车协作的前提，是两边对同一瞬间有一致的定义。做法：启动时对钟，运行中低频再校，传输延迟单独标定。传球联调第一晚，两边时间差了 300 毫秒，球传出去的落点全凭猜测。那晚之后，时间同步进了握手流程，位置和动作的对齐都以它为基准。

对钟的原理是往返测量。A 发一个带本机时刻的请求，B 收到后立即回一个带两端时刻的应答，A 拿到往返时间，按往返的一半估计单程延迟，据此校正钟差。无线链路的往返时间有抖动，重传与调度都会影响单次测量，所以单次对钟不够，运行中按低频再校，把漂移压在预算以内。

时钟源纪律：一份数据链只认一个时钟源。时间戳在源头打，下游不用自己的时钟重打，重打会叠加两段延迟。混用两个时钟的表现是数据顺序错乱，观感像丢包，实际是排序错了。第 28 章写过仿真时间与墙钟不能混用，双车场景再叠一条，两边车子的时钟来源各自唯一，再通过对钟拉到同一时间轴上。

验证方法：两边对同一事件打时间戳，急停广播这类全网可见的事件最合适，事后把两边的日志并排，时间差就是要压掉的目标。每次链路改动后复测一次，把数值记进联调报告。

## 联调前的链路检查清单

通信层的联调按清单走，四层各查一遍再上台。

- 物理层：线缆与水晶头是否压紧，接口灯是否亮，供电是否正常，无线天线是否装牢。
- 地址层：是否同一网段，IP 有没有冲突，串口设备名是否固定，udev 规则是否生效。
- 协议层：ROS_DOMAIN_ID 是否一致，多播是否可达，QoS 档位是否匹配，帧格式两端是否同版。
- 应用层：话题频率是否正常，时间戳是否新鲜，字段解析是否正确，序号是否连续。
- 无线专项：心跳是否在跳，重发计数有没有持续增长，急停链路是否单独验证过。

## 几条小结

- 通信故障按物理层，地址层，协议层，应用层的顺序排查。
- 无线链路的确定性靠应用层的心跳与重发机制建立。
- 帧格式里省掉的细节，调试阶段都要花时间补回来。
- 双车协同动作以时间同步为前提。
