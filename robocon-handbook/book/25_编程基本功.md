## 代码进阶路线

从这一章到第 31 章，代码按三档递进：先写对，再写稳，后写快写顺。每章都给对照的例子，基础档解决能跑，进阶档解决跑在车上不出事。读的时候先看基础档，弄清它错在哪，再看进阶档改了什么，为什么必须改。这些例子覆盖从电控固件到上位机的常用写法，顺序跟着数据链走：先有变量与内存，再有缓冲区与队列，然后是总线上的字节，最后是工程化的调试与测试。

## C 语言在电控里的日常

STM32 那边全是 C。电机闭环，串口解帧，PID，编码器采样，都跑在这上面。日常写 C 的感受是贴着硬件走：指针直接点寄存器，位操作配掩码控 GPIO，中断服务函数里只搬数据置标志，复杂逻辑全部交给主循环。嵌入式规范里 malloc 属于禁用项，内存都在编译期定好，静态数组加栈够用了。volatile 在这类代码里出现频率很高，编译器有时会过度优化，把中断里改过的变量优化掉，加上这个限定词才能拦住这种优化。

一个 STM32 工程拆开看，文件分工是固定的。main.c 管初始化和主循环，驱动文件按外设分，串口一个，CAN 一个，定时器一个，协议解析单独一层，谁都不直接碰别人的寄存器。中断服务函数短到只有几行，收一个字节，放进缓冲区，置个标志，剩下的交给主循环。这条边界划清楚，节拍才稳。

malloc 被禁的原因有两条。堆上的内存分配耗时不确定，峰值工况里一次分配就可能把控制节拍拖过去。碎片积累之后，长时间运行的节点还可能分配失败。替换办法是静态数组加固定大小的池，容量在上电时就定死，用没了就是设计问题，早暴露早处理。

## 中断里的共享变量

中断与主循环共享的每一个标志位，都值得单独看一眼。下面先看一段事故写法。

```c
// 错误版：标志位没加 volatile，主循环可能永远读不到更新
static int frame_ready = 0;   // 中断里置位，主循环里查询

void USART1_IRQHandler(void)
{
    if (frame_full)           // 帧收满标志
        frame_ready = 1;      // 中断里写
}

int main(void)
{
    while (1) {
        if (frame_ready) {    // 编译器可能只读一次，缓存进寄存器
            handle_frame();
            frame_ready = 0;
        }
    }
}
```

这段代码在开优化之后随时会失效。主循环里读 frame_ready 的语句，编译器看不到它会被中断改动，就把它优化成只读一次，之后一直用寄存器里的旧值，中断置位再多次也读不到。现象是中断明明在跑，主循环却像没收到数据。

```c
// 正确版：volatile 让每次读写都回到内存
static volatile int frame_ready = 0;
```

一个关键词的差别，行为完全不同。volatile 告诉编译器这个变量可能被程序之外的力量改动，不许缓存，每次访问都去内存拿最新的值。中断与主循环共享的标志位，双边读写的缓冲区计数，都要照这个规矩来。数据本身超过一个字节时，还要配上关中断保护或者双缓冲，防止主循环读到更新到一半的内容。

## C++ 在上位机的日常

上位机跑的是 ROS 2，rclcpp 工程基本是 C++。节点用类来组织，回调函数收数据，Eigen 做矩阵，OpenCV 做图像，PCL 做点云。智能指针管生命周期，shared_ptr 注意不要形成循环引用，手动 new 出来的要配上 delete。模板够用即可，报错大量输出的时候从第一条读起。

节点类有固定骨架：构造函数里声明参数，创建订阅和发布，回调函数只做一件事，把数据放进成员变量或者丢进队列。

```cpp
// 进阶档：一个最小的 ROS 2 节点类骨架
#include <rclcpp/rclcpp.hpp>
#include <sensor_msgs/msg/imu.hpp>

class ImuMonitor : public rclcpp::Node
{
public:
    ImuMonitor() : Node("imu_monitor")
    {
        // 参数先声明后读取，默认值写在这里
        rate_hz_ = this->declare_parameter<double>("rate_hz", 100.0);

        sub_ = this->create_subscription<sensor_msgs::msg::Imu>(
            "/imu/data", 10,
            std::bind(&ImuMonitor::on_imu, this, std::placeholders::_1));
    }

private:
    void on_imu(const sensor_msgs::msg::Imu::SharedPtr msg)
    {
        // 回调里只存快照，重活交给主流程
        last_stamp_ = msg->header.stamp;
    }

    double rate_hz_{100.0};
    rclcpp::Subscription<sensor_msgs::msg::Imu>::SharedPtr sub_;
    builtin_interfaces::msg::Time last_stamp_;
};

int main(int argc, char ** argv)
{
    rclcpp::init(argc, argv);
    rclcpp::spin(std::make_shared<ImuMonitor>());
    rclcpp::shutdown();
    return 0;
}
```

关键行四处。declare_parameter 把参数声明和读取合成一步，默认值写清楚，现场不传参也能跑。create_subscription 的第二个参数是队列深度，回调处理慢的时候，队列深浅直接决定丢帧还是堵住。回调里只存时间戳这种轻量快照，一次推理要几十毫秒的活不能放在回调里，否则整条回调链跟着排队。main 函数三段式固定，初始化，spin，退出清理，不要在里面加业务逻辑。

节点成员变量分三类：配置参数，订阅发布句柄，最新数据快照。快照被多个回调访问时，加锁或者用原子类型，不要默认它是安全的。

## Python 的三种角色

队里 Python 承担三类工作。一是胶水脚本：解析日志，生成标定表，批量转换数据集。二是快速原型：想法先在 rclpy 里跑通，再决定要不要迁到 C++。三是现场工具：画曲线，看数据，盯调参面板。

三类工作有三条纪律。胶水脚本要幂等，同一份输入跑两次结果一致，方便复算，解析出的中间结果落盘存档，标定表生成错了能退回上一步。原型迁 C++ 的判据是耗时，离线小工具留在 Python，占控制链路的必须先在真机上测过延迟再定去留。现场工具要能离线跑，依赖提前装好，赛场网络条件差，装不上依赖的工具等于没有。

## 指针与内存的实验室现场

指针是 C 的基本功，也是事故高发区。数组越界踩到隔壁变量，现象是某个不相关的参数发生了变化。悬垂指针访问已释放的内存，现象是随机崩溃。结构体直接往字节数组里 memcpy，对齐和长度都可能对不上，帧就散了。内存踩踏的代价最高，因为它能让任何模块受牵连。查法：编译告警全开，越界靠自检代码拦住，释放之后把指针置空。

下面看两个最短的事故现场。

```c
// 事故版：越界一字节，悬垂一次访问
uint8_t data[8];
for (int i = 0; i <= 8; i++)
    data[i] = 0;          // 多写的一字节踩进相邻内存

uint8_t *buf = (uint8_t *)malloc(32);
parse_frame(buf);
free(buf);
verify_frame(buf);        // 用已释放的内存，结果随机
```

第一段里循环上限写成 8，数组只有 8 个元素，第 9 次写入落进相邻变量的地盘，那个变量会在某个不相干的时刻变值，查起来完全找不到联系。第二段里 buf 释放之后还传给下一个函数，那块内存随时会被别人拿去用，读出来的东西随机，这类故障最缠人，它不报错，只让结果偶尔不对。

```c
// 修正版：边界用 sizeof，释放后置空
uint8_t data[8];
for (size_t i = 0; i < sizeof(data); i++)
    data[i] = 0;

uint8_t *buf = (uint8_t *)malloc(32);
if (buf != NULL) {
    parse_frame(buf);
    free(buf);
    buf = NULL;           // 置空之后误用会当场出错，好过随机出错
}
```

边界条件用 sizeof 算出来，不写死数字。分配之后先判空。释放之后马上置空。这三条是全队统一的写法，代码评审时逐条对。

栈和堆还要分开想。栈空间小，函数里的局部大数组直接放上去，一次深调用就可能溢出，现象是函数返回地址被改写，程序跳进未知位置，所以大缓冲区一律做成静态或者动态分配，不摆栈上。内存问题的排查靠两样，编译告警全开加静态检查先扫一遍，运行时用 gdb 看崩溃现场。

## 调试基本功

排查从复现开始，复现完成之后再动手改。复现不了的先录包，靠数据定位。打印是最朴素的工具，打点带上时间戳和状态字，宁少勿滥，高频控制环里多一行打印，节拍立刻受影响。STM32 侧用 ST-Link 单步，上位机侧用 gdb 看调用栈，ROS 侧靠录包回放做对照。

打印有几个固定规格。每行前缀带模块名和等级，微控制器侧用定长格式，方便事后脚本切分。控制环里的打印走环形缓冲，由低优先级后台慢慢吐出去，不让打印本身占节拍。现场临时加的打点，问题解决当天删掉，避免下次排查被旧噪音误导。

## 工程习惯

改动配置之前先备份，改动代码之后尽快提交，commit 信息写清楚改了什么。参数改动留记录，谁改的，什么时候改的，为什么改。命名统一，电机就叫 motor，一个代码库里不要出现三种拼法。接口文档随手更新，联调前对一遍字段，单位，频率，超时。

习惯落到细处是几件小事。函数超过一屏就拆开，一个函数只做一段逻辑。注释写为什么，不写是什么，代码本身能讲清是什么。提交粒度按一件事一次，方便单独退回。接手别人的模块之前，先把它的日志和参数对一遍，读代码从入口函数读起，不从中间跳。这些要求看着琐碎，实测下来，能让一个陌生人在半天内看懂上一个学期写的车端代码。

## 几条小结

- C/C++/Python 的语法本身不难。真正要清楚的是每段代码跑在哪块芯片上，它失效时哪台车会停下来。
- 报错从第一条读起。根因通常只有一处，后面的报错大多是它的连锁反应。
- 改环境之前先备份。备份花不了一分钟，重装系统要花整个下午，还会停掉全组的调试。
- 环境熟练度平时看不出价值，出问题的当天直接决定排查和恢复的速度。
- 中断与主循环之间只传标志与快照。volatile 和关中断保护是标配，不是可选项。
