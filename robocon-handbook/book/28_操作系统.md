## 进程，线程，协程

一个 ROS 2 节点默认是一个进程。进程有自己的内存空间，崩溃了不会影响其他进程。进程内部可以开线程并行工作，线程之间共享内存，代价是数据访问需要同步。协程是用户态的轻量切换，Python 的 async 和 await 就是协程的实现，一个 await 让出一次执行权，其他任务先跑。选型时，进程用于需要隔离的场景，线程适合共享内存的并行任务，协程切换开销最小，适合高并发场景。

三者的切换代价差着量级。进程切换要换页表，微秒到几十微秒。线程切换换栈与寄存器，微秒级。协程在用户态完成切换，纳秒到百纳秒级，因为切换点是程序里显式写出的 await，没有内核参与。Python 还多一层约束：全局解释器锁让同一时刻只有一个线程执行字节码，计算密集的多线程不提速，这类任务要并行就上多进程。等网络与串口这类 IO 时，解释器在等待里放开锁，线程和协程都能把等待叠起来。ROS 2 的 rclpy 默认用单线程执行器，回调一个接一个跑，某个回调里做了长阻塞，其他话题的响应一起停住，要并行回调就换多线程执行器，代价又回到锁的问题上。

## 锁与竞态

两个执行体访问同一份数据就会产生竞态。典型情形是定位在更新位姿，决策同时读到半新半旧的坐标，动作随之偏移。解法有三条：用锁保护临界区，范围尽量小。简单计数改用原子操作。开销最小的做法是只保留一个写者，其他执行体都读副本。锁持有时间太长会拖慢整条链路，锁加漏了则表现为随机出错。

先看最朴素的错误形态。Python 里 pkt_total += 1 看着是一步，实际是取值，加一，写回三步，线程可以在这三步之间被换出去，两个线程各读到 100，各写回 101，一次加法就消失了，并发次数多了，统计值稳定偏小。下面是这段的基础写法，先给不带锁的错误版，再给加锁版，两版放在一起对照。

```python
import threading

pkt_total = 0                       # 通信线程累加, 主线程定时上报

def rx_worker_bad(n):
    global pkt_total
    for _ in range(n):
        pkt_total += 1              # 错误版: 取值 加一 写回, 中间会被换出

pkt_lock = threading.Lock()

def rx_worker_ok(n):
    global pkt_total
    for _ in range(n):
        with pkt_lock:              # 加锁版: 进入临界区, 退出自动放锁
            pkt_total += 1

def run(worker):
    t1 = threading.Thread(target=worker, args=(100000,))
    t2 = threading.Thread(target=worker, args=(100000,))
    t1.start()
    t2.start()
    t1.join()
    t2.join()

run(rx_worker_bad)
print("无锁结果", pkt_total)        # 常见结果小于 200000
pkt_total = 0
run(rx_worker_ok)
print("加锁结果", pkt_total)        # 稳定 200000
```

对照关键行。错误版的问题不在循环写法，在 += 不是原子操作，任何一步之后都可能被换出。加锁版改了一行 with pkt_lock，进入时拿锁，退出时放锁，语句块里抛异常也会正确释放。锁对象与它保护的数据一对一命名，pkt_lock 管 pkt_total，别的线程想读这个值也要用同一把锁，读方不加锁就可能读到写了一半的状态。临界区里只放必要的语句，把所有循环都包进锁里会让另一个线程一直等，加锁的收益被等待吃掉。

加锁之外还有三条路可以走。只留一个写者：通信线程把收到的包塞进队列，统计线程从队列里取数并累加，统计量只有一个写者，锁整个省掉，第 26 章的事件队列就是这个用法。原子操作：C++ 侧用 std::atomic 管简单计数，读改写一步完成。单写者加副本：定位线程把一份完整位姿算好，整体替换指针，读方每次拿到的都是完整的一份，不会读成半新半旧，6.1 节位姿发布只留一个发布者的纪律，讲的是同一件事。死锁的避免办法两条：多把锁按同一顺序获取，相关数据尽量装进一把锁管。最后一条纪律：持锁期间不调用外部回调，回调里再碰同一把锁，就把自己锁住了。

## 调度与实时性

Linux 不是实时系统，普通进程随时可能被调度器打断，几十毫秒的抖动很常见。控制环需要固定节拍，实时任务放在 STM32 上执行，裸机加中断，节拍稳定。上位机一侧靠绑核，调整 nice，关闭省电模式来抑制抖动。Jetson 的默认省电模式频率偏低，跑定位之前先把频率锁定。

调度器按公平原则分配 CPU，普通线程的优先级差别只体现在分到的份额上，负载重的时候，一次被换出的排队时间就到了几十毫秒的档位。抑制抖动的手段有限但要会用：taskset 把关键线程绑到固定核，减少核间迁移。nice 调高优先级份额。关掉按需调频让频率稳定。更硬的需求用实时调度策略，代价是别的线程可能长期拿不到 CPU，用之前把风险想清。定量判断的方法是测延迟分布，看最大值不看平均值。我们的分工绕开了在 Linux 上调实时这条路：控制环与安全回路在 STM32 上，毫秒级节拍由裸机保证。上位机只承担百毫秒级响应，定位修正按 10 赫兹发布，调度抖动在这个量级里能被吸收。Jetson 用之前把频率模式与散热状态一起确认，省电模式加高温降频叠在一起，帧率掉得没有规律。

## 内存管理

操作系统给每个进程分配虚拟内存，通过页表映射到物理内存。内存不够会触发交换，一旦开始交换，实时性无法保证。点云和图像占用内存很大，程序跑起来用 top 观察常驻内存曲线，平稳的可以放心，持续上升的要查泄漏，valgrind 和智能指针是常用工具。录包对磁盘的消耗最大，盘写满之后进程会以难以定位的方式崩溃，所以录包目录单独放在一块盘上，并设置写入阈值报警。

机制的细节：虚拟地址按页映射，页的单位通常是 4 KB，物理内存不够时，系统把不常用的页写到交换区，之后每次访问要换回来，延迟从纳秒级跳到毫秒级，所以车上把交换区关掉，内存紧张时宁可让进程退出，也不让整机拖慢。内存耗尽时系统挑一个大进程杀掉，现象是程序夜里自己退出了，dmesg 里留有记录，常驻内存曲线是提前发现它的工具。泄漏排查的顺序：持续上升的曲线指认嫌疑进程，valgrind 定位到分配点，C++ 侧智能指针管住生命周期，shared_ptr 的循环引用单独过一遍，两个对象互指，引用计数永远不归零。录包链路的账单独算：点云与图像写盘量按每秒几百兆计，给 bag 设单个文件大小上限，录包盘与系统盘分开，写满之前报警。

## 异步与超时

上位机上的一个任务经常要同时等好几路 IO：等相机出新帧，等串口回包，等另一台车的心跳。每处开一个线程成本高且收尾麻烦，异步把等待变成事件循环里的一次注册，一个线程管很多路等待。asyncio 的三件基本物：async def 定义协程函数，await 把执行权让出去，事件循环在条件满足时把协程接回来。基础形态的等待是裸 await，没有超时，对端不回包，任务就停在那里，上层流程跟着卡死。这段进阶档代码处理的是等待的收尾：超时放弃，取消回收。

```python
# 进阶档: 超时放弃, 取消回收
import asyncio

async def wait_ack(stream, task_id, timeout=0.3):
    # 在 timeout 秒内等一行回包, 超时按失败处理
    try:
        line = await asyncio.wait_for(stream.readline(), timeout)
    except asyncio.TimeoutError:
        print(f"指令 {task_id} 无确认")
        return None
    return line

async def send_with_confirm(stream, send_fn, task_id):
    waiter = asyncio.create_task(wait_ack(stream, task_id))
    try:
        await send_fn(task_id)          # 发指令
        return await waiter             # 等确认
    except asyncio.CancelledError:
        waiter.cancel()                 # 取消路径: 等待任务一起停
        await asyncio.gather(waiter, return_exceptions=True)
        raise                           # 取消继续向上传, 不能吞掉
    except Exception:
        waiter.cancel()                 # 发送失败: 同样不留没人管的任务
        await asyncio.gather(waiter, return_exceptions=True)
        raise
```

对照关键行。wait_for 到点会取消内部的等待并抛出 TimeoutError，捕获之后按失败返回，异常不往主循环上冒。create_task 建出的等待任务要有归属：正常路径在 return await waiter 处收掉，取消路径在 except 里手动 cancel，再用 gather 等它真正退出，这两步缺一步就会留下没人管的任务。CancelledError 捕获后必须重新抛出，吞掉它会让上级以为任务正常完成，关闭流程跟着乱。超时值示例取 0.3 秒，实际数值进参数表，与第 9 章的判定间隔对表。还有一条边界：事件循环跑在单线程里，协程里直接调用阻塞函数会卡住整个循环，阻塞调用交给线程池或留给 ROS 的执行器去做。

## Linux 生存手册

工具箱：ssh 免密登录，rsync 拉文件，tmux 让任务在断连后继续跑，journalctl 看服务日志，systemd 管理开机自启的节点。串口设备名会在重启后变化，用 udev 规则按 USB 口给设备起固定名字，权限加进 dialout 组。车上的系统装好就做整盘镜像，坏了直接换盘，恢复以分钟计。

几件工具的用法细节。ssh 免密：本机生成密钥对，把公钥送到车的账号里，之后登录与 rsync 都不用输密码，密钥生成时带注释，换机器时能认出来是谁的。rsync 拉日志与录包比 scp 灵活，-av 保留属性与时间，--delete 只在目录镜像时用，别对着错的路径用。tmux 解决断连问题：训练场上 ssh 一断，前台的进程跟着死，把任务放进 tmux 里跑，会话断了 attach 回来接着看，长任务再配一份输出重定向到日志，双保险。journalctl 看服务：-u 指定服务，-f 跟尾，-b 只看本次开机，服务起不来先看它的最后二十行。整盘镜像：系统装好调通之后备份一份，盘坏直接换盘，恢复时间以分钟计。

下面这段是进阶档写法，把两件手工操作固化成配置文件：串口固定名与开机自启。

```bash
# 进阶档: 串口固定名与开机自启两份配置
# udev 规则: 按 USB 物理口固定串口名, 同型号设备不撞
sudo tee /etc/udev/rules.d/99-stm32.rules > /dev/null <<'EOF'
KERNEL=="ttyUSB*", KERNELS=="1-2", SYMLINK+="ttySTM32", MODE="0660", GROUP="dialout"
EOF
sudo udevadm control --reload-rules
sudo udevadm trigger

# systemd 服务: 开机把整车链路拉起来
sudo tee /etc/systemd/system/robot.service > /dev/null <<'EOF'
[Unit]
Description=ROBOCON onboard stack
After=network.target

[Service]
User=robot
ExecStart=/home/robot/run_stack.sh
Restart=on-failure
RestartSec=2

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now robot.service
```

对照关键行。udev 规则按物理口位置匹配，两个同型号的串口设备插在不同口上也能各得一名，SYMLINK 起别名，代码里只认这个别名，权限与属组一次配好。reload 与 trigger 让规则立即生效，不用重启。systemd 单元里：After 让网络先就绪，ExecStart 指向包装脚本，Restart 与 RestartSec 管进程退出后的自动拉起，WantedBy 决定开机自启。包装脚本里 source ROS 环境再启动节点，原因在于 systemd 起服务时没有登录 shell 的环境，环境变量不在，直接把长命令写进单元文件就会起不来。服务起来之后再看一遍订阅与心跳是否正常，这条进预检清单。

## 时间戳纪律

每份数据都带时间戳，时间戳来自同一个时钟源。双车协作先对齐时钟，再谈数据融合。ROS 里仿真时间和墙钟时间不能混用，录包回放走仿真时钟，实时链路走墙钟。角速度大时，时钟偏差会放大成空间错位，角速度 180 度每秒时，10 毫秒偏差就是 1.8 度旋转错位，点云立刻分层。

时钟源的口径：车上默认用系统时钟，联网时由 NTP 对时校准，离线之后靠晶振自己走，长时间离线有累积偏差，双车对时用第 9 章的往返估计。回放链路的两个开关要成对使用：播放端的 --clock 与订阅端的 use_sim_time 同时打开，只开一边，时间戳一半仿真一半墙钟，数据排布立刻错乱。时间戳在信号进入系统的第一站打上，不要在转发节点里补打，排队与转发的延迟会被写进时间戳，后面所有延迟分析都被污染。传感器之间的对齐：相机与雷达的采样时刻不同，融合前按时间戳对齐到同一时刻，快速旋转下 10 毫秒的错位就是 1.8 度的空间错位。

## 常见坑清单

- 回调里做阻塞操作，单线程执行器被拖住，其他话题一起延迟。
- 持锁期间调用回调或做 IO，锁范围越滚越大，极端情况进死锁。
- 用 sleep 等硬件就绪，换成事件通知或轮询加超时。
- systemd 单元里直接写长命令，环境变量不全，服务起不来，命令放进包装脚本。
- udev 按厂商产品号固定串口名，两个同型号设备撞名，改用物理口或序列号。
- 交换区没有关闭，内存一紧张，整机延迟失控。
- 仿真时钟与墙钟混用，数据时间戳错乱，录包回放对不上。

## 几条小结

- 疑难问题排查到最后，多数落在进程状态和网络链路这两个基础环节。
- 共享数据尽量减少，锁的粒度要小，临界区要短。
- 实时任务放在 STM32 上执行，上位机的调度抖动难以根除。
- 车上系统装好后先做整盘镜像备份，故障时恢复以分钟计。
- 共享统计量要么加锁要么只留一个写者，两条路选一条走透。
- 异步的取消路径要写完整，取消不回收会留下没人管的任务。
- 串口名按物理口或序列号固定，开机自启用包装脚本把环境带齐。
