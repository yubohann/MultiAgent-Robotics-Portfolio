# 第 13 章 通信案例

> 通信出问题时现场表现各不相同，丢一个包，球就传空半个场。这一章四张卡，依次讲丢包，线材，网络配置和无线信道。

## 案例 1：双车丢包与挂号重发机制的诞生

**现象**：双车联调，传球动作对不上，商量好的时机全乱。发送车日志记着指令发出去了，接收车没有任何记录，球接到一半停住。丢包毫无规律，偶尔连着丢，节奏直接断掉。

**排查路径**：

1. 抓收发两端日志对时间轴，指令确实发出了，对端确实没收到。指令序号在接收侧有跳空，丢失发生在空中
2. 换位置拉近距离，丢包变少，依然存在，链路不保证送达。距离只是一个因素
3. 查干扰源，备馆里同频设备密集，信道拥挤，单包丢失成了常态。手机热点，图传，遥控器都挤在 2.4 吉赫兹上
4. 复盘时重新梳理一遍，链路只做尽力而为，应用层得把可靠性接过来。链路的定位是尽力送达，可靠性要由应用层补上

**根因**：ESP-NOW 是无连接链路，单包上限 250 字节，丢包后发送端不会收到任何反馈。第一版协议发完即结束，没有确认与重发，丢一个包就有一个动作作废。发送完成回调只说明本地发出，不代表对端收到。干扰下的丢失呈突发性，连续几个序号一起消失，只做单包重试会连着撞上同一段坏窗口，重试要带间隔与次数上限，挂号重发的设计由此而来。

**解决**：设计挂号重发状态机。指令带任务标识与序号，先挂号后发指令，接收方回确认，超时重发，重发不超过 3 次。去重逻辑保证重发不重复执行，指令过期不执行。心跳 20 赫兹一帧，300 毫秒收不到就进安全降级。急停最高优先级，锁存加人工复位。五个机制各有分工，心跳报活解决链路判断，应答确认解决单条送达，去重解决重发重复执行，过期解决迟到指令，急停解决最坏情况。接收端对同一任务标识的同一序号只执行一次。

**预防**：

- 传球与接球按对方确认推进，对方没确认，这一步不往前走
- 协议测试加丢包注入与延迟注入，异常帧一起测，测完才准上车。注入的口径是丢包，延迟，乱序，重复，全过才算通过
- 五个机制随协议文档一起交接，新人不改机制只加字段，新字段只往尾部追加
- 每场练习赛结束看一次通信统计，丢包率，重发次数，心跳断连次数，三项一起看趋势
- 协议版本号随包发出，两端版本不一致时拒绝执行高风险指令

延伸：协议文件后来定成固定结构，五个机制一页纸讲清，字段表列出名称，类型，单位，取值范围，文末附改动记录。新人接手先读这一页，改协议之前先想清楚改动落在哪个机制上。

## 案例 2：串口乱码排查，从波特率到线材

**现象**：上位机日志里开始出现乱码，帧头解析时不时失败，偶尔一帧 CRC 对不上。重启能正常一阵，跑几个激烈动作又出现。故障还有时间规律，白天少，晚上频繁。晚上的连续大动作调试把问题催了出来。

**排查路径**：

1. 先对波特率与帧格式，两端配置逐项核对，全部一致，软件假设排除。波特率，数据位，校验位，停止位，逐项对过
2. 上逻辑分析仪抓原始字节，乱码与电机大电流动作出现在同一时刻。乱码帧出现的时刻与电机加速段的电流峰值重合
3. 查线材，信号线与动力线捆在一束里走了很长一段，嫌疑很大。耦合路径清楚了
4. 检查端子，一个压接松动的接插件，车一颠它接触时好时坏。逐段做拉动试验，端子手一拽就动，间歇断点就在这里

**根因**：两件事叠加在一起，信号线贴着动力线走，电机动作的噪声耦合进串口信号。一个压接不良的接插件在振动下时通时断。单独看每项都不严重，叠加后成了疑难故障。串口是单端信号，电平相对地线判断，动力电流在地线上的波动会把判决阈整体抬落，电机的脉宽调制边沿又通过并行线束耦合进信号线，两路夹击之下字节被翻。压接不良是第二种病，接触电阻随振动与温度变化，时通时断，两种机理叠加才难查。CRC 能发现错误帧，重同步能让链路恢复，来源不除，故障率就降不下来。长帧对波特率偏差还更敏感，两端时钟的微小偏差在帧内累积，采样点逐位后移，靠后的字节最先出错，这是把帧长压短，校验随身带的一条理由。

**解决**：重压端子，接插件换新并加固。信号线改走线路径，与动力线分开，长距离平行贴着走的一律拆开，这一点和布线章节的规矩对上了。CRC 与重同步机制保留，乱码发生率归零，连续跑一整天没再出现。压接标准补进工艺，端子压接后做拉拔检查，接插件带防松结构，交叉处走垂直。

**预防**：

- 走线工艺写进装机标准，信号与动力分开，验收时逐段看，新线束入库前过一道走线检查与拉拔抽检
- 串口设备名用 udev 规则绑定，避免端口与设备错配，绑定文件随配置进版本管理
- 开机自检加一条链路检查，收发一帧对一帧再放行
- 传输质量进日常记录，错误帧计数与重同步次数突然变多，先查线束再查协议
- 长走线的机内链路优先双绞并带地线参考，条件允许时上差分传输

## 案例 3：ROS 多机网络的 IP 迷案

**现象**：多机联调时，ROS 里两台设备时隐时现。下午能 ping 通，傍晚就看不到，换一条网线能正常半天，之后恢复原状。数据在链路上时断时续。

**排查路径**：

1. 先 ping，通断规律对不上任何物理操作，单纯线缆问题排除。插拔，搬动，开关机都试过，规律对不上
2. 换交换机，问题照旧，设备端口也排除。视线转到配置层
3. 顺带扫了一遍网段，两台设备的地址完全相同，追查下去，源于复用旧配置
4. 再看发现机制，场馆网络把多播关了，两台机器本来就看不清对方。两件事叠在一起

**根因**：网卡地址冲突加多播被禁，两个问题叠加。地址冲突让数据包发不到正确目标，多播被禁让节点的自动发现失效。两个问题的源头都在网络配置层。地址冲突时，两台设备对同一个地址的询问互相应答，数据包时而送到这台时而送到那台，表现就是时隐时现。发现机制依赖多播交换节点信息，多播一堵，谁也不认识谁。两件事的表现相似，都像链路不稳，分开测才能拆开。

**解决**：全队定了一份静态地址分配表，一机一地址，写进车上的配置，不允许临场改动。发现机制改成单播配置，把对端地址显式列出来。启动自检里加一条链路检查项，拓扑里该看到的设备一个不能少。地址表定成三列，设备名，地址，责任人，改一台登记一台。发现机制准备两套配置，多播可用用多播，受限时切单播对端名单，进场按网络条件选一套。

**预防**：

- 网络配置进文档，出发前全队按表核对一遍
- 新设备入网先查地址再连网络，一次入网一次登记，地址顺手写到设备标签上
- 场馆网络条件不可控，链路检查项固定放在自检里，两套发现配置都留在车上，切换动作写进流程卡
- 临场换网络之前先把新网络的地址规则问清楚，没有把握就沿用自带交换机的小网
- 自检的设备清单固定下来，连接级，进程级，数据级各有一项，网络一变先跑清单再上任务

## 案例 4：无线信道干扰与信道切换

**现象**：同一个频道，早上双车通信正常，观众一多就开始丢包。练习赛间隙最挤的时候，心跳都会断，链路判定降级，车停住等。丢包看起来随机，实际与场馆人流同步起落。

**排查路径**：

1. 记录丢包率与时间的对应关系，高峰与人流高峰重合。丢包率曲线与观众人数曲线形状一致，早晚两头低，中间高
2. 把车挪到场馆不同角落测，干扰跟着位置变，2.4 吉赫兹频段的拥挤是主要嫌疑。靠看台一侧丢得凶，场地中央好一些，两个观察指向同一处
3. 换信道重测，同一时段丢包率明显变化，信道选择有效
4. 配合心跳与重发观察，干扰期间动作靠确认推进，安全底线保住了。链路最差的时候，车停在安全状态

**根因**：2.4 吉赫兹频段在赛馆里高度拥挤，同频设备互相干扰，单包丢失率随环境波动。信道选错，等于一直在最拥挤的信道上通信。观众的手机热点与场馆接入点在高峰时段把信道占满，常规无线设备又扎堆在少数几个信道上，空闲窗口少。ESP-NOW 收发双方必须同信道，换信道要两台车一起换，换完要复测。干扰造成的丢包随时间波动，机制上是信道竞争，拥挤时段单个包被挤掉的概率上升。信道号还要在双车之间核对一致，参数表里信道一项写成显式字段，上车前对表。

**解决**：进场先做信道扫描，挑相对干净的信道，双车同时切换并复测。信道号写进参数表，跟车走。丢包由心跳与挂号重发兜底，通信质量记入联调清单。扫描的做法是先摸一遍周边占用，挑相对干净的几个信道，双车同步切换，再用丢包测试跑一轮确认，留下的那个写进参数表。比赛期间把每场的丢包率记下来，与人流时段对照，为下一场选信道留参考。

**预防**：

- 信道选择变成场地适应期的固定动作，每换一个场馆重新扫，训练期建一份丢包与信道的对照记录，进场先查表再扫描
- 蓝牙这类在赛场本就脆弱的链路，正式方案里只作备份
- 关键指令全部走确认链路，链路不健康就停住等，比赛节奏主动放慢

延伸：无线链路的纪律落在三处，一是进场前把频段测干净，二是关键指令只走带确认的通道，三是链路异常时停在安全状态等恢复。后续如果引入更多无线节点，先做占用测量再定频点，测量记录留档，不靠现场临场发挥。
