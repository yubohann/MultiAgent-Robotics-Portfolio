# 第 1 章 上位机选型：两台车，两台电脑

> 装车第一个月，学长把一台 NUC，一把内六角，一袋网线放到我面前，要求只有一句：ssh 能通就算赢。我当时没觉得这有什么难。后来熟悉了两台车的分工，才看懂这台 NUC 和半自动车上那台 Jetson 的关系。

## 两台车，两台电脑

那个赛季两台主赛篮球车分工不同，一台遥控，一台半自动，上位机配置跟着分工走。

**遥控车配 NUC。** 这台车负责运球，传球，走位，全听操作手指挥。电脑不需要多大算力，第一位的是稳定。x86 生态成熟，ROS 的包装上就能用，价格合适，从遥控器到电机的控制链路也短。NUC 与这台车最匹配。

**半自动车配 Jetson NX 8GB。** 这台车负责找篮筐，算距离和角度，生成发射参数，自动投篮。视觉推理依赖 GPU，Jetson 的 CUDA 正好对上。8GB 内存要同时支撑定位，检测和任务逻辑三部分，余量不大，足以打完一场比赛。

两台机器的任务清单不一样。遥控车那台是短的：人工指令换成车体速度，机构动作按序列执行，状态回显给操作手。它不碰视觉，也不碰定位，算力需求是平的。半自动车那台反过来，视觉推理和激光定位两个重活一起吃 CPU 与 GPU 的预算，任务调度也更复杂，NX 8GB 这台就是给这两件事准备的。

两台电脑各管一台车。两车之间没有线缆，也没有共享内存，数据交换全走无线。分工的好处是直接可见的。

## 一台车载电脑的检查表

车上的电脑不是放在桌上用的，选型时先把检查项列成一张表，再按表核对候选。

- 接口：网口要够雷达和调试两路，USB 口要够相机，手柄接收端和调试线，串口按需留。
- 供电：先看输入电压范围，再看峰值功率。车上是 22.2 伏一级的电池母线，电脑要么自带宽压输入，要么配一级 DC-DC。
- 体积与重量：电脑要跟着车跑，碰撞是常态，固定孔位和减震安排在选型阶段就要确认下来。
- 散热：封闭车体里没有风道，CPU 和 GPU 持续满载时，散热片和进风口的位置要提前留。
- 时间基准：电脑要能被外部时钟校时，录包和多机联调都依赖统一时间，这一项容易被跳过。
- 生态：驱动，镜像，排错经验这三样，决定出问题之后的恢复速度。
- 价格与货期：预算内的型号还要在比赛前到货，两个条件同时满足才算数。

权重因人而异，我们的排序是生态与稳定在前，参数在次，价格最后。这张表在采购前对一遍，到货装机再对一遍，两遍结论不一致的地方，就是选型时漏掉的项。

## 候选机型评估：迷你主机与双机方案

候选清单上还有两类机器，我们把账算完才排除。

第三方迷你主机。参数表上同样的核心数，价格能低一截，接口有时给得更足。售后与支持的问题放在后面展开，这里先补一笔评估记录：候选里有一台两千元档的小机器，账算下来，球检测和框检测两路任务同时开就吃紧，只能保一路。核数不等于能同时干几件事，这条在便宜机器上体会得最直接。

CPU 与 GPU 两条线。选型初期有一条通用判断：重 CPU 的任务多，选 x86 迷你主机。重 GPU 的任务多，选带 CUDA 的板子。两样都重，就考虑两条线并存的机型。我们两台车的任务正好分成这两种，这条判断落地就是两台机器，各自匹配各自的任务，一台全能的机器没有出现在方案里。

双机方案。一台车上挂两台电脑的做法评估过。账的大头在链路：两台机器之间每交换一次数据，带宽和延迟都要叠加进端到端时间，任务分工和统一调度也要多维护一层。两台车两台电脑是另一回事，那是按车分工，各自独立，这个组合一直跑到赛季结束。

部署经验参照。给四足项目做准备时，我们存过一份 legged_control 的本地部署指南，参考机配置记录得很清楚：NUC11，Ubuntu 20.04，ROS noetic。指南里着重标了一处工具链的坑：构建要用 catkin build，先跑 catkin_make 会让后续步骤失败。这类细节单看是小事，复现时才用得上。这份记录后来也成了我们评估机器时的参照点。

## JetPack 与 CUDA 的上手成本

Jetson 的账要另算一笔时间。系统用官方的 JetPack 镜像刷进去，工具链与 x86 上的习惯不一样：系统镜像和控制固件捆在一起升级，深度学习库要跟着镜像版本对表，自己编译的包在 ARM 上耗时更长。这些属于上手成本，队里如果没人提前摸过，调试期要多花几天。

实际做法是装好一台就留档：镜像版本，库版本，编译脚本各备一份，后面复装照着走。散热也是 Jetson 要提前想的，满载跑视觉时散热片是热的，车体内的风道不设计好，推理速度会在长时间运行后往下掉。

x86 那台省心得多。包管理是常规的 apt，生态顺，遇到问题能查到的回答多。遥控车配 NUC 的底气也在这里，它不跑重活，稳定和省心排在参数前面。两台机器的系统镜像和软件清单各自留档，一车一套参的习惯从选型期就定下来。

## 2025 年当时，其他选项为何出局

选型要贴住时间点。2025 年做决定时，候选方案有这些。

- **树莓派**：价格最低，但视觉和定位同时跑就吃力，算力不足以支撑半自动车的任务。
- **Jetson Orin 系**：性能好，但当时价格高，货期不稳定，预算和赛程都等不起。
- **RK3588**：NPU 跑轻量模型够用，成本也低，但当年生态年轻，工具链不成熟，正赛要的是稳。这块板子属于后来上手过的平台，故事留到别处写。
- **工控机**：稳定性好，但重量，功耗，价格三条摆到车上都不划算。
- **第三方迷你主机**：参数漂亮，出问题查资料难，售后责任不清。车载设备最怕的是坏了没人管。
- **双车共用一台电脑**：跨车的线缆和通信环节复杂，坏一处两车都停，分开更可靠，放弃。

最后落在 NUC 加 Jetson NX 8GB 这个组合上。这套组合陪我们跑完整个赛季。

## 算力预算：识别，定位，决策怎么分

上位机的任务分三部分。识别跑 YOLO，主要占 GPU。定位跑 FAST-LIO2，主要占 CPU。决策与任务逻辑计算量不大，但对实时性和内存敏感。

装系统当天就要把内存预算做出来。我的习惯是赛前把每个进程的 CPU 和内存占用过一遍，给录包留出余量。录包的磁盘写入在关键时刻会造成卡顿。8GB 内存，三部分任务加系统加日志，分完之后余量很紧。

量占用不需要复杂工具。CPU 和内存用系统自带的监控看，Jetson 上还有官方的 tegrastats，各核占用，内存，温度和功耗一屏都给。满载跑一遍检测加定位，数据就齐了。录包单独记账：一段比赛长度的包有多大，写到哪块盘，写满了会不会顶掉正在跑的任务，这三问在装系统当天就该有答案。

8GB 这笔账可以摊开看。操作系统和基础服务占一档，FAST-LIO2 的地图与点云缓冲占一档，检测模型与推理框架占一档，任务逻辑与日志占一档，剩下的才是录包和其他余量。四个档位里，点云缓冲和录包最容易低估，前者跟着地图规模走，后者跟着记录习惯走。赛前把这两项的实测值记下来，写进装机记录。

升级算力之前，先摸清当前占用。我们那年两台电脑从实验室跑到赛场，平台一路用到底。选型时多花一周想清楚，比开赛后临时换机器便宜得多。

## 对标：哈工大把强化学习用进控制

有一个点我记到现在：哈尔滨工业大学把强化学习用进了控制方案。这个方向值得留意。

我们那套系统里，参数靠人工标定，策略靠状态机写死。这套方法可控，但每年题目一换，不少工作要重做。强化学习如果进入控制与决策，迭代方式会变：一部分参数和策略可以在仿真里练出来，人把精力留给规则和接口。2025 年我们止步于此。想接手的同学，仿真和算力这两门课要提前补，这里消耗的主要是时间和设备。

## 小结

电脑跟着任务选，算力预算在装系统当天做出来，生态成熟度决定出问题时解决问题的速度，属于长期成本。这三条在后面各章的选型里一直适用。
