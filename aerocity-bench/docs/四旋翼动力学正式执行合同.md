# AeroCityBench 四旋翼动力学正式执行合同

状态：`implementation_partial / native_preflight_partial / formal_score_eligible=false`

本文冻结 AeroCityBench 的四旋翼执行边界。它不把历史能力探针、USD 文件存在或截图升级为正式实验结果。

## 1. 受控运行时资产

正式原生执行只接受用户显式提供的本地 CF2X 文件，例如：

```text
$AEROCITY_CF2X_USD
```

其根 USD 的 SHA-256 必须为：

```text
7372ac0786312c47a92603da3fcd412d560b21c3757a8f0d5e7c2bfb2233d2f4
```

相对 schema `configuration/cf2x_robot_schema.usd` 的 SHA-256 必须为：

```text
c7a63f78ce3937c25cd05936ee73348bfdbbd0a10e82c0b8a37250730a3cbb9c
```

任何缺失、哈希变化、schema 缺失、Nucleus/Omniverse 路径、旧五寸机目录或自动回退都必须在 Isaac 启动前失败。CF2X 目前仅是本地运行时依赖；其来源和再分发许可尚未完成公开发布清理，因此不得提交、打包、上传或作为 benchmark 资产再分发。

## 2. 唯一允许的 L1 执行链

```text
方法公开动作
-> 统一低层 controller
-> 四个请求旋翼推力 [N]
-> IsaacLab Multirotor + ThrusterCfg
-> 基于 CF2X 旋翼位置/转向的 allocation matrix
-> 根刚体 PhysX wrench、重力、碰撞和惯量积分
-> 测得状态和 ContactSensor
-> OBSERVE / evaluator-private 确认
-> ExecutionReceipt / FailureRecord
-> episode 分数
```

禁止作为 L1 正式执行器：

- `DynamicCuboid`；
- 飞行循环内直接写 root pose、root velocity、线速度或角速度；
- 用 joint velocity 作为推进；
- 用原始总 body wrench 替代逐旋翼推力；
- 旧五寸机、Nucleus、Omniverse 或未哈希锁定资产。

初始 root pose/velocity 只允许出现在 episode reset。飞行循环中，`Multirotor.set_thrust_target()` 接受每个旋翼的牛顿推力，`ThrusterCfg` 分别推进四个执行器状态；`Multirotor.write_data_to_sim()` 以 CF2X 的几何 allocation matrix 将四个实际推力合成为根刚体的 6D wrench，并交由 PhysX 积分。当前 IsaacLab 实现并不在四个 prop-link 刚体上分别施加外力。receipt 必须记录请求值、`Multirotor.data.applied_thrust`、allocation 语义和根刚体施力模型。

## 3. 参数与证据边界

`quadrotor_dynamics.py` 当前使用 CF2X USD 中已静态检查的质量、惯量和旋翼位置。native runner 从 `root_physx_view.get_masses()` 读取实际参与 PhysX 的各刚体质量，并要求其总和与哈希锁定 USD 的 `0.0282 kg` 在 `1e-6 kg` 内一致；不依赖 `Multirotor.data.default_mass` 这个当前可能为空的缓存。推力系数、反扭矩、旋翼方向、推进器时间常数和控制器增益仍为 `parameter_audit_pending` 候选值。它们不能因为能悬停或通过单元测试就自动升级为真实机参数。

每次 native preflight 或 L1 vertical slice 必须绑定：

- CF2X 根文件和 schema 哈希；
- `cf2x_contract.py`、`cf2x_native.py`、动力学合同和运行脚本哈希；
- 旋翼名称、分配矩阵、请求/计算/实际执行器状态的逐旋翼推力；
- `wrench_application_model=derived_geometry_allocation_to_root_body_physx` 与 `prop_link_forces_applied_directly=false`；
- `ContactSensor.net_forces_w` 接触证据；
- 控制器、城市、任务、episode、运行时与回放哈希；
- `formal_score_eligible=false`，直至所有门禁关闭。

## 4. L0、L1、L2

| 层级 | 用途 | 相机与动力学 | 正式 geometry 分数 |
| --- | --- | --- | --- |
| L0 | 训练、调试、单元测试 | 解析几何/简化动力学，无 RTX 相机 | 否 |
| L1/G1 | geometry 主榜 | CF2X、PhysX、碰撞、几何 ray/evaluator；不向方法提供 RGB | 唯一候选来源 |
| L2/P1 | 感知、回放、视觉审查 | 同一轨迹的 RGB-D/分割，只在 OBSERVE/dwell 事件触发 | 单独榜 |

关闭 RGB 渲染不等于删除相机几何。固定外参、FoV、时间戳和 LOS 仍须与 evaluator 一致。L2 渲染候选为 2 Hz，允许范围 2--5 Hz；`96x69` 与 `160x120` 是不同 profile，不能混入一个结果批次，任何切换都要重新标定。

## 5. 五个 CF2X 准入门

1. 根 USD、相对 schema、default prim、body、四个 prop 和四个 joint 全部哈希与结构核验；
2. `Multirotor` allocation、推进器、悬停、爬升、横移、偏航和制动在独立 native preflight 中通过；其中悬停至少执行 30 个模拟秒并审计热身后高度斜率、最大/末端高度误差、末端垂直速度和接触；持续横移时也必须复验同一垂直门；
3. 地面跌落的真实 `ContactSensor` 证据通过，并在后续城市障碍/窄通道中冻结碰撞语义；
4. 几何 ray、相机 rig、FoV、OBSERVE/dwell 和 profile 指纹一致；
5. 多 UAV 完成“方法动作 -> 原生执行 -> OBSERVE -> 私有确认 -> receipt/failure -> 返航/终止 -> episode 评分”。

截至 2026-07-31，代码已实现第 1 项的 fail-closed 合同以及第 2--4 项的运行入口。本机 CUDA/PhysX 的隔离 receipts 已验证：1.0 s `shared-hold` 稳定悬停；两个独立 Isaac 进程各完成 30.0 个模拟秒 `shared-long-hold`，均保持 `z=1.5 m`、末端垂直速度 `2.14e-06 m/s`、热身后高度斜率 `0 m/s`、零接触，跨进程末状态差为零；30.0 s `open-loop-hover` 的末端高度误差为 `-0.332 mm`、热身后斜率为 `-1.45e-05 m/s`；30.0 s `shared-long-lateral-hold` 在最大俯仰约 `0.0385 rad` 下到达 `0.35 m` 横移目标，末端高度误差约 `-1.07e-06 m`、热身后高度斜率约 `2.04e-07 m/s`、零接触。长时门禁的候选界限是：全程高度误差 `<=0.02 m`、末端高度误差 `<=0.01 m`、末端垂直速度 `<=0.01 m/s`、10 s 后高度斜率绝对值 `<=2.5e-04 m/s`、零接触；它会拒绝持续下沉或上升，但仍是 `candidate_preflight_only`。2.5 s `shared-lateral-hold` 横移 `0.416858 m`；2.5 s `shared-altitude-hold` 爬升 `0.300320 m`；3.0 s `shared-yaw-hold` 偏航 `1.465154 rad`；6.0 s `shared-lateral-step` 受控制动，最大横移 `0.157512 m`、末端横移 `0.023038 m`、末端速度约 `0.05537 m/s`。所有这些无接触机动都实测到 PhysX 总质量 `0.0282000003 kg` 与锁定 `0.0282 kg` 一致。另一个 3.0 s `open-loop-drop` 地面接触诊断在约 `2.07 s` 首次接触，峰值 `ContactSensor` 力为 `5.379 N`，最终根刚体高度约 `0.015 m`；它只证明地面接触信号和 PhysX 接触响应，不证明城市障碍、机间碰撞或安全策略。

三座相互独立的开发城市已完成相同的单机 private slice：calibration、train、validation 分别在 167.0、192.6、205.8 个模拟秒内完成一次 `OBSERVE` 私有确认、零接触、零越界和返航闭环；实际墙钟分别约为 52.8、61.9、65.5 秒。初版候选 guidance 曾在 return 末段出现边界越界，同时存在随残余水平误差逐周期变化的 yaw 目标；修复后的 candidate guidance 将 position target 锚定于测得状态、分别限制水平/垂直速度，并对三段安全天空路线冻结每个路线段的 yaw。三次通过说明该修复在三种开发 split 上可重复，但不证明因果充分性、城市碰撞安全、窄通道能力、真实机参数或多机稳定性。每次 slice 还强制使用新的、不同的 public/private `.json` 文件路径；已存在回执、同名 public/private 路径或非 `.json` 路径会在 Isaac 启动前失败。

这些回执不进入 Git，因为它们披露本地资产路径和私有运行内容；它们仍不能替代四机闭环或正式评分。历史 DynamicCuboid 11/11 能力报告也只证明该探针本身，不能替代任一 CF2X 门。

### 5.1 四机共享世界策略预飞行，仍非正式 episode

2026-07-31 新增的 `cf2x_l1_fleet_preflight.py` 在同一个 Isaac PhysX world 中生成四架本地 CF2X。它将公开 ID 与 Isaac-safe prim path 分离，每个物理 tick 均先写完四架机的逐旋翼推力、再且仅再执行一次 `sim.step()`；每条 L1-like receipt 按 `action_sequence -> drone_id` 排序、连接 action/observation/state/previous-receipt 哈希链。历史 v3 仍保留；最新 v4 会明确拒绝旧 schema，并额外绑定公开路线预算审计、policy 调用延迟与 G1 公开观测构建延迟的独立分位数、以及 deadline-miss tick 数，避免把缺字段或混合延迟静默视为有效。

历史证据必须保留并如实解释：v12 在 97.0 个模拟秒发生 `uav-03` 下界越界，末端约 `z=0.6165 m`、`vz=-4.90 m/s`。对 v11/v12 的同前缀比较表明，它不是悬停慢性下沉，也不能用延长预算掩盖。根因包括 reference route 在未抵达高到低转场航点时将短暂静止误判为“卡死”，以及局部 occupancy 将远距离转场误当作可跳过的扫描位姿。两种跳过都会产生不连续的低空指令。修复为：reference policy 必须持续发布未抵达航点；occupancy 只可处理已进入本地感知半径的实际 scan pose。另加入只读取测得高度、垂速、公开 flight bounds 和机体半径的 candidate vertical braking envelope；它以速度上限和制动距离限制下降参考，不写 root state，也不会在低层观察目标上永久禁止下降。

修复后的 v13（90.0 模拟秒）为零碰撞、零越界，但尚未 OBSERVE；v14（120.0 模拟秒）为 600 control ticks、7,200 shared PhysX steps、零碰撞、零越界、28 次 `OBSERVE`，评测器均接受，v3 receipt/binding/public-private commitment 检验均通过。它没有 confirmation、RETURN 或完整 episode 分数，且出现 92 条 planner deadline miss；因此仅记录为“公开策略已进入观察/评测器入口”的候选工程证据，不能称作任务成功、baseline 成绩、真实飞行或 formal L1 result。

随后对原始 exhaustive `sweep-3d` 公开路线进行了 300 s 冻结预算的逐机运动下界审计。历史路线在 1.5 m/s 水平、1.0 m/s 垂直速度下的下界约为每机 1,100--1,500 s，故已确定为 P0 `BUDGET_INFEASIBLE`，不得再启动 Isaac 后才发现超时。v4 在 AppLauncher 前 fail-closed 拒绝这类路线；公开 `task_spec` 新增仅含全城 collider 高度包络的 safe-sky transit contract，不披露目标、组件坐标或 evaluator 私有内容。候选的稀疏、每机最多一个公开 facade group 的 `sweep-3d` 仅是预算化 coverage diagnostic：其当前 calibration 路线在同一速度下的乐观运动/停留/返航下界为 237.18--255.40 s。该下界允许水平与垂直同时运动，仍不包含控制收敛、避障、姿态变化或计算，不能证明 native 完成，更不能变成正式 baseline 成绩。下一门仍是以公开策略完成 `OBSERVE -> evaluator confirmation -> RETURN -> episode score`，并单独降低或解释 G1 occupancy 的 deadline miss，不能通过提高目标高度、读取 private episode 或简单拉长任务时限绕过。

v4 的新派生 calibration 输入已完成原生复核，原 city 与历史 v12--v14 报告均未覆盖。`shared-hold` 在 30.0 simulated s、150 control ticks、1,800 shared PhysX steps 中四机均通过高度门：31 个测量样本、全程高度跨度 `0 m`、末端垂直速度绝对值最大 `2.14e-06 m/s`、热身后斜率 `0 m/s`、零碰撞、零越界、零 deadline miss。初始 `public-policy` 在 120.0 simulated s、600 ticks、7,200 shared PhysX steps 中零碰撞、零越界、零 FailureRecord；它产生 4 次 `OBSERVE` action 和 3 份 observation receipt，但仍为 0 confirmation、0 RETURN、7 个 deadline-miss tick、未返航。

后续必须保留失败反例。路线收紧后的 v5 public-policy 在 `54.6 s` 发生 `uav-00` 出界：安全天空转场同时请求约 `180 deg` 的立面朝向，横移和大幅偏航耦合导致错误方向漂移。其 public/private 哈希链和 CPU validator 均 PASS，但 `safe_completion=false`，所以它是有效的失败证据，绝不是通过。修复后，非 `OBSERVE` 转场保持测得姿态；同位置的 staging pose 到达并稳定后，才以零平移转向立面。v6 在相同 city、速度、CF2X 文件和 120.0 simulated s 中完成 600 ticks/7,200 shared steps，零碰撞、零越界、零 FailureRecord，且仅 `uav-00` 发出 4 次合法 `OBSERVE` 并得到 4 份 observation receipt；仍为 0 confirmation、0 RETURN、未返航，policy deadline miss 为 5。它只消除了该首段姿态耦合越界的复现，不能表明四机均完成搜索，也不能表明高度轨迹已进入稳态：策略运行中的爬升/下降是路线指令，不应用 shared-hold 的零漂移阈值解释。防慢性下沉的证据仍只来自独立的长时悬停和横移保持门。

所有这些 public/private 报告均由 CPU validator 复核 PASS；它们保留在 `E:/` 的本地私有工程证据中，且始终 `formal_score_eligible=false`。runner 对未来运行会把 progress receipt 终态写为 `COMPLETED`、`FAILED` 或 `REJECTED`；新的 v7 30 s shared-hold 已原生复核此修复，最终 `COMPLETED`、150 ticks/1,800 shared steps、零高度斜率和末端 `|vz|=2.14e-06 m/s`。v5/v6 遗留的 `IN_PROGRESS` 文件是已知历史工具缺陷，不能被视为活动进程。这些结果不能替代完整路线、城市窄通道、跨城市或正式评分验证。

### 5.2 四机 private-witness fixture：三座开发城市原生预飞行通过

`cf2x_l1_fleet_preflight.py --execution-mode private-witness-fixture` 只用于验证一条最小共享世界因果链：`OBSERVE -> evaluator-private confirmation -> RETURN -> all-home`。评测器从私有 episode 的预验证 witness 中确定一条候选路线；公开方法、公开报告和公开路线预算审计均不会取得 target、witness、其坐标或选中机 ID。公开报告只保存 `private_fixture_commitment` 哈希，完整 route 与私有证据只保存在本地 `E:/`。

该模式必须同时满足：四架 CF2X 在同一个 PhysX world；每个物理 tick 先写四份逐旋翼推力再执行一次 `sim.step()`；确认只可附着到 evaluator 接受的 `OBSERVE` source observation；至少一条实际 `RETURN` receipt；所有四架机进入各自公开 home radius。任何一个条件缺失只能写成 `PRIVATE_FIXTURE_INCOMPLETE` 并以失败终态退出，不能因“安全完成”或“有确认”标作闭环成功。CPU 合同与篡改回归已覆盖确认挂接、公开泄漏、确认计数和无 RETURN 伪造。

2026-07-31，calibration/train/validation 三座独立开发城市的原生 fixture 均提前闭合：模拟时间分别为 `228.0/200.2/164.8 s`，控制 tick 为 `1,140/1,001/824`，shared PhysX steps 为 `13,680/12,012/9,888`；每城均为4次 `OBSERVE`、1个确认、零碰撞、零越界、零 planner deadline miss，并分别产生 `568/499/409` 条实际 `RETURN` receipt，四机均回 home。每个 public/private 哈希链和 CPU validator 均 PASS，progress 均为 `COMPLETED`。`tools/summarize_cf2x_fixture_preflights.py` 只读取三份公开报告，拒绝路径/内容哈希重用、目标或 witness 键泄漏、未闭合状态和覆盖既有聚合证据；输出只含 commitment、非敏感计数和 aggregate hash。完整私有证据只留在本地 `E:/`，不提交 Git。三城复现只证明内部最小因果链可运行；它仍不是四机完整 search episode、公开 baseline、正式 L1 结果或论文实验。

## 6. 论文证据

论文必须报告 vehicle/controller/sensor/task 四类配置分离、每旋翼推力单位、质量与惯量来源、接触/失效处理、native 吞吐和低保真偏差。至少要给出悬停、爬升、横移、偏航、制动和狭窄通道的测得轨迹，并把 L0 与 L1 的排名相关、淘汰误差和安全漏报作为校准结果，而不是用 L0 分数代替 L1。

仅展示机体外观、USD、相机截图或历史 capability PASS，不足以证明 benchmark 使用了真实四旋翼动力学。
